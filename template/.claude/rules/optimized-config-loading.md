# Загрузка конфигурации (частичная)

Скрипт `.claude/tools/load-config-optimized.py` загружает в ИБ **только изменённые
файлы** конфигурации (`1c-batch load-config src/cf --list-file …`). Частичная
загрузка — единственный режим: она корректно отрабатывает все четыре операции —
добавление и удаление реквизита, добавление и удаление объекта — с тем же
результатом, что и полная перезагрузка, но быстрее (полный режим `--full` убран за
ненадобностью). Кроссплатформенно; требует Python 3.6+, git и локальную копию
`1c-batch` (wrapper `.claude/skills/1c-batch/scripts/1c-batch.py`).

Скрипт берёт изменённые файлы из `git diff` относительно `HEAD` по `src/cf` (плюс
новые untracked-файлы), сводит каждый подфайл объекта к корневому файлу объекта
метаданных и запускает загрузку. Если изменённых файлов нет — загрузка пропускается.

## Кто и когда запускает

Загрузку ведёт **оркестратор** на этапе `develop`, только если в `task.json` включён
флаг `update_db` (см. навык `task-orchestration`). Субагенты её не запускают:
это долгая фоновая операция, а субагент не умеет «проснуться» по её завершении и
просто жёг бы токены в ожидании.

## Запуск в фоне и лог процесса

Оркестратор (главный цикл) запускает загрузку **в фоне** с перенаправлением всего
вывода в лог, после чего НЕ опрашивает процесс в цикле — харнесс сам разбудит
оркестратора по завершении процесса. Только тогда оркестратор читает лог.

```bash
# <id> — идентификатор задачи; каталог logs/task#<id> создать заранее
python .claude/tools/load-config-optimized.py > logs/task#<id>/load-config.log 2>&1
```

- **Где лог:** `logs/task#<id>/load-config.log` (stdout+stderr скрипта).
- **Как анализировать:** дождавшись завершения процесса, проверь код возврата и
  содержимое лога:
  - код возврата `0` и строка `✅ Оптимизированная загрузка завершена` — успех;
  - строка `✅ Нет изменённых файлов конфигурации — загрузка не требуется` — грузить
    было нечего (тоже успех);
  - строка `❌ Ошибка при загрузке конфигурации` или ненулевой код возврата — ошибка.
    Загрузка в «грязную» базу недопустима, поэтому оркестратор **возвращает задачу на
    этап `develop`** (как при падении тестов — цикл `cyclic-review-workflow`):
    разработчик читает этот лог и чинит исходники/метаданные. Лимит 10 итераций; при
    его исчерпании `develop` помечается `failed`.
