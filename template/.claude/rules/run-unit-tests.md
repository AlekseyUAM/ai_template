# Запуск юнит-тестов

## Где живут тесты (фреймворк проекта)

Юнит-тесты в проекте — это **общие модули внутри расширения `ЮнитТесты`**
(исходники в `src/cfe/ЮнитТесты`), а НЕ модули в основной конфигурации `src/cf`.
Расширение само прогоняет тесты в тестовой базе; его раннер (`ЮТ_Тестирование*`)
подключён к параметру запуска `ВыполнитьЗапускЮнитТестов`.

- Новый тест-модуль добавляй в `src/cfe/ЮнитТесты/CommonModules/` по образцу
  `ЮТ_ТестыПример`: экспортная `Сценарии()` возвращает массив имён тест-функций;
  каждая тест-функция экспортная и возвращает `Булево`.
- Отдельного раннера НЕ изобретай и в `src/cf` тест-модули НЕ клади — это нарушает
  и фреймворк, и типовое ограничение задач «не меняем лишние объекты».
- Загрузка перед прогоном — расширения, а не конфигурации:
  `python .claude/skills/1c-batch/scripts/1c-batch.py load-extension src/cfe/ЮнитТесты --name ЮнитТесты`.

Детали ролей — в `.claude/agents/developer-tests.md` (пишет тесты и конфиг запуска,
фаза Red) и навыке `task-orchestration` (оркестратор запускает прогон и выносит вердикт
в `TESTING.md` на этапе `testing`). Это авторитетный источник.

## Как запускать

Команда вида **«запусти тесты <конфиг>»** выполняется скриптом
`.claude/tools/run-tests.py`:

```bash
python .claude/tools/run-tests.py configs/task#<id>/test.json
```

Конфиг — **один на задачу**: `configs/task#<id>/test.json` (образец формата —
`configs/test_example.json`):

```json
{
    "ИмяМодуля": "<ИмяТестМодуля из TESTS.md>",
    "ИмяФайлаЛог": "<абсолютный путь>/logs/task#<id>/result.json"
}
```

`ИмяМодуля` — общий модуль расширения с `Сценарии()` (имя фиксирует `developer-tests`
в `TESTS.md`). `ИмяФайлаЛог` — абсолютный путь; каталог `logs/task#<id>` создай заранее.
(`configs/test.json` — лишь дефолт скрипта без аргумента; для задач используй
per-task конфиг.)

Для отладочного прогона части сценариев задай `--test` — имена коротких сценариев
из `Сценарии()` через запятую:

```bash
python .claude/tools/run-tests.py \
    configs/task#<id>/test.json --test СебестоимостьФИФО,ПроверкаСклада --timeout 90
```

Таймаут для отладочного прогона задаёт запускающий — короткий (60–120 c), чтобы быстро
локализовать зависание; полный прогон идёт с обычным таймаутом. Если отбор ничего не
нашёл, `result.json` содержит `Выполнено=false` с текстом ошибки.

Скрипт стартует базу (из `.1c-devbase.json`) в режиме предприятия через
`1c-batch run-enterprise --wait -C "ВыполнитьЗапускЮнитТестов=<абсолютный путь к конфигу>"`.
Относительный путь к конфигу приводится к абсолютному; если файл не найден —
запуск не делается, если пуст — выводится предупреждение. Кроссплатформенно; требует
Python 3.6+ и локальную копию `1c-batch`.

### Предварительная компиляция (обязательна)

Перед стартом предприятия скрипт компилирует модули пакетным конфигуратором
(`1c-batch check-modules --thin-client --server --extension ЮнитТесты`). Зачем: ошибка
компиляции в предприятии выводится **модальным окном**, из-за которого сеанс висит вечно,
а оркестратор ждёт завершения в фоне — задача встаёт. Конфигуратор же пишет ошибки в лог
и завершается кодом, без модальных окон. При ошибке компиляции предприятие **не
запускается** — скрипт возвращает `2` и печатает текст ошибки.

Параметры: `--extension ИМЯ` (расширение с тестами, по умолчанию `ЮнитТесты`),
`--no-check` (пропустить компиляцию — только для отладки).

`check-modules` вызывается с `-Extension ИМЯ`, поэтому проверяются модули **только
этого расширения** — основная конфигурация (`src/cf`) не проверяется. Ошибки в
основной конфигурации этот шаг не ловит.

### Таймаут сеанса

Предприятие запускается с таймаутом `--timeout СЕК` (по умолчанию `600`). По истечении
скрипт убивает **только своё** дерево процессов (сам сеанс и его `1cv8`); чужие сеансы 1С
(другие базы, конфигуратор пользователя) не трогаются. Возврат при таймауте — `124`.

При таймауте скрипт **дополнительно проверяет модули основной конфигурации**
(`check-modules` без `--extension`): сеанс мог зависнуть на модальном окне ошибки
компиляции модуля, загруженного в базу на этапе разработки и не входящего в расширение
с тестами. Если такая ошибка найдена, возвращается `2` (а не `124`), текст ошибки
печатается в лог. Если ошибок нет — остаётся `124`, причина таймаута другая.

### Коды возврата

| Код | Значение |
|-----|----------|
| `0` | штатное завершение |
| `1` | ошибка запуска (нет конфига, нет wrapper 1c-batch) |
| `2` | ошибка компиляции модулей (предприятие не запускалось; после таймаута — ошибка найдена в основной конфигурации) |
| `3` | ошибка среды/лицензии при проверке модулей |
| `124` | таймаут сеанса предприятия (ошибок компиляции основной конфигурации нет) |

## Результат

`Сообщить(...)` в пакетном режиме в stdout НЕ попадает — результаты пишет сам
раннер в файл `ИмяФайлаЛог` (JSON). Читай его. Тесты пройдены, **только если**:
`Выполнено = true`, `ОписаниеОшибки = null`, и у **каждого** теста `Результат = true`.
