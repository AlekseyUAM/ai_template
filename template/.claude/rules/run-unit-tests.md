# Запуск юнит-тестов

## Где живут тесты (фреймворк проекта)

Юнит-тесты в проекте — это **общие модули внутри расширения `ЮнитТесты`**
(исходники в `src/cfe/ЮнитТесты`), а НЕ модули в основной конфигурации `src/cf`.
Расширение само прогоняет тесты в тестовой базе; его раннер (`ЮТ_Тестирование*`)
подключён к параметру запуска `ВыполнитьЗапускЮнитТестов`.

- Новый тест-модуль добавляй в `src/cfe/ЮнитТесты/CommonModules/` по образцу
  `ЮТ_ТестыПример`: экспортная `Сценарии()` возвращает массив имён тест-функций;
  каждая тест-функция экспортная и возвращает `Булево`.
- Отдельного раннера НЕ изобретай и в `src/cf` тест-модули НЕ клади — это нарушает
  и фреймворк, и типовое ограничение задач «не меняем лишние объекты».
- Загрузка перед прогоном — расширения, а не конфигурации:
  `python .claude/skills/1c-batch/scripts/1c-batch.py load-extension src/cfe/ЮнитТесты --name ЮнитТесты`.

Детали ролей — в `.claude/agents/developer-tests.md` (пишет тесты и конфиг запуска,
сам выполняет красный смоук и отладочные прогоны) и навыке `task-orchestration`
(оркестратор проверяет доказательства смоука, запускает полный прогон этапа `testing`
и выносит вердикт в `TESTING.md`). Это авторитетный источник.

## Как запускать

Команда вида **«запусти тесты <конфиг>»** выполняется скриптом
`.claude/tools/run-tests.py`:

```bash
python .claude/tools/run-tests.py configs/task#<id>/test.json
```

**`run-tests.py` — исключение из правила «≤10 мин»: таймаут инструмента Bash
2 000 000 мс.** У скрипта три собственных бюджета по 600 c: проверка расширения,
проверка основной конфигурации и сеанс предприятия (итого до 1800 c); таймаут
2 000 000 мс оставляет запас, чтобы Bash не убил обёртку ровно на границе 3×600 c, —
иначе она не напечатает `rc 3` (среда/лицензия или таймаут проверки модулей), и
станет неясно, среда это или дефект кода. С таймаутом 600 000 мс обёртка гибнет ещё
раньше. Саму команду `run-tests.py` — с побочными эффектами (загрузки, процессы
1С) — запускай в Bash, а не под `Monitor`. В `claude -p` используй Bash с
таймаутом 2 000 000 мс; `run_in_background` запрещён. В интерактивной сессии
`Monitor` служит только для ожидания (скрипт в нём не запускай) — см.
`task-orchestration`.

Конфиг — **один на задачу**: `configs/task#<id>/test.json` (образец формата —
`configs/test_example.json`):

```json
{
    "ИмяМодуля": "<ИмяТестМодуля из TESTS.md>",
    "ИмяФайлаЛог": "<абсолютный путь>/logs/task#<id>/result.json"
}
```

`ИмяМодуля` — общий модуль расширения с `Сценарии()` (имя фиксирует `developer-tests`
в `TESTS.md`). `ИмяФайлаЛог` — абсолютный путь; каталог `logs/task#<id>` создай заранее.
(`configs/test.json` — лишь дефолт скрипта без аргумента; для задач используй
per-task конфиг.)

Для отладочного прогона части сценариев задай `--test` — имена коротких сценариев
из `Сценарии()` через запятую:

```bash
python .claude/tools/run-tests.py \
    configs/task#<id>/test.json --test СебестоимостьФИФО,ПроверкаСклада --timeout 90
```

Таймаут для отладочного прогона задаёт запускающий — короткий (60–120 c), чтобы быстро
локализовать зависание; полный прогон идёт с обычным таймаутом. Если отбор ничего не
нашёл, `result.json` содержит `Выполнено=false` с текстом ошибки.

На красном смоуке ожидаемый код возврата — `4` (прогон состоялся, все тесты красные;
зелёных до реализации быть не должно). `0` на смоуке означает, что тесты не проверяют
новое поведение.

Скрипт стартует базу (из `.1c-devbase.json`) в режиме предприятия через
`1c-batch run-enterprise --wait -C "ВыполнитьЗапускЮнитТестов=<абсолютный путь к конфигу>"`.
Относительный путь к конфигу приводится к абсолютному; если файл не найден —
запуск не делается, если пуст — выводится предупреждение. Кроссплатформенно; требует
Python 3.6+ и локальную копию `1c-batch`.

### Предварительная компиляция (обязательна)

Перед стартом предприятия скрипт компилирует модули пакетным конфигуратором в два
шага:

1. модули расширения с тестами —
   `1c-batch check-modules --thin-client --server --extension ЮнитТесты`;
2. модули **основной конфигурации** —
   `1c-batch check-modules --thin-client --server` (без `--extension`).

Зачем: ошибка компиляции в предприятии выводится **модальным окном**, из-за которого
сеанс висит вечно, а оркестратор синхронно ждёт завершения — задача встаёт без
таймаута. Ошибка в основной конфигурации (`src/cf`, модуль загружен на этапе
разработки) вела себя так же: её ловила только диагностика после 600-секундного
зависания предприятия. Теперь precheck основной конфигурации ловит её заранее.
Конфигуратор же пишет ошибки в лог и завершается кодом, без модальных окон. При
ошибке компиляции на любом шаге предприятие **не запускается** — скрипт возвращает
`2` и печатает текст ошибки.

Сама проверка модулей ограничена **600 c** на процесс: зависшая проверка (не
ответившая среда) убивается по дереву процессов, скрипт печатает «проверка модулей
не уложилась в 600 c — проблема среды, не компиляции» и возвращает `3`. Это не
ошибка компиляции — код править не нужно, проверяйте среду.

Параметры: `--extension ИМЯ` (расширение с тестами, по умолчанию `ЮнитТесты`),
`--no-check` (пропустить обе проверки — только для отладки),
`--no-check-main` (пропустить только проверку основной конфигурации; расширение
проверяется).

### Таймаут сеанса

Предприятие запускается с таймаутом `--timeout СЕК` (по умолчанию `600`). По истечении
скрипт убивает **только своё** дерево процессов (сам сеанс и его `1cv8`); чужие сеансы 1С
(другие базы, конфигуратор пользователя) не трогаются. Возврат при таймауте — `124`.

При таймауте скрипт **дополнительно проверяет модули основной конфигурации**
(`check-modules` без `--extension`): сеанс мог зависнуть на модальном окне ошибки
компиляции модуля, загруженного в базу на этапе разработки и не входящего в расширение
с тестами. Если такая ошибка найдена, возвращается `2` (а не `124`), текст ошибки
печатается в лог. Если сама проверка не уложилась в 600 c — возвращается `3`
(проблема среды, не кода). Если ошибок нет — остаётся `124`, причина таймаута другая.

Диагностика — тоже проверка модулей, и её ошибки среды не выдаются за таймаут
сеанса: если она не запустилась из-за среды/лицензии или не уложилась в 600 c,
скрипт возвращает `3` («проблема среды/лицензии, не код»), а не `124`. Код `124`
остаётся только за настоящим таймаутом сеанса, когда ошибки компиляции нет и
причины в среде диагностика не нашла.

### Коды возврата

| Код | Значение |
|-----|----------|
| `0` | все тесты пройдены, результат свежий |
| `1` | ошибка запуска (нет конфига, нет wrapper 1c-batch) |
| `2` | ошибка компиляции модулей расширения или основной конфигурации (предприятие не запускалось; после таймаута — ошибка найдена в основной конфигурации) |
| `3` | среда/лицензия или таймаут проверки модулей (600 c) — не ошибка компиляции; так же при диагностике после таймаута сеанса: среда/лицензия или таймаут самой диагностической проверки |
| `4` | прогон состоялся, но есть проваленные тесты / `Выполнено=false` / `ОписаниеОшибки≠null` |
| `5` | `result.json` не найден, невалиден или список тестов пуст |
| `124` | таймаут сеанса предприятия без ошибки компиляции и без проблемы среды в диагностике |

## Результат

`Сообщить(...)` в пакетном режиме в stdout НЕ попадает — результаты пишет сам
раннер в файл `ИмяФайлаЛог` (JSON). Старый файл перед прогоном удаляется, поэтому
после прогона любой существующий `result.json` — свежий. `run-tests.py` печатает
сводку (`Выполнено`, `ОписаниеОшибки`, `✓/✗` по тестам, `ИТОГ: N/M пройдено`) и
возвращает `0/4/5` (см. таблицу кодов). Тесты пройдены, **только если**:
`Выполнено = true`, `ОписаниеОшибки = null`, и у **каждого** теста `Результат = true`.
