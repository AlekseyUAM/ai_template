# Циклический workflow: develop → [testing] → review → develop

Для задач, где требуется итеративное улучшение кода на основе результатов тестирования и замечаний ревьюера.

## Включение циклического workflow

Циклический workflow **активируется автоматически**, если включены этапы:
- `testing: true` И/ИЛИ `review: true`, ИЛИ включён флаг `update_db: true`

При этом:
- Если `update_db` включён и загрузка в ИБ упала → цикл: develop → develop
- Если `testing` включен и не пройдён → цикл: develop → testing → develop
- Если `testing` включен и пройдён → цикл: develop → testing → review → develop
- Если `testing` отключен, но `review` включен → цикл: develop → review → develop

## Логика выполнения

### 0. Загрузка в ИБ после `develop` (если `update_db` включён)
```
После develop оркестратор грузит конфигурацию в ИБ (см. task-orchestration,
правило optimized-config-loading); лог — logs/task#<id>/load-config.log:
├─ Ошибка загрузки (в «грязную» базу грузить нельзя):
│  ├─ Перезагрузить develop в pending (task_status.py ... develop pending — 
│  │  автоматически инкрементирует iteration в task.json)
│  ├─ Если iteration ≥ 10: отметить develop как failed, остановиться
│  │  (разработчик читает load-config.log и чинит исходники/метаданные)
│  └─ Архивировать DEVELOP.md → DEVELOP.<n>.md, где <n> — прежнее значение iteration
└─ Успех:
   └─ Перейти к следующему включённому этапу (testing/review/docs)
```

### 1. Этап `testing` (если включен)
```
После завершения testing ищем в TESTING.md строку-ячейку вердикта ровно
«| Вердикт | ✓ ПРОЙДЕНО |» (не голый глиф ✓/✗):
├─ Если строки «| Вердикт | ✓ ПРОЙДЕНО |» НЕТ (тесты не пройдены —
│  строка «| Вердикт | ✗ НЕ ПРОЙДЕНО |»):
│  ├─ Вернуть по виновнику (строка «| Виновник | … |») — task_status.py 
│  │  автоматически инкрементирует iteration возвращаемого этапа в task.json:
│  │  ├─ «| Виновник | код |»  → task_status.py ... develop pending (чинит разработчик)
│  │  └─ «| Виновник | тест |» → task_status.py ... tests pending (чинит developer-tests;
│  │     develop не трогаем — код не менялся)
│  ├─ Архивировать артефакты (DEVELOP.md → DEVELOP.<n>.md, где <n> — прежнее iteration)
│  └─ Если iteration ≥ 10: отметить этап как failed, остановиться
└─ Если строка «| Вердикт | ✓ ПРОЙДЕНО |» есть (все тесты пройдены):
   └─ Перейти к review
```

### 2. Этап `review` (если включен)
```
После завершения review ищем в REVIEW.md строку-ячейку вердикта ровно
«| Вердикт | ✓ ПРИНЯТО |» (не голый глиф ✓/✗ — он встречается в чек-листе):
├─ Если строки «| Вердикт | ✓ ПРИНЯТО |» НЕТ (вердикт «на доработку» —
│  строка «| Вердикт | ✗ НА ДОРАБОТКУ |»):
│  ├─ Определить следующий этап: task_status.py инкрементирует iteration:
│  │  ├─ Если testing включен: task_status.py ... testing pending
│  │  └─ Если testing отключен: task_status.py ... develop pending
│  ├─ Архивировать артефакты (REVIEW.md → REVIEW.<n>.md, где <n> — прежнее iteration)
│  └─ Если iteration ≥ 10: отметить review как failed, остановиться
└─ Если строка «| Вердикт | ✓ ПРИНЯТО |» есть (одобрено):
   └─ Перейти к следующему включённому этапу (обычно `docs`)
```

> **Исполнитель цикла — оркестратор.** Отдельного инструмента для цикла нет:
> архивирование артефактов и возврат этапа в `pending` ведёт сам оркестратор обычными 
> файловыми операциями (см. навык `task-orchestration`, раздел «Циклический workflow»). 
> **Счётчик итераций ведёт `task_status.py` автоматически:** он инкрементирует поле 
> `iteration` этапа в `task.json` при переводе этапа в `running`.

## Управление итерациями этапа

Номер итерации хранится в поле `iteration` каждого этапа в `task.json`.
`task_status.py` инкрементирует его автоматически при переводе этапа в `running`:

```bash
# Пример: посмотреть текущую итерацию этапа develop
grep -A 20 '"name": "develop"' tasks/task#001/task.json | grep '"iteration"'

# Поле iteration содержит число итераций (0 = первый запуск)
# Максимум: 10 итераций
```

## Архивирование артефактов при циклах

Перед новой итерацией артефакты переименовываются для сохранения истории:

```bash
# Пример: если это итерация 2, то:
# TESTS.md → TESTS.1.md (старый, если возврат на tests — виновник тест)
# DEVELOP.md → DEVELOP.1.md (старый, если возврат на develop — виновник код)
# TESTING.md → TESTING.1.md (старый)
# REVIEW.md → REVIEW.1.md (старый)
#
# Новые артефакты будут созданы как TESTS.md / DEVELOP.md, TESTING.md, REVIEW.md
```

## Остановка цикла

Цикл останавливается:
- ✅ **Одобрения ревьюером** (строка «| Вердикт | ✓ ПРИНЯТО |» в REVIEW.md)
- ❌ **Достижения максимума итераций** (iteration ≥ 10 в task.json) → этап отмечается `failed`
- ❌ **Явной остановки** командой `python .claude/tools/task_status.py <task_dir> <stage> failed`

## Примечания

- Счётчик итераций начинается с 0 в поле `iteration` этапа в `task.json`
- `task_status.py` инкрементирует `iteration` при переводе этапа в `running`
- Максимум 10 итераций предотвращает бесконечные циклы
- Каждый раз при возврате в develop обновляется DEVELOP.md с указанием номера итерации
- История всех версий сохраняется через архивные файлы (DEVELOP.1.md, DEVELOP.2.md и т.д.)
- Разработчик видит номер итерации в артефактах
- Вердикт этапа `testing` (его выносит оркестратор) и ревьюер дают замечания в каждой итерации
