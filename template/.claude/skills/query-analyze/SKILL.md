# /query-analyze — автоматический анализ запросов 1С

Находит нарушения стандартов разработки оптимальных запросов (ИТС).
Работает в два шага: извлечение текста запроса из `.bsl`/СКД-XML и прогон
реестра автоматических проверок.

## Извлечение запросов

```bash
# Из .bsl-файла или каталога (рекурсивно)
python "${CLAUDE_SKILL_DIR}/scripts/extract_queries.py" -Path src/cf/Catalogs/Товары/Ext/ManagerModule.bsl
# Из макетов СКД (XML)
python "${CLAUDE_SKILL_DIR}/scripts/extract_queries.py" -Path src/cf/Reports -Xml
```

Выводит блоки `# <путь>:<строка>` с текстом запроса, разделённые `--- 8< ---`.

## Анализ запроса

```bash
# Текст запроса из файла
python "${CLAUDE_SKILL_DIR}/scripts/analyze_query.py" query.txt
# Или из stdin
python "${CLAUDE_SKILL_DIR}/scripts/extract_queries.py" -Path Module.bsl | python "${CLAUDE_SKILL_DIR}/scripts/analyze_query.py" -
```

Находки печатаются как `severity | код | строка N | сообщение`, где код — осмысленный
слаг правила (напр. `select-star`, `vt-filter-in-where`, `like-leading-wildcard`), а не
`std*`. Флаг `-Detailed` показывает и пройденные проверки. Код возврата ≠ 0 при находках
уровня `error`.

**Нумерация строк.** `строка N` в находке отсчитывается от начала **текста запроса**
(с 1), а не от строки в исходном `.bsl`/XML. Абсолютную позицию в файле даёт заголовок
блока `# <путь>:<строка>` из `extract_queries.py`: прибавь N к ней, чтобы перейти к месту
в исходнике.

## Шкала severity и вердикт

Единая шкала (как в `bsl_ls` / LSP): `error` = **критичная**, `warning` =
**важная**, `info` = **минорная**. **Любая находка `error`|`warning`
(критичная|важная) блокирует приёмку** — см. агент `reviewer`; `info` не блокирует.

Если структурные (AST) проверки пропущены из-за отсутствия `node`/бандла (см.
«Зависимости») — это **не** «проверки пройдены». Ревьюер трактует недоступность
анализатора как **критичную** находку (слой контроля не отработал) → «на доработку»,
пока окружение не починено.

## Зависимости

Структурные (AST) проверки требуют:
- `node` в PATH;
- вендоренного бандла `scripts/vendor/sdbl_parse.js` (пересборка: `scripts/vendor/build-parser.sh`).

Без них работают **только текстовые правила** (keyword-lowercase, query-one-line); все
структурные проверки **ПРОПУСКАЮТСЯ** (не считаются пройденными). Инструмент
выводит предупреждение в stderr в этом случае.

Это отличается от ситуации, когда парсер **отработал и сообщил синтаксическую
ошибку** (текст запроса не разбирается). Тогда это не пропуск слоя, а находка
`query-not-parseable` (severity `warning` → важная, блокирует приёмку): запрос
не откроется конструктором запросов и, как правило, некорректен.

## Классы ошибок, ловимых по AST-модели

Структурные проверки используют полный разбор запроса от SDBL-парсера
(`vendor/sdbl_parse.js`), а не регэкспы. Помимо нарушений стандартов оптимальных
запросов ловятся частые ошибки, из-за которых запрос не компилируется или молча
выдаёт неверный результат (типовые промахи кодогенерации):

- `alias-collides-with-field` (**важная**) — псевдоним источника совпал с именем
  поля другой таблицы (`… КАК Номенклатура` при наличии поля `Номенклатура`).
  Платформа выдаёт «Неоднозначное поле». Сверяет псевдонимы источников с `path`
  полей/условий/ключей соединений и их таблицей-владельцем.
- `order-after-totals` (**критичная**) — `УПОРЯДОЧИТЬ ПО` стоит после `ИТОГИ`
  (нарушен порядок секций). Платформа выдаёт синтаксическую ошибку. **Парсер к
  такому порядку лоялен** (разбирает без ошибки, молча теряя `УПОРЯДОЧИТЬ`),
  поэтому проверка текстовая, а не через `query-not-parseable`.
- `totals-field-not-aggregated` (**важная**) — в запросе с `ИТОГИ` поле не входит
  ни в группировку, ни в агрегат → на строках-итогах оно вернётся `NULL` (частая
  причина runtime-ошибки «Преобразование значения к типу Булево…»).
- `aggregate-without-isnull` (**важная**) — агрегат `СУММА/СРЕДНЕЕ/МАКСИМУМ/
  МИНИМУМ` без `СГРУППИРОВАТЬ ПО` и без `ЕСТЬNULL`: на пустом наборе вернёт
  `NULL`, а не 0 (сравнение `NULL = число` ложно — тихая логическая ошибка).
  `КОЛИЧЕСТВО(*)` не флагуется (на пустом наборе даёт 0).

## Чего анализатор НЕ проверяет

Автопроверки работают только по тексту запроса. Соответствие индексам БД,
семантике задачи и составу метаданных проверяется вручную — см. навык
`query-review`. В частности, существование полей и правильность суффиксов
ресурсов виртуальных таблиц (`СуммаОборот`, `СтоимостьРасход`, `…Остаток`)
зависит от состава метаданных регистра (вид, корреспонденция, субконто) и
проверяется в `query-review` через `code_index` (`get_object_structure`).
