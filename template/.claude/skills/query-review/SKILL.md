# /query-review — чеклист ручного ревью запросов 1С

Сюда вынесены требования стандартов оптимальных запросов, которые НЕ
проверяются скриптом `query-analyze` (нужны знание индексов БД, состава
метаданных или семантики задачи). Проверяй каждый пункт глазами.

Пункты сгруппированы по темам; каждый — требование и что проверить глазами. Коды находок навыка `query-analyze` (например `select-star`, `vt-filter-in-where`) соответствуют этим темам.

## Общие требования по разработке оптимальных запросов

- Минимизировать объём выборки — убедиться, что запрос выбирает ровно те данные, которые нужны задаче, без избыточных полей и строк.
- Минимизировать количество запросов к СУБД — проверить, нет ли многократных однотипных вызовов, которые можно объединить в один запрос или пакет.
- Не переносить всё в СУБД — оценить, не проще ли сложную обработку (сортировка, свёртка, вычисления) выполнить на стороне сервера 1С вместо усложнения запроса.
- Условные тексты запроса — рассмотреть, можно ли заменить один сложный универсальный запрос несколькими простыми, выбираемыми по предусловиям.
- Эффективный план выполнения — для сложных запросов проверить план выполнения (консоль запросов / ТЖ / средства СУБД), убедиться в отсутствии timeout warning оптимизатора.
- Вложенные подзапросы — проверить, не добавлены ли вложенные запросы исключительно ради читаемости; при наличии — убедиться, что они необходимы по задаче.
- Сложные условия соединений и ГДЕ — проверить, нет ли подзапросов и конструкций ВЫБОР в предложениях соединения и ГДЕ; при наличии — оценить, нельзя ли упростить.

## Псевдонимы источников данных в запросах

- Осмысленность псевдонима — проверить, что псевдоним источника понятно описывает его роль в данном запросе (например, «ОстаткиНаСкладах», а не «Таблица1» или «РегистрНакопления»).
- CamelCase-оформление — каждое слово в псевдониме начинается с прописной буквы, предлоги и местоимения из одной буквы — тоже прописными («ТоварыНаСкладах», а не «ТоварынаСкладах»).
- Имена классов метаданных в качестве псевдонима — убедиться, что псевдоним источника не совпадает с именем класса объектов метаданных («Справочник», «Документ», «РегистрНакопления» и т.д.), так как это не описывает роль источника в конкретном запросе.

## Упорядочивание результатов запроса

- Наличие УПОРЯДОЧИТЬ ПО при зависимости от порядка — если алгоритм зависит от порядка записей или результат показывается пользователю, убедиться что присутствует УПОРЯДОЧИТЬ ПО; при отсутствии — проверить, что код явно не зависит от порядка.
- NULL в полях сортировки — при наличии УПОРЯДОЧИТЬ ПО проверить: если поле сортировки получено через ЛЕВОЕ СОЕДИНЕНИЕ или иначе может быть NULL, обернуть его в ЕСТЬNULL() для предсказуемой сортировки на разных СУБД.
- Ссылочные типы в УПОРЯДОЧИТЬ ПО — при отображении результатов пользователю убедиться, что сортировка ведётся по полям примитивных типов; сортировку по ссылочным полям заменить на сортировку по их строковому представлению.
- Избыточное УПОРЯДОЧИТЬ ПО — если алгоритм не зависит от порядка и результат не показывается пользователю, УПОРЯДОЧИТЬ ПО должно отсутствовать (снижает нагрузку на СУБД).
- РАЗЛИЧНЫЕ + УПОРЯДОЧИТЬ ПО — при использовании РАЗЛИЧНЫЕ убедиться, что в УПОРЯДОЧИТЬ ПО используются только поля, включённые в секцию ВЫБРАТЬ (иначе неявное включение полей сортировки может нарушить РАЗЛИЧНЫЕ).

## Проверка на пустой результат выполнения запроса

- Проверка пустоты результата — если цель — лишь узнать, есть ли строки, использовать `РезультатЗапроса.Пустой()`, а не `Выбрать()` + `Следующий()`: вызов `Выбрать()` затратнее, чем `Пустой()`.
- Отсутствие избыточного Пустой() перед итерацией — если результат всё равно будет перебираться (`Выбрать()` + `Следующий()` или `Выгрузить()`), предварительный вызов `Пустой()` не нужен и должен отсутствовать.

## Использование ОБЪЕДИНИТЬ и ОБЪЕДИНИТЬ ВСЕ

- Необходимость удаления дублей — если query-analyze пометил ОБЪЕДИНИТЬ без ВСЕ, проверить: действительно ли нужно устранять дубли между объединяемыми выборками? Если нет — заменить на ОБЪЕДИНИТЬ ВСЕ. Если да — убедиться в наличии комментария, объясняющего необходимость дедупликации.

## Оператор ПОДОБНО

- Экранирование спецсимволов при пользовательском вводе — если значение шаблона приходит от пользователя (через параметр &Шаблон), убедиться, что специальные символы (%, _, [, ], ^, ~) экранируются перед передачей в запрос; рекомендуется использовать ОбщегоНазначения.СформироватьСтрокуДляПоискаВЗапросе (БСП) или аналог.
- Ключевое слово СПЕЦСИМВОЛ при наличии экранирования — если в запросе используется экранирование символов в шаблоне, убедиться, что конструкция дополнена ключевым словом СПЕЦСИМВОЛ с указанием выбранного символа экранирования.
- Длина шаблона не более 1024 символов — при использовании динамически вычисляемых шаблонов убедиться, что длина строки не превысит 1024 символа (ограничение MS SQL 2005).
- Параметрический шаблон с ведущим wildcard — если шаблон передаётся параметром (&Шаблон) и в коде видно, что к нему добавляется «%» спереди (например «"%" + ОбщегоНазначения.СформироватьСтрокуДляПоискаВЗапросе(...)»), осознанно оценить влияние на производительность: будет полный скан таблицы.

## Округление результатов арифметических операций в запросах

- Порядок операндов деления — если порядок числителя значительно меньше порядка знаменателя, переставить операнды: выполнять умножение перед делением (0.02 * 9287492 / 28346 вместо 0.02 / 28346 * 9287492), чтобы не терять точность на промежуточном результате.
- ВЫРАЗИТЬ на операндах деления — при использовании ВЫРАЗИТЬ на операндах проверить, что указанная разрядность минимально достаточна для представления значений (избыточное завышение снижает точность последующих вычислений и замедляет запрос).
- ВЫРАЗИТЬ на результате деления — если ВЫРАЗИТЬ применяется к результату деления, убедиться, что разрядность минимальна, но достаточна для представления значений результата; учитывать ограничение 31 разряд суммарно.
- Умножение дробных значений без ВЫРАЗИТЬ — если оба множителя могут иметь дробную часть, оценить необходимость обёртки ВЫРАЗИТЬ(... КАК Число(m,n)) для стабилизации точности на разных СУБД; query-analyze не детектирует этот случай автоматически.

## ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ

- Обоснованность ПОЛНОГО СОЕДИНЕНИЯ — если query-analyze пометил ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ, убедиться, что запрос не может быть переписан через ОБЪЕДИНИТЬ ВСЕ + группировку; при наличии объективных причин — добавить комментарий с обоснованием.
- Два и более ПОЛНЫХ СОЕДИНЕНИЯ в одном запросе — особо критичный случай для PostgreSQL; при наличии более одного ПОЛНОГО СОЕДИНЕНИЯ в одном операторе выполнить нагрузочный тест или предоставить обоснование.

## Ограничения на использование вложенных запросов в условии соединения

- Альтернатива через временную таблицу — если query-analyze пометил вложенный запрос в условии соединения, убедиться, что он переписан через временную таблицу (ПОМЕСТИТЬ): это стандартный способ избежать проблем с производительностью и совместимостью.
- Семантика «среза последних» через ПО — если вложенный подзапрос в условии соединения использовался для получения «среза последних» (МАКСИМУМ по периоду, дате и т.п. с условием на внешнее поле), проверить, что переработанный запрос через временную таблицу сохраняет корректную семантику отбора.

## Соединения с вложенными запросами и виртуальными таблицами

- Соединение с вложенным запросом — исключение «мало записей» — если query-analyze пометил соединение с подзапросом, убедиться, что оно не попадает под исключение («вложенный запрос сканирует мало записей»); если попадает, добавить комментарий с обоснованием; иначе — переписать через временную таблицу.
- Соединение с виртуальной таблицей при неудовлетворительной производительности — если запрос соединяется с виртуальной таблицей (РегистрНакопления.*.Остатки, РегистрСведений.*.СрезПоследних и т.п.) и при этом работает медленно, вынести обращение к виртуальной таблице в отдельный запрос с сохранением результатов во временной таблице.
- Вложенные соединения (неявные подзапросы) — проверить, нет ли в запросе конструкции «ЛЕВОЕ СОЕДИНЕНИЕ А ЛЕВОЕ СОЕДИНЕНИЕ Б ПО... ПО...» (второй ПО относится к первому СОЕДИНЕНИЮ, создавая неявный подзапрос); при наличии заменить на последовательные соединения или временную таблицу.

## Разыменование ссылочных полей составного типа в языке запросов

- Разыменование составного поля через точку — найти все вхождения «Таблица.Поле.Реквизит» в запросе; для каждого из них выяснить (по метаданным конфигурации), является ли «Поле» составным типом. Если да — это неявное соединение со ВСЕМИ таблицами, входящими в составной тип, что может дать десятки левых соединений. Критично при наличии RLS.
- Использование ВЫРАЗИТЬ при разыменовании составного поля — если разыменование составного поля необходимо, убедиться, что применяется ВЫРАЗИТЬ(Поле КАК КонкретныйТип).Реквизит в сочетании с КОГДА... ССЫЛКА... ТОГДА. Прямое «Таблица.СоставноеПоле.Реквизит» без ВЫРАЗИТЬ — нарушение стандарта.
- Избыточные типы в составном поле — если по метаданным поле объявлено как составной тип с несколькими вариантами, проверить: включены ли в тип только реально используемые ссылочные типы (не «любая ссылка», не «ссылка на любой документ»)? Избыточные типы следует убрать через редактирование метаданных.
- Денормализация как альтернатива — если поле составного типа используется в запросе только ради получения одного реквизита (например, «Регистратор.Дата»), рассмотреть вынос этого реквизита в исходную таблицу (дополнительный реквизит «ДатаРегистратора»): это устраняет неявное соединение целиком.

## Эффективные условия запросов

- Индексированность полей основного условия — убедиться, что поля, используемые в условиях ГДЕ, ПО и виртуальных таблицах, проиндексированы в соответствующей таблице метаданных. Автоматически не проверяется — нужны знание метаданных.
- ИЛИ по разным полям в условии ГДЕ — если query-analyze не пометил, проверить: не содержит ли условие «Поле1 = А ИЛИ Поле2 = В» по разным полям без охватывающего индексного условия? Такой паттерн не приводится к «В» и препятствует использованию одного индекса; рекомендуется переписать через ОБЪЕДИНИТЬ ВСЕ.
- Арифметика над полем как единственное/основное условие — проверить, нет ли конструкции вида «Таблица.Поле - 1 > 0» без предшествующего индексного условия; арифметика над полем блокирует использование индекса. При наличии — переместить в дополнительное условие или ввести вычисляемое индексированное поле.
- Несколько ролей с разным RLS для одного права — проверить дизайн ролей: назначение пользователю двух и более ролей с разным RLS на один объект метаданных приводит к появлению ИЛИ в запросах СУБД даже при отсутствии ИЛИ в тексте запроса, что делает условие неиндексным.

## Несоответствие индексов и условий запроса

> Справочник индексов (какие индексы платформа создаёт для таблиц БД автоматически): см. [reference/indexes-db-tables.md](reference/indexes-db-tables.md).

- Условие ГДЕ покрыто подходящим индексом — для каждого условия в секции ГДЕ убедиться, что в таблице существует индекс, содержащий все поля условия в самом начале, подряд без «пробелов».
- Условие соединения ПО покрыто индексом — для каждого условия в секции соединения ПО убедиться в наличии подходящего индекса по используемым полям.
- Параметры виртуальной таблицы покрыты индексом — для виртуальных таблиц (Остатки, СрезПоследних и т.п.) убедиться, что передаваемые в условие параметры соответствуют полям в начале основного индекса таблицы.
- Отсутствие «пробела» в индексе — если в условии задействованы поля из середины индекса, но не задано поле, стоящее перед ними в индексе — индекс используется лишь частично; проверить необходимость перестановки измерений или дополнительного индексирования.
- Необходимость создания нового индекса — если ни один из существующих индексов не покрывает условие, рассмотреть индексирование реквизита/измерения (с дополнительным упорядочиванием для справочников и документов); избегать создания индексов «на всякий случай» и по низкоселективным полям.

## Дополнительные индексы

- Применимость дополнительных индексов — убедиться, что конфигурация рассчитана на КОРП-лицензии платформы; если целевая аудитория — только ПРОФ-лицензии, дополнительные индексы использовать нельзя.
- Производительность без дополнительных индексов — убедиться, что запрос работает с приемлемой скоростью при отключённых дополнительных индексах на типичном объёме до 100 000–1 000 000 записей; тестировать оба режима: с включёнными и с отключёнными индексами.
- Достижимость результата без дополнительных индексов — если приемлемую производительность можно обеспечить обычным индексированием реквизита (свойство «Индексировать»), использовать его вместо дополнительного индекса.
- Включаемые поля (не ключевые) — если поле в запросе используется только в секции ВЫБРАТЬ, а не в условии ГДЕ/ПО, добавлять его в дополнительный индекс как включаемое (неиндексируемое), а не как ключевое; это высвобождает место под дополнительные ключевые поля.

## Обращения к виртуальным таблицам

- Простота условий виртуальной таблицы — убедиться, что условия, передаваемые в параметры виртуальной таблицы, являются простыми конструкциями вида «Измерение = Значение»; подзапросы и неявные соединения через точку (Ссылка.Реквизит) в параметрах ВТ допустимы только при выполнении всех ограничений–2.2 (один подзапрос, без соединений, без обращений к шапке через точку из табличной части, без условий во временных таблицах).
- Подзапрос в параметрах ВТ — если в условии виртуальной таблицы используется подзапрос, убедиться: в нём только одна таблица, нет явных и неявных соединений (в том числе через точку от ссылки), нет обращений к реквизитам шапки из табличной части; для временной таблицы — нет секции ГДЕ.
- Несколько подзапросов в параметрах ВТ — если требуется несколько условий с подзапросами, выбрать одно наиболее селективное (отфильтровывающее максимум записей); остальные условия перенести во внешний запрос или предварительно материализовать через временные таблицы.

## Эффективное обращение к ВТ Остатки

- Дата в параметрах ВТ Остатки — если query-analyze пометил ВТ Остатки с периодом, убедиться: действительно ли нужны исторические остатки на конкретную дату? Если цель — текущие остатки, убрать дату (оставить первый параметр пустым): платформа будет читать только хранимую таблицу текущих остатков без группировки.
- Использование ВТ Остатки вместо ОстаткиИОбороты — если нужны только остатки (без оборотов), убедиться, что запрос обращается именно к «Остатки», а не к «ОстаткиИОбороты»: ОстаткиИОбороты всегда читает таблицу движений, что медленнее.
- Все измерения ВТ Остатки использованы во внешнем запросе — для самого эффективного плана без разделения итогов: проверить по метаданным регистра, что все его измерения либо присутствуют в секции ВЫБРАТЬ внешнего запроса, либо участвуют в условиях соединения; пропущенные измерения вынуждают СУБД добавить группировку в вложенный запрос.
- Режим разделения итогов — если регистр накопления или бухгалтерии работает в режиме разделения итогов, помнить: даже при соблюдении прочих условий (нет даты, все измерения используются) платформа будет читать и таблицу движений; оценить, оправдан ли этот режим с учётом снижения параллельности записи и производительности чтения.

## Использование временных таблиц

- Объём данных в ВТ — убедиться, что временная таблица не содержит сотни тысяч записей: такой объём существенно снижает производительность при записи и может исчерпать место на диске; при больших данных переходить на пакетную обработку порциями.
- Минимальный набор данных в ВТ — убедиться, что во временную таблицу помещаются только те данные, которые реально нужны последующим запросам; лишние строки и поля — лишняя нагрузка на запись и место.
- ВТ не создаётся в цикле — проверить BSL-код: временная таблица не должна создаваться (ПОМЕСТИТЬ) и удаляться (УНИЧТОЖИТЬ) в цикле, если можно создать её однажды до цикла.
- ВТ не копируется ради переименования — убедиться, что вместо копирования ВТ в другую ВТ только с целью переименования передаётся имя таблицы параметром.
- Индексирование при JOIN — если query-analyze пометил ВТ без ИНДЕКСИРОВАТЬ ПО, участвующую в соединении, убедиться в реальной необходимости индекса: для маленьких ВТ (менее 1000 записей) индекс не нужен; если ВТ велика — добавить ИНДЕКСИРОВАТЬ ПО по полям условия соединения (ПО).
- Индексирование при В (...) — если query-analyze пометил ВТ без ИНДЕКСИРОВАТЬ ПО, используемую в В (...), убедиться: для маленьких ВТ индекс не нужен; если ВТ велика — добавить ИНДЕКСИРОВАТЬ ПО по полям из списка выбора подзапроса В (...).
- Несколько условий использования ВТ — если временная таблица используется одновременно в нескольких соединениях/условиях В, и только одно из них проверяется часто, строить индекс только для наиболее часто проверяемого условия.

## Вычисление количества записей в запросах

- Количество записей через КОЛИЧЕСТВО, а не СУММА — если query-analyze пометил СУММА(1) или ЕСТЬNULL(СУММА(1), 0), заменить на КОЛИЧЕСТВО(*) или КОЛИЧЕСТВО(<Поле>): использование СУММА(1) ведёт к переполнению при ≥10 млн. записей из-за разрядности числа по умолчанию (7 знаков).
- Разрядность ВЫРАЗИТЬ при условном подсчёте — если query-analyze пометил СУММА(ВЫБОР...ТОГДА 1...) без ВЫРАЗИТЬ, убедиться, что литерал 1 обёрнут в ВЫРАЗИТЬ(1 КАК ЧИСЛО(17, 0)): при ≥10 млн. условных записей переполнение неизбежно без явного расширения разрядности.
- Подсчёт записей в коде 1С (BSL) вместо запроса — проверить, не получает ли код все записи из СУБД (Выбрать() + Следующий() или Выгрузить() +.Количество()) с целью лишь посчитать их число; такой паттерн нельзя обнаружить в тексте запроса — проверяется только анализом окружающего BSL-кода.

## Многократное выполнение однотипных запросов

- Запрос не выполняется в цикле — проверить BSL-код вокруг запроса: если вызов «Запрос.Выполнить()» или «МенеджерВременныхТаблиц» находится внутри цикла (Для каждого / Пока / Цикл), убедиться, что это один из допустимых исключений — порционная обработка, виртуальные таблицы с датой среза, заметное усложнение одного запроса.
- Набор объектов — условие В вместо серии запросов — если запрос фильтрует по одному объекту (параметр &Объект = Ссылка), а вызов повторяется в цикле по списку, переписать на условие «В (&СписокОбъектов)» и передать весь список одним параметром.
- ОБЪЕДИНИТЬ ВСЕ для разнотипных объектов — если однотипные данные запрашиваются из разных таблиц поочерёдно, объединить операторы в один пакет или через ОБЪЕДИНИТЬ ВСЕ.
- БСП: функции для работы со списками — при использовании БСП проверить, что вместо ЗначениеРеквизитаОбъекта / КонтактнаяИнформацияОбъекта в цикле вызываются их «списочные» варианты (ЗначениеРеквизитаОбъектов / КонтактнаяИнформацияОбъектов).
- Допустимые исключения обоснованы — если серия запросов в цикле оставлена намеренно, убедиться, что в коде присутствует комментарий с обоснованием (одно из исключений п.2: деградация производительности при ВТ с датой среза, порционная обработка в обработчике обновления / групповом проведении / загрузке данных).

## Разрешение итогов для периодических регистров сведений

- Условия включения итогов — если запрос обращается к СрезПоследних/СрезПервых периодического регистра сведений без указания даты (первый параметр ВТ пустой), проверить по метаданным все четыре условия из п.1: (1) в регистре ожидается большой объём данных; (2) запросы к срезу на текущий момент выполняются часто; (3) условия в параметрах ВТ задаются только на значения измерений и допустимых разделителей; (4) RLS регистра использует только измерения и допустимые разделители. Если все четыре условия выполнены — рассмотреть включение «Разрешить итоги: срез последних/первых».
- Условия отключения итогов — если запросы к срезу всегда (или чаще всего) выполняются на конкретную дату (первый параметр ВТ не пустой) или условия в параметрах ВТ содержат подзапросы/обращения через точку к реквизитам связанных таблиц — включение итогов не даст ускорения; убедиться, что итоги не включены.
- Альтернативный вариант запроса — если итоги не применяются из-за явной даты в параметрах ВТ, рассмотреть, можно ли разделить запрос на два пути: один — без даты (использует итоги), другой — с датой (обычный запрос); выбор пути выполняется предварительной проверкой наличия записей с будущей датой.
- Пересчёт итогов не требуется — убедиться, что в конфигурации нет отдельного механизма принудительного пересчёта итогов; актуализация выполняется платформой автоматически при записи набора записей. Исключение: если где-то в коде вызывается РегистрСведенийМенеджер.УстановитьИспользованиеИтогов(Ложь) — убедиться, что это сделано обоснованно и итоги впоследствии включаются обратно.

## Оформление текстов запросов

- Псевдонимы полей (КАК) — убедиться, что все поля выборки (особенно реквизиты вида «Объект.Реквизит.Вложенный») имеют явный псевдоним через КАК, и что перед псевдонимом стоит именно ключевое слово КАК.
- Комментарии к сложным запросам — в запросах с вложенными подзапросами, объединениями или несколькими соединениями должны быть комментарии, объясняющие назначение каждой таблицы или секции.
- Комментарий к объекту Запрос — при создании объекта Запрос в коде рядом должен быть комментарий с описанием цели запроса.
- Программная сборка запроса — если текст запроса собирается динамически, проверить: используются ли параметры/СтрЗаменить вместо конкатенации фрагментов; может ли каждая часть быть открыта в конструкторе запросов.

## Запросы в динамических списках

- Простота запроса динамического списка — оценить, можно ли упростить архитектуру: вынести рассчитываемые состояния/агрегаты в отдельный регистр сведений с фоновым расчётом, чтобы запрос стал простым чтением одной таблицы.
- Режим динамического считывания — убедиться, что для динамического списка выбран подходящий режим: при большом объёме данных — режим «динамическое считывание включено» с назначенной основной таблицей; режим «основная таблица не задана» использовать только для заведомо малых выборок.
- РАЗЛИЧНЫЕ и СГРУППИРОВАТЬ ПО — убедиться, что в запросе динамического списка отсутствуют конструкции РАЗЛИЧНЫЕ и СГРУППИРОВАТЬ ПО: они существенно «утяжеляют» запрос и замедляют работу списка.
- ВЫБОР в условиях соединения и ГДЕ — убедиться, что конструкция ВЫБОР не используется в предложении ГДЕ или в условиях соединения ПО: это отдельно запрещено для динамических списков.
- Упорядочивание по вычисляемому ВЫБОР — убедиться, что сортировка УПОРЯДОЧИТЬ ПО не ведётся по полю, полученному через конструкцию ВЫБОР, включая пользовательское упорядочивание; это недопустимо для динамических списков.
- Количество соединяемых таблиц — убедиться, что запрос динамического списка соединяется с минимальным числом реальных таблиц; оптимально — одна таблица, назначенная основной; ориентир максимум — 4 таблицы; при большем числе рассмотреть денормализацию данных.
- Соединение с виртуальными таблицами — убедиться, что соединения с виртуальными таблицами допустимы только в строго ограниченных случаях: СрезПоследних/СрезПервых с заведомо малым объёмом, ВТ Остатки без даты (хранимые итоги), ВТ Остатки с полным набором измерений для работы без группировки.
- Временные таблицы — если в динамическом списке используются временные таблицы, убедиться, что их объём заведомо мал: ВТ не кешируются и заполняются заново при каждом считывании порции данных.
- Основная таблица динамического списка — убедиться, что в свойствах динамического списка на форме назначена основная таблица: это необходимо для корректного динамического считывания и для применения ограничений RLS.
- Поля составного типа — убедиться, что в соединениях, отборах и упорядочивании поля составного типа содержат только ссылочные типы; при известном заранее конкретном типе — применять ВЫРАЗИТЬ(Поле КАК КонкретныйТип).
- Индексирование полей — проверить индексирование полей, по которым выполняются соединения, условия, быстрые отборы, упорядочивание и группировка; следует также предусмотреть индексы для полей, по которым пользователь часто упорядочивает список.
- Проверка под неполными правами (RLS) — проверить скорость работы динамического списка именно в режиме с настроенными ограничениями доступа к данным (RLS): условия RLS автоматически добавляются к запросам и могут существенно замедлить список.
- Вспомогательные колонки через ПриПолученииДанныхНаСервере — если в динамическом списке нужны вспомогательные колонки, по которым не требуется отбор/сортировка/группировка, рассмотреть вынос их в обработчик ПриПолученииДанныхНаСервере; все данные для таких колонок следует выбирать одним запросом сразу для всех передаваемых строк.
