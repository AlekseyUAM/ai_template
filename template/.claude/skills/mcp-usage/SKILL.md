# Использование MCP-серверов 1С

Пять серверов, каждый закрывает свой класс задач. Общий принцип: **не читай сырой XML/код руками и не угадывай** — спроси тот сервер, который держит нужный факт в индексе или в справочнике.

| Нужно | Сервер | Старт |
|-------|--------|-------|
| Найти, где и как что-то реализовано в конфигурации | `code_index` | `search_terms` |
| Структура/состав/связи объекта метаданных | `code_index` | `get_object_profile` / `get_object_structure` |
| Справка по API платформы (типы, методы, свойства, конструкторы) | `1c_platform` | `search` → `info` |
| Статический анализ BSL (ошибки, стандарты) | `bsl_ls` | `check` |
| Сложный/неоднозначный вопрос, ревью логики/производительности | `1c_naparnic` | `ask_1c_ai` |

**Золотые правила:**
1. Перед написанием нового кода/объекта — ищи существующее через `code_index` (`search_terms`, `get_object_structure`). Дублирование — повод остановиться.
2. После правок BSL — прогоняй `bsl_ls check` и чини найденное до чистоты.
3. Не угадывай синтаксис платформы — `1c_platform`.
4. `code_index` требует параметр `repo` (алиас репозитория) почти в каждом инструменте. В проекте он всегда один — **передавай `repo="src"`**. Вызывать `get_stats` ради алиаса не нужно.

## `code_index` — поиск и навигация по кодовой базе

Индекс BSL + метаданных + графов вызовов/данных. Самый богатый сервер; для него — подробный разбор.

### 0. Обязательная преамбула
- Алиас репозитория всегда `src` — **передавай `repo="src"`** во все инструменты, где он требуется. Вызывать `get_stats` ради алиаса не нужно.
- `get_stats` (без параметров) — статистика индекса / список подключённых репо. Полезен для контроля размера индекса, не как обязательная преамбула.
- `health` — живость сервера и демона индексации, если результаты кажутся пустыми/устаревшими.

### 1. Поиск «где реализован функционал X» (главный вход)
- **`search_terms`** — ПЕРВЫЙ выбор для BSL. Ищет процедуры по *смыслу*, а не по точному написанию: имя процедуры (CamelCase разбивается: `УточнитьДанныеПоШтрихкоду` → `уточнить данные по штрихкоду`), имя+синоним объекта-владельца, комментарий над процедурой. Спрашивай 1–3 корня слов: `штрихкод`, `резерв склад`, `расчет цен`. Словоформы/подстроки от 3 символов, регистр и ё/е не важны. Возвращает `proc_key = '<путь>::<имя>'` — тело берёшь потом через `get_function`.
- **`search_function`** / **`search_class`** — нечёткий FTS по словам (bm25), выдача без тел (локации/сигнатуры). Для функций любого языка; на BSL часто уступает `search_terms`.
- **`search_text`** — FTS по текстовым файлам (md/txt/yaml/toml).

### 2. Точное имя известно → навигация и тела
- **`find_symbol`** (имя точное) — ГДЕ определён символ, без тел. Для распространённых имён (стандартные обработчики) обязательно задавай `path_glob`, иначе сотни локаций.
- **`get_function`** / **`get_class`** — ТЕЛО по точному имени (с исходником). Поддерживают массовый режим через `names: [...]`. Неуникальное имя → тела опускаются, вернутся локации + подсказка сузить `path_glob`.
- **`get_file_summary`** — оглавление файла без тел (сигнатуры, диапазоны строк, импорты). Безопасно на больших модулях.
- **`read_file`** (`repo`+`path`, опц. `line_start`/`line_end`) — содержимое файла из индекса (и text, и code через zstd). `stat_file` — метаданные файла (размер, строки, язык). `list_files` (`pattern`/`path_prefix`/`language`) — список файлов.

### 3. Regex-поиск по коду
- **`grep_code`** — regex по ВСЕМУ тексту code-файлов (module-level + тела: объявления `Перем`, таблицы маршрутизации, литералы, комментарии). Надмножество `grep_body`. Желателен `path_glob` ИЛИ `language` (full-scan дорогой).
- **`grep_body`** — только тела функций/классов, но показывает, в какой ИМЕННО функции найдено. Бери, когда важно «в какой процедуре».
- **`grep_text`** — regex по текстовым файлам.
- Параметр паттерна: `regex` (синоним `query`); у `grep_body` есть ещё `pattern` (LIKE-подстрока). `context_lines` — строки вокруг.

### 4. Метаданные объекта (структура/формы/модули/связи)
- **`get_object_profile`** — ПОЛНЫЙ паспорт объекта за ОДИН вызов: `structure` + `forms` (с обработчиками) + `modules` (с UUID) + `data_links`. Имя singular: `Document.РеализацияТоваровУслуг`. `sections=['structure']` — сузить и удешевить. Заменяет серию из трёх вызовов ниже.
- **`get_object_structure`** — только структура: реквизиты/ТЧ/измерения/ресурсы, `enum_values`, `predefined`, `owners`, `properties` (периодичность, проведение), `commands`. `name_like` + `meta_type` — структуры ВСЕХ объектов темы одним вызовом. **Это единственный источник структуры: XML объектов НЕ индексируется как текст — не ищи его через `grep_text`/`list_files`.**
- **`get_form_handlers`** (`owner_full_name` + `form_name`) — пары событие→обработчик формы.

### 5. Графы связей (impact-анализ, «что сломается»)
- **`find_references`** — «карта влияния» объекта одним вызовом: `data_refs` (структурные ссылки) + `code_usages` (обращения в .bsl) + `role_rights` (какие роли дают права). Главный инструмент перед изменением объекта.
- **`get_data_links`** (`direction` out/in/both, `depth` ≤4) — ссылочные связи по реквизитам/измерениям.
- **`find_data_path`** (`from`→`to`) — есть ли путь по ссылкам между объектами.
- **`get_register_writers`** — регистраторы регистра / движения документа (из декларативного состава, точнее разбора кода проведения). Работает в обе стороны.
- **`get_event_subscriptions`** (фильтры `event`/`source`/`handler_module`) — подписки на события; `event` принимает рус/англ.

### 6. Графы вызовов BSL
- **`get_callers`** / **`get_callees`** (`function_name`) — кто вызывает / что вызывает.
- **`get_call_tree`** (`root`, `direction` callees/callers, `max_depth`≤10) — дерево вызовов.
- **`find_path_bsl`** (`from`→`to`, ключи `<rel_path>::<name>`) — путь в BSL-графе с `call_type`. Универсальный аналог — `find_path`.

### 7. Длинный хвост — `bsl_sql`
Произвольный **read-only** SQL (SELECT/WITH) по таблицам индекса, когда named-tool нет: фильтры, join'ы, агрегации. Колонку `repo` фильтровать НЕ нужно (в каждой БД она `'default'`). Ключевые таблицы: `metadata_objects`, `metadata_modules`, `metadata_forms`, `event_subscriptions`, `proc_call_graph`, `data_links`, `role_rights`, `metadata_code_usages`. Запись/PRAGMA отклоняются.

## `1c_platform` — справочник API платформы

Для синтаксиса, сигнатур и доступных членов типов. **Не угадывай — спрашивай здесь.**

- **`search`** (`query`, `type` method/property/type/null, `limit`) — поиск по API конкретными терминами 1С. Точка входа, когда точное имя неизвестно.
- **`info`** (`name`, `type` method/property/type) — детальная карточка элемента по точному имени.
- **`getMembers`** (`typeName`) — ПОЛНЫЙ список методов и свойств типа (`СправочникСсылка`, `Запрос`, `ТаблицаЗначений`).
- **`getMember`** (`typeName`, `memberName`) — один метод/свойство типа.
- **`getConstructors`** (`typeName`) — способы создания объекта типа.

Маршрут: не знаешь имя → `search`; знаешь тип, нужен весь API → `getMembers`; знаешь элемент → `info`/`getMember`; создаёшь объект → `getConstructors`.

## `bsl_ls` — статический анализ BSL

- **`check`** (`code` — текст модуля; опц. `config`, `filename`). Возвращает ошибки/предупреждения по стандартам.
- **Перед вызовом прочитай `.bsl-language-server.json` в корне проекта и передай его в `config`** (строкой-JSON или объектом), чтобы проверки шли по правилам проекта. Если файла нет — не передавай `config` (пойдут правила по умолчанию).
- Прогоняй после каждого изменения BSL и доводи до чистоты перед следующим шагом.

## `1c_naparnic` — ИИ-ассистент по 1С

Для неоднозначных/концептуальных вопросов и экспертной проверки, когда детерминированные серверы не дают ответа. **Отправляет запрос/код во внешний ИИ** — применяй осознанно, не шли конфиденциальное без необходимости.

- **`ask_1c_ai`** (`question`, опц. `programming_language`, `create_new_session`) — свободный вопрос по 1С.
- **`explain_1c_syntax`** (`syntax_element`, опц. `context`) — объяснение конструкции языка.

Проверку кода делай через `bsl_ls` (стандарты/синтаксис); `1c_naparnic` оставь для концептуальных и неоднозначных вопросов. `check_1c_code` не использовать.

## Рецепты под частые задачи

- **«Где реализовано X?»** → `search_terms "X"` (с `repo="src"`) → `get_function(proc_key)`.
- **«Изучить объект перед доработкой»** → `get_object_profile('Document.X')`; для списка объектов темы → `get_object_structure(name_like='…')`.
- **«Что сломается, если изменю объект?»** → `find_references('Catalog.X')` (+ `get_register_writers` для документов/регистров).
- **«Кто дёргает эту процедуру?»** → `get_callers` / `get_call_tree(direction=callers)`.
- **«Не изобретаю ли велосипед?»** (search-before-write) → `search_terms` + `get_object_structure(name_like=…)` (или `bsl_sql` по `metadata_objects`).
- **«Как правильно вызвать метод платформы?»** → `1c_platform search` → `info`/`getMembers`.
- **«Проверить написанный код»** → `bsl_ls check` (с `config` из проекта); концептуальные сомнения — `1c_naparnic ask_1c_ai`.
