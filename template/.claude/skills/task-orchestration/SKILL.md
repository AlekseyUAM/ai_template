# Оркестрация задачи

## Источник
`tasks/task#<id>/task.json` — список этапов с полями `name`, `enabled`, `subagent`,
`artifact`, `status`, `changed_files`.

## Ветка задачи
Отдельную ветку git под задачу не создавай: в проекте одновременно выполняется
только одна задача, все изменения идут в текущей ветке проекта.

## Git-жизненный цикл задачи (ведёт оркестратор)
Коммитит **только оркестратор** — это операция жизненного цикла задачи, а не роли.
Субагенты (включая ревьюера, он `readonly`) `git commit`/`git add` не делают.
Модель — «один коммит = одна принятая задача» на текущей ветке проекта; веток под
задачу нет. Модель исходит из того, что **задачи не пересекаются во времени**: новая
начинается только после того, как предыдущая принята (и закоммичена) или брошена.
Параллельного ведения двух задач эта модель не поддерживает — для него понадобились
бы ветки под задачу.

1. **Старт задачи — baseline-коммит.** Перед первым этапом зафиксируй всё, что есть в
   рабочем дереве, одним baseline-коммитом: `git add -A`, затем `git commit` (если
   коммитить нечего — пропусти). Делаем это **безусловно и без вопросов к
   пользователю** Поскольку задачи не пересекаются, любые незакоммиченные правки
   на старте — это не половина параллельной задачи, их безопасно свернуть в baseline.
   Это условие корректности ревью: ревьюер определяет пул изменений через голый
   `git diff` (рабочее дерево vs. индекс), и без чистого baseline посторонние правки
   попали бы в `git diff` и `task.diff` и были бы ошибочно приписаны задаче.
2. **Во время задачи — коммитов НЕ делаем.** На всех этапах и во всех итерациях цикла
   `develop → testing → review` рабочее дерево накапливает правки задачи без коммитов.
   Так каждую итерацию `git diff` ревьюера = накопленные изменения задачи относительно
   baseline — ровно то, что нужно проверить. Никто не выполняет `git add`: ревьюер
   завязан на незастейдженные правки (`git diff` без `--cached`), после `git add` он
   увидит пустой дифф и пропустит изменения.
3. **Финал — один коммит после приёмки.** Только после вердикта `✓ ПРИНЯТО` в
   `REVIEW.md` (и завершения `docs`, если включён) оркестратор делает один коммит со
   всеми изменениями задачи. Сохранённый ревьюером `task.diff` совпадёт с этим
   коммитом. Дерево снова чистое → baseline для следующей задачи готов.

## Порядок этапов
analyze → plan → tests → develop → testing → review → docs.
Выполняй только этапы с `enabled: true`, в указанном порядке.

## Для каждого этапа
1. **Прочитай определение агента этапа** `.claude/agents/<subagent>.md` ПЕРЕД
   делегированием (например, для этапа `tests` — `.claude/agents/developer-tests.md`).
   Это единственный авторитетный источник проектных конвенций роли: где и как
   оформлять артефакты кода (тесты — в расширении `ЮнитТесты`, а не в `src/cf`),
   каким фреймворком/шаблоном пользоваться, какие пути конфигов/логов, какие навыки
   обязательны. Оркестратор обязан знать эти конвенции, иначе навяжет субагенту
   неверный способ.
2. `task_status.py ... <этап> running`.
3. Делегируй субагенту этапа (`subagent`): передай **цель, план, ограничения,
   артефакты предыдущих этапов и всегда `TASK.md`** — то есть ЧТО сделать и в каких
   рамках. НЕ переписывай КАК это делать: способ (где лежат файлы, какой фреймворк,
   какие команды) задан в определении агента — не навязывай встречный рецепт и не
   выдавай «импровизируй, если чего-то нет». Если твои указания противоречат
   определению агента — это баг оркестрации: субагент пойдёт за твоим более
   конкретным промптом и нарушит конвенцию. При делегировании передавай ТОЛЬКО
   реально существующие артефакты предыдущих этапов. Не требуй отсутствующих файлов,
   если соответствующие этапы не были включены.
4. Убедись, что субагент записал `<artifact>` (например `ANALYZE.md`) в каталог
   задачи, И что артефакты кода легли туда, куда предписывает определение агента
   (например, тест-модули — в `src/cfe/ЮнитТесты`, а не в основную конфигурацию).
5. `task_status.py ... <этап> done --files <изменённые>` (или `failed` при ошибке).

**Этап `testing` — исключение:** у него нет субагента (поле `subagent` пустое),
делегировать некому. Этот этап оркестратор ведёт сам — прогоняет тесты и выносит
вердикт (см. «Этап testing»).

## Долгие фоновые операции без расхода токенов
Загрузка конфигурации в ИБ и прогон тестов — долгие операции. Их ведёт **оркестратор**
(главный цикл), а не субагент: субагент не умеет «проснуться» по завершении фонового
процесса и просто жёг бы токены в ожидании. Правило для оркестратора:
- запускай операцию **в фоне** с перенаправлением всего вывода в лог-файл в каталоге
  `logs/task#<id>/`;
- **не опрашивай** процесс в цикле — харнесс сам разбудит оркестратора по завершении
  процесса;
- проснувшись, прочитай лог/результат из `logs/task#<id>/` и прими решение.

## Загрузка в базу после этапа `develop` (флаг `update_db`)
Если в `task.json` поле `update_db` истинно (`1` / `true` / `"да"` / `"yes"`), то
**после** успешного завершения этапа `develop` (код написан, метаданные валидны,
статический анализ чист) загрузку конфигурации в ИБ и обновление БД выполняет
**оркестратор** — не разработчик. Способ — только частичная загрузка изменённых
файлов (правило `optimized-config-loading`), в фоне, с логом:
```bash
python .claude/tools/load-config-optimized.py > logs/task#<id>/load-config.log 2>&1
```
Проснувшись по завершении, проанализируй `logs/task#<id>/load-config.log` (см. правило
`optimized-config-loading`):
- **Успех** — зафиксируй итог и переходи к следующему включённому этапу.
- **Ошибка загрузки/обновления** — загрузка в «грязную» базу недопустима, поэтому
  **верни задачу на `develop`** так же, как при падении тестов (цикл
  `cyclic-review-workflow`): инкрементируй `.iteration_count`, заархивируй `DEVELOP.md`
  (→ `DEVELOP.<n>.md`), переведи `develop` в `pending` и запусти его заново. Разработчик
  прочитает `logs/task#<id>/load-config.log`, починит исходники/метаданные. При
  `.iteration_count ≥ 10` пометь `develop` как `failed` и остановись.

Если `update_db` выключен — шаг пропусти.

## Этап testing (ведёт оркестратор)
Если этап `testing` включён, его ведёт **оркестратор** сам (субагента `tester` нет).
Тесты написал разработчик тестов (`developer-tests`) и зафиксировал имя тест-модуля и
путь к конфигу запуска `configs/task#<id>/test.json` в `TESTS.md`. Порядок:
1. `task_status.py ... testing running`.
2. Создай каталог `logs/task#<id>` (если ещё нет).
3. Загрузи расширение `ЮнитТесты` (с тест-модулями) в тестовую базу — в фоне, с логом:
   ```bash
   python .claude/skills/1c-batch/scripts/1c-batch.py load-extension src/cfe/ЮнитТесты --name ЮнитТесты > logs/task#<id>/load-extension.log 2>&1
   ```
4. Прогони тесты по конфигу из `TESTS.md` (правило `run-unit-tests`) — в фоне, с логом;
   сам результат раннер пишет в `ИмяФайлаЛог` из конфига (`logs/task#<id>/result.json`):
   ```bash
   python .claude/tools/run-tests.py configs/task#<id>/test.json > logs/task#<id>/run-tests.log 2>&1
   ```
   Запуск — долгая фоновая операция: не опрашивай процесс в цикле, дождись пробуждения
   по его завершении (см. «Долгие фоновые операции без расхода токенов»).
5. Проснувшись, прочитай `logs/task#<id>/result.json`. Тесты пройдены, **только если**:
   `Выполнено` = `true`, `ОписаниеОшибки` = `null`, и у **каждого** теста
   `Результат` = `true`. Разбор падений — по полям теста и `ЗаписиЖР` (отладочные записи
   журнала регистрации из тестов).
6. Запиши вердикт в `TESTING.md` (формат ниже) и `task_status.py ... testing done`.
7. По вердикту веди цикл (правило `cyclic-review-workflow`): `✗ НЕ ПРОЙДЕНО` — верни
   задачу на `develop` (разработчик разберёт лог `logs/task#<id>/result.json` и починит
   код); `✓ ПРОЙДЕНО` — переходи к следующему включённому этапу.

### Вердикт в TESTING.md
Первой секцией `TESTING.md`, сразу после заголовка `#`, помести секцию `## Вердикт` и в
ней таблицу ровно такого вида — строку-ячейку вердикта пиши **дословно** (ровно одно из
двух значений; пробелы вокруг `|`, регистр и глиф `✓`/`✗` не меняй):

```
## Вердикт

| Параметр | Значение |
| --- | --- |
| Вердикт | ✓ ПРОЙДЕНО |
| Тестов всего | <N> |
| Провалено | 0 |
```

Тесты не пройдены — та же таблица, но строка `| Вердикт | ✗ НЕ ПРОЙДЕНО |` и ненулевое
число проваленных. Строка `| Вердикт | … |` должна встречаться в файле **ровно один
раз**. `✓ ПРОЙДЕНО` допустимо тогда и только тогда, когда проваленных = 0,
`Выполнено` = `true` и `ОписаниеОшибки` = `null`.

## Статусы
`pending → running → done | failed`. Отключённый этап — `skipped`, его пропускаем.
В циклическом workflow (правило `cyclic-review-workflow`) допустим обратный переход
`done → pending`: при возврате этапа на доработку оркестратор переводит его в
`pending` командой `task_status.py ... <этап> pending` и запускает заново.

## Циклический workflow develop ↔ testing/review (оркестратор ведёт его сам)
Если включены `testing` и/или `review`, задача идёт итерациями по правилу
`cyclic-review-workflow`. Оркестратор — единственный исполнитель этого цикла (внешнего
инструмента нет), поэтому обязан:
1. После `testing` прочитать вердикт из `TESTING.md`, после `review` — из `REVIEW.md`
   (ищи строку-ячейку `| Вердикт | … |` дословно).
2. При вердикте «✗ НЕ ПРОЙДЕНО» / «✗ НА ДОРАБОТКУ» — **не продолжать** к следующему
   этапу: инкрементировать счётчик `.iteration_count` в каталоге задачи (создать со
   значением `0`, если файла нет), заархивировать артефакты итерации
   (`DEVELOP.md`→`DEVELOP.<n>.md` и т.п.) и вернуть нужный этап в `pending`.
3. Лимит — 10 итераций: при `.iteration_count ≥ 10` пометить этап `failed` и
   остановиться. Чтение/запись `.iteration_count` и архивирование выполняет сам
   оркестратор (обычными файловыми операциями) — это не делает `task_status.py`.
4. При вердикте «✓ ПРОЙДЕНО» / «✓ ПРИНЯТО» — перейти к следующему включённому этапу.

## Гейты (поля `gate` / `approved`)
Гейт — это обязательная пауза на подтверждение пользователя после этапа, у которого
`gate: true`. Единственный критерий — поле `gate`; никакие другие флаги на это не
влияют.

Порядок:
1. Заверши этап с `gate: true` (`... <этап> done`).
2. ОСТАНОВИСЬ и покажи пользователю результат/артефакт этапа, запроси подтверждение.
3. После подтверждения отметь гейт:
   `python .claude/tools/task_status.py tasks/task#<id> <этап> approve`.
4. Только теперь переходи к следующему этапу.

Это подкреплено кодом: `task_status.py` ОТКАЖЕТСЯ перевести следующий этап в
`running`, пока у предыдущего включённого этапа `gate: true` и `approved: false`
(вернёт ошибку «гейт не пройден»). Статус `approve` выставляет `approved: true`,
не меняя `status` этапа.
