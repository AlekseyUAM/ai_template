# Оркестрация задачи

## Источник
`tasks/task#<id>/task.json` — список этапов с полями `name`, `enabled`, `subagent`,
`artifact`, `status`, `changed_files`.

## Ветка задачи
Отдельную ветку git под задачу не создавай: в проекте одновременно выполняется
только одна задача, все изменения идут в текущей ветке проекта.

## Git-жизненный цикл задачи (ведёт оркестратор)
Коммитит **только оркестратор** — это операция жизненного цикла задачи, а не роли.
Субагенты (включая ревьюера, он `readonly`) `git commit`/`git add` не делают.
Модель — «один коммит = одна принятая задача» на текущей ветке проекта; веток под
задачу нет. Модель исходит из того, что **задачи не пересекаются во времени**: новая
начинается только после того, как предыдущая принята (и закоммичена) или брошена.
Параллельного ведения двух задач эта модель не поддерживает — для него понадобились
бы ветки под задачу.

1. **Старт задачи — baseline-коммит.** Перед первым этапом зафиксируй всё, что есть в
   рабочем дереве, одним baseline-коммитом: `git add -A`, затем `git commit` (если
   коммитить нечего — пропусти). Делаем это **безусловно и без вопросов к
   пользователю** Поскольку задачи не пересекаются, любые незакоммиченные правки
   на старте — это не половина параллельной задачи, их безопасно свернуть в baseline.
   Это условие корректности ревью: ревьюер определяет пул изменений через голый
   `git diff` (рабочее дерево vs. индекс), и без чистого baseline посторонние правки
   попали бы в `git diff` и `task.diff` и были бы ошибочно приписаны задаче.
2. **Во время задачи — коммитов НЕ делаем.** На всех этапах и во всех итерациях цикла
   `develop → testing → review` рабочее дерево накапливает правки задачи без коммитов.
   Так каждую итерацию `git diff` ревьюера = накопленные изменения задачи относительно
   baseline — ровно то, что нужно проверить. Никто не выполняет `git add`: ревьюер
   завязан на незастейдженные правки (`git diff` без `--cached`), после `git add` он
   увидит пустой дифф и пропустит изменения.
3. **Финал — один коммит после приёмки.** Только после вердикта `✓ ПРИНЯТО` в
   `REVIEW.md` (и завершения `docs`, если включён) оркестратор делает один коммит со
   всеми изменениями задачи. Сохранённый ревьюером `task.diff` совпадёт с этим
   коммитом. Дерево снова чистое → baseline для следующей задачи готов.

## Порядок этапов
analyze → plan → tests → develop → testing → review → docs.
Выполняй только этапы с `enabled: true`, в указанном порядке.

## Для каждого этапа
1. **Прочитай определение агента этапа** `.claude/agents/<subagent>.md` ПЕРЕД
   делегированием (например, для этапа `tests` — `.claude/agents/developer-tests.md`).
   Это единственный авторитетный источник проектных конвенций роли: где и как
   оформлять артефакты кода (тесты — в расширении `ЮнитТесты`, а не в `src/cf`),
   каким фреймворком/шаблоном пользоваться, какие пути конфигов/логов, какие навыки
   обязательны. Оркестратор обязан знать эти конвенции, иначе навяжет субагенту
   неверный способ.
   
   **Перед каждым этапом учитывай** `USER_FEEDBACK.md` (правило `user-feedback`) — замечания
   пользователя из Telegram (если файл присутствует в каталоге задачи).
2. `task_status.py ... <этап> running`.
3. Делегируй субагенту этапа (`subagent`): передай **цель, план, ограничения,
   артефакты предыдущих этапов и всегда `TASK.md`** — то есть ЧТО сделать и в каких
   рамках. НЕ переписывай КАК это делать: способ (где лежат файлы, какой фреймворк,
   какие команды) задан в определении агента — не навязывай встречный рецепт и не
   выдавай «импровизируй, если чего-то нет». Если твои указания противоречат
   определению агента — это баг оркестрации: субагент пойдёт за твоим более
   конкретным промптом и нарушит конвенцию. При делегировании передавай ТОЛЬКО
   реально существующие артефакты предыдущих этапов. Не требуй отсутствующих файлов,
   если соответствующие этапы не были включены.
4. Убедись, что субагент записал `<artifact>` (например `ANALYZE.md`) в каталог
   задачи, И что артефакты кода легли туда, куда предписывает определение агента
   (например, тест-модули — в `src/cfe/ЮнитТесты`, а не в основную конфигурацию).
5. `task_status.py ... <этап> done --files <изменённые>` (или `failed` при ошибке).
   **Исключение — `develop` при `update_db: true`:** этот этап закрывается `done`
   только после успешной загрузки в ИБ (см. «Загрузка в базу после этапа
   `develop`»). До неё этап остаётся `running`; `task_status.py` откажется
   закрыть его без завершённой загрузки.
   **Исключение — `tests`:** этап закрывается `done` только после подтверждения
   доказательств красного смоука (см. «Красный смоук после этапа `tests`»).

**Этап `testing` — исключение:** у него нет субагента (поле `subagent` пустое),
делегировать некому. Этот этап оркестратор ведёт сам — прогоняет тесты и выносит
вердикт (см. «Этап testing»).

## Долгие операции: синхронный запуск с таймаутом
Загрузка конфигурации в ИБ и полный прогон тестов на этапе `testing` — долгие операции.
Их ведёт **оркестратор** (главный цикл), а не субагент. Смоук и отладочные прогоны
выполняет `developer-tests` синхронно в своём ходе; параллельно с этапом `testing`
тесты не запускаются. Правило для оркестратора:
- запускай операцию **синхронно** обычным вызовом Bash (без `run_in_background`) с
  перенаправлением всего вывода в лог-файл в каталоге `logs/task#<id>/` и явным
  `timeout` инструмента Bash — до 600000 мс (10 мин). Пока команда выполняется,
  токены не расходуются;
- **не используй `run_in_background` для этих операций.** В неинтерактивном режиме
  `claude -p` (AgentMon, benchmark) ход завершается (`end_turn`), и харнесс убивает
  фоновый процесс: «пробуждения» по завершении не будет, операция потеряется;
- после возврата команды прочитай лог и код возврата из `logs/task#<id>/` и прими
  решение;
- если операция не укладывается в 10 мин, уменьши объём (частичная загрузка
  `load-config-optimized.py` уже это делает) или разбей её на несколько синхронных
  вызовов; фоновый режим не используй.
- **`run-tests.py` — исключение из правила «≤10 мин»: таймаут Bash 2 000 000 мс.**
  У скрипта свои бюджеты: проверка расширения — до 600 c, проверка основной
  конфигурации — ещё до 600 c, сеанс предприятия — до 600 c (итого до 1800 c).
  Таймаут 2 000 000 мс оставляет запас, чтобы Bash не убивал обёртку ровно на границе
  3×600 c: иначе она не успеет напечатать `rc 3` (среда/лицензия/таймаут проверки
  модулей), и будет неясно, среда это или дефект кода. При `timeout` 600 000 мс
  обёртка гибнет ещё раньше. Смотри лог после возврата команды; `Monitor` — только
  для ожидания, не для запуска (см. ниже).

## Процессы 1С и ожидание
- **Не убивай процессы по широкой подстроке.** `pkill -f "1cv8 ENTERPRISE"` матчит
  собственную командную строку, убивает свой shell (`Exit code 144`) и может задеть
  чужие сеансы.
- Linux/macOS: `pkill -f '[1]cv8'` (скобки исключают сам шаблон из совпадений) или
  `pgrep -f '[1]cv8'` + точечный `kill <pid>`.
- Windows: `Get-Process`/`Stop-Process -Id` (PowerShell) или `taskkill /PID <pid>`;
  не `taskkill /IM 1cv8.exe` — убьёт все сеансы.
- Предпочитай `run-tests.py`/`1c-batch`: они убивают только своё дерево процессов по таймауту.
- `sleep` заблокирован хуком. Жди через `Monitor` — во всех режимах, не опросом в
  цикле. `run_in_background` — только в интерактивной сессии; в `claude -p` никогда
  (фон убивается при `end_turn`, см. выше).
- Не диагностируй зависание среды дольше **одного цикла** «reload расширения + повтор».
  Не помогло — остановись и сообщи о проблеме среды, не повторяй эксперименты.

## Красный смоук после этапа `tests` (выполняет developer-tests; оркестратор проверяет)
Смоук — часть завершения этапа `tests`, до `develop`. Он ловит ошибки компиляции
тест-модуля, ошибки setup и зелёные тесты до реализации. Загрузку расширения и прогон
выполняет автор тестов (`developer-tests`) — у него есть Bash и `run-tests.py --test`
для локальной итерации. Оркестратор проверяет доказательства.

1. После того как автор тестов записал `TESTS.md` (с секцией «Смоук») и
   `configs/task#<id>/test.json`, **не закрывай этап `tests`** — он остаётся `running`.
2. Проверь доказательства смоука:
   - `TESTS.md` содержит секцию «Смоук» с общим числом сценариев;
   - `logs/task#<id>/run-tests-smoke.log` и `result.json` (`ИмяФайлаЛог` из конфига)
     существуют, и их mtime позже mtime тест-модуля `src/cfe/ЮнитТесты`;
   - `logs/task#<id>/load-extension-tests.log` заканчивается `LOAD_EXIT=0`, и его mtime
     не старше mtime тест-модуля; `EXIT=load-failed` в `run-tests-smoke.log` —
     доказательство недействительно.
   - в логе `EXIT=4` (прогон состоялся, тесты красные — на смоуке это норма), нет
     `EXIT=2`; в `result.json` `Выполнено = true`, `ОписаниеОшибки = null`, число
     тестов равно числу сценариев из секции «Смоук», у каждого теста `Результат = false`.
3. Если доказательства отсутствуют/противоречивы — один контрольный синхронный прогон
   (см. «Долгие операции: синхронный запуск с таймаутом»):
   ```bash
   python .claude/skills/1c-batch/scripts/1c-batch.py load-extension \
       src/cfe/ЮнитТесты --name ЮнитТесты \
       > logs/task#<id>/load-extension-tests.log 2>&1
   load_rc=$?; echo "LOAD_EXIT=$load_rc" >> logs/task#<id>/load-extension-tests.log
   if [ "$load_rc" -eq 0 ]; then
       python .claude/tools/run-tests.py configs/task#<id>/test.json --timeout 300 \
           > logs/task#<id>/run-tests-smoke.log 2>&1
       rc=$?; echo "EXIT=$rc" >> logs/task#<id>/run-tests-smoke.log
   else
       echo "EXIT=load-failed" >> logs/task#<id>/run-tests-smoke.log
   fi
   ```
   `LOAD_EXIT≠0` или `EXIT=load-failed` — загрузка расширения не удалась, прогон
   тестов не выполнялся; такой контрольный прогон смоук не подтверждает.
   Не подтвердился — вернуть `tests` в `pending` с логом.
4. Критерии корректного красного (те же, что у автора тестов): нет ошибок
   компиляции/setup; ни один тест не зелёный; красные падают по утверждению или по
   ожидаемому отсутствию функциональности; проверяемый вызов не обёрнут в `Попытка`.
5. Смоук подтверждён — `task_status.py ... tests done --files <изменённые>`, дальше
   `develop`.

Особые случаи:
- ошибка компиляции в `ЮнитТесты` — дефект теста: верни `tests` в `pending`, автор
  чинит и повторяет смоук сам;
- ошибка компиляции в `src/cf` — дефект baseline, тест-модуль не виноват: зафиксируй
  лог, закрой `tests` и передай лог разработчику на `develop`; после `develop` смоук
  повторится в рамках `testing`;
- зелёный тест до реализации — дефект теста: верни `tests` в `pending`.

> Возврат `tests` из `review` также завершается красным смоуком автором тестов до
> `tests done`, независимо от того, включён ли `testing`.

## Загрузка в базу после этапа `develop` (флаг `update_db`)
Если в `task.json` поле `update_db` истинно (`1` / `true` / `"да"` / `"yes"`),
загрузку конфигурации в ИБ и обновление БД выполняет **оркестратор** — не
разработчик.

Загрузка — **часть завершения этапа `develop`**: пока она не завершилась успехом,
`develop` нельзя помечать `done` (иначе падение загрузки маскируется статусом
«готово», в том числе в мониторе). Это стережёт `task_status.py`: при `update_db`
он не даст поставить `develop done` без завершённой загрузки.

Порядок:
1. Разработчик закончил. Проверь только:
   - `DEVELOP.md` существует;
   - перечисленные в нём изменённые файлы совпадают с `git status --short`.
   Не перечитывай код, не перезапускай `bsl_ls`/`code-analyze`/`meta-validate` и не
   изучай дифф: это зона `developer` и `reviewer`. Расхождение списка файлов — возврат
   на `develop`. Этап `develop` — по-прежнему `running`.
2. Отметь начало загрузки:
   ```bash
   python .claude/tools/task_status.py tasks/task#<id> db-update start
   ```
3. Запусти частичную загрузку изменённых файлов (правило
   `optimized-config-loading`) **синхронно** (Bash `timeout=600000`) с логом:
   ```bash
   python .claude/tools/load-config-optimized.py --state logs/task#<id>/load-state.json > logs/task#<id>/load-config.log 2>&1
   ```
4. После возврата команды проверь код возврата и лог:
   - **Успех** (код `0` и строка `✅ Оптимизированная загрузка завершена` или
     `✅ Нет изменённых файлов конфигурации — загрузка не требуется`):
     1. Если в `DEVELOP.md` есть отложенные проверки `validate_query` по запросам к
        новым объектам — прогони их сейчас через MCP `1c-md` по литералам ровно в том
        виде, как они записаны в исходнике. `valid:false` по причине, отличной от
        «Таблица не найдена», — дефект: `db-update done`/`develop done` не вызывай,
        верни `develop` в `pending` по циклу `cyclic-review-workflow` и передай
        разработчику сообщение валидатора. Если MCP `1c-md` не подключён — зафиксируй
        в `DEVELOP.md`, что проверка недоступна; не выдавай её за выполненную.
     2. Проверки пройдены (или отложенных не было) — закрой загрузку и этап:
        ```bash
        python .claude/tools/task_status.py tasks/task#<id> db-update done
        python .claude/tools/task_status.py tasks/task#<id> develop done --files <изменённые>
        ```
        только теперь переходи к следующему включённому этапу;
   - **Ошибка** (`❌ Ошибка при загрузке конфигурации` или ненулевой код возврата):
     `db-update done` и `develop done` **не вызывай**. Загрузка в «грязную» базу
     недопустима → верни задачу на `develop` так же, как при падении тестов (цикл
     `cyclic-review-workflow`): заархивируй `DEVELOP.md` (→ `DEVELOP.<n>.md`),
     переведи `develop` в `pending` и запусти заново. Разработчик прочитает
     `logs/task#<id>/load-config.log` и починит исходники/метаданные. При
     достижении лимита (`iteration ≥ 10`) пометь `develop` как `failed` и остановись.

Если `update_db` выключен — шаг пропусти и ставь `develop done` как обычно.

## Этап testing (ведёт оркестратор)
Если этап `testing` включён, его ведёт **оркестратор** сам (субагента `tester` нет).
Тесты написал разработчик тестов (`developer-tests`) и зафиксировал имя тест-модуля и
путь к конфигу запуска `configs/task#<id>/test.json` в `TESTS.md`. Порядок:
1. `task_status.py ... testing running`.
2. Создай каталог `logs/task#<id>` (если ещё нет).
3. Загрузи расширение `ЮнитТесты` (с тест-модулями) в тестовую базу — **синхронно**
   (Bash `timeout=600000`), с логом:
   ```bash
   python .claude/skills/1c-batch/scripts/1c-batch.py load-extension src/cfe/ЮнитТесты --name ЮнитТесты > logs/task#<id>/load-extension.log 2>&1
   ```
4. Прогони тесты по конфигу из `TESTS.md` (правило `run-unit-tests`) — **синхронно**
   (Bash `timeout=2000000` — исключение из правила «≤10 мин», см. «Долгие операции»),
   с логом; сам результат раннер пишет в `ИмяФайлаЛог` из
   конфига (`logs/task#<id>/result.json`):
   ```bash
   python .claude/tools/run-tests.py configs/task#<id>/test.json > logs/task#<id>/run-tests.log 2>&1
   ```
   Запуск — долгая операция: дождись возврата команды, затем читай лог
   (см. «Долгие операции: синхронный запуск с таймаутом»).

   **Запускай предприятие только через `run-tests.py`** — не вызывай `1cv8 ENTERPRISE`
   (или `1c-batch run-enterprise`) напрямую в обход скрипта. Скрипт сначала компилирует
   конфигуратором модули расширения с тестами и модули основной конфигурации (ошибка
   компиляции иначе всплывёт модальным окном и подвесит сеанс навсегда), не дольше
   600 c на проверку, и запускает сеанс с таймаутом. Прямой запуск без таймаута — как раз
   то, что уже подвешивало задачу; это запрещено, в том числе для диагностики падения.

   Код возврата `run-tests.py` (в `run-tests.log` и как exit-код процесса) различай до
   чтения `result.json`:
   - **`2` — ошибка компиляции** (текст ошибки в логе). Может возникнуть **до
     запуска предприятия** — на предпроверке модулей расширения или основной
     конфигурации, — либо после таймаута, если последующая проверка модулей
     основной конфигурации нашла ошибку компиляции. Виновник — код или тест,
     по тому, в каком модуле ошибка компиляции: ошибка в тест-модуле расширения
     `ЮнитТесты` → виновник **тест**; ошибка в модуле конфигурации `src/cf` → виновник
     **код**. `result.json` при этом нет — вердикт выноси по логу.
   - **`3` — среда/лицензия или таймаут проверки модулей** (проверка модулей не
     уложилась в 600 c, дерево процессов убито; возможен и при предпроверке, и при
     диагностике после таймаута сеанса — в том числе если диагностика вообще не
     запустилась из-за среды/лицензии). Это **не ошибка компиляции** —
     код не править: проверь `platform_path`, лицензию и доступ к базе. Если среда в
     порядке, допускается один повтор прогона; не помогло — остановись и сообщи о
     проблеме среды.
   - **`124` — таймаут сеанса** (сеанс не завершился за `--timeout`, скрипт убил своё
     дерево процессов, не нашёл ошибок компиляции основной конфигурации и проблемы
     среды при диагностике). Разберись
     по `run-tests.log` и `result.json` (если успел появиться): тест зациклился/ждёт
     ввода — виновник **тест**; код уходит в вечный цикл/блокировку — виновник **код**.
     Не перезапускай вслепую.
   - **`4` — тесты выполнены, но есть проваленные** (сводка `run-tests.py` и
     `result.json` актуальны). Читай `result.json` по шагу 5.
   - **`5` — файла результата нет/он невалиден**: прогон не дошёл до записи. Не
     перезапускай вслепую; проверь лог и `ИмяФайлаЛог` в конфиге.
5. Проснувшись, прочитай `logs/task#<id>/result.json` и сводку `ИТОГ:` из
   `run-tests.log`. Тесты пройдены, **только если**: `Выполнено` = `true`,
   `ОписаниеОшибки` = `null`, и у **каждого** теста `Результат` = `true`. Причину
   падения ищи в `ОписаниеОшибки` теста; при необходимости — в журнале регистрации ИБ.
6. При падении **определи виновника** — код или сам тест. Сверь, что утверждает
   упавший тест, с критериями приёмки (`ANALYZE.md` / `TASK.md`) и фактическим
   результатом:
   - **код** — тест утверждает корректное (по критериям приёмки) поведение, но код даёт
     неверный результат;
   - **тест** — сам тест дефектный: ожидаемое значение/настройка данных не соответствуют
     критериям приёмки, тест неидемпотентен или не удаляет артефакты прошлого прогона,
     либо проверяет не то. (Не списывай реальный баг кода на тест.)
7. Запиши вердикт в `TESTING.md` (формат ниже) — при падении укажи и виновника — затем
   `task_status.py ... testing done`.
8. По вердикту веди цикл (правило `cyclic-review-workflow`); `✓ ПРОЙДЕНО` — переходи к
   следующему включённому этапу. При `✗ НЕ ПРОЙДЕНО` верни задачу на доработку по
   виновнику (см. правило `cyclic-review-workflow`, где описана автоматическая итерация этапов):
   - **виновник код** → верни `develop` в `pending` (архивируй `DEVELOP.md`); разработчик
     разберёт `logs/task#<id>/result.json` и починит код;
   - **виновник тест** → верни `tests` в `pending` (архивируй `TESTS.md`); разработчик
     тестов (`developer-tests`) починит тест-модуль. `develop` не трогай — код не менялся.
   `DEVELOP.md`/`TESTS.md` архивируй сам, а `TESTING.md`/`REVIEW.md` вручную не
   трогай: `task_status.py` переименует их сам при переводе `develop`/`tests` в
   `pending` (см. «Циклический workflow»).
     После правки теста автор тестов сам повторяет красный смоук и обновляет
     `TESTS.md`; оркестратор проверяет доказательства, затем `testing`.

### Вердикт в TESTING.md
Первой секцией `TESTING.md`, сразу после заголовка `#`, помести секцию `## Вердикт` и в
ней таблицу ровно такого вида — строку-ячейку вердикта пиши **дословно** (ровно одно из
двух значений; пробелы вокруг `|`, регистр и глиф `✓`/`✗` не меняй):

```
## Вердикт

| Параметр | Значение |
| --- | --- |
| Вердикт | ✓ ПРОЙДЕНО |
| Тестов всего | <N> |
| Провалено | 0 |
```

Тесты не пройдены — та же таблица, но строка `| Вердикт | ✗ НЕ ПРОЙДЕНО |`, ненулевое
число проваленных и дополнительная строка с виновником — ровно одно из двух:
`| Виновник | код |` или `| Виновник | тест |` (определяет, на какой этап вернуть
задачу — см. шаг 8). Строка `| Вердикт | … |` должна встречаться в файле **ровно один
раз**. `✓ ПРОЙДЕНО` допустимо тогда и только тогда, когда проваленных = 0,
`Выполнено` = `true` и `ОписаниеОшибки` = `null` (тогда строку `| Виновник | … |` не
пишем).

## Продолжение субагента (SendMessage)
Если субагент этапа уже запускался, возврат на **тот же этап** (`tests` из
смоука/`testing`, `develop` из `testing`/`review`) выполняй продолжением агента через
SendMessage, а не новым запуском. Это сохраняет контекст правок и не заставляет агента
заново читать большие артефакты.

1. После запуска субагента сохрани его идентификатор в
   `logs/task#<id>/agents.json` (если инструмент его вернул):
   ```json
   {
     "tests": {"agent_id": "<id>", "iteration": 1},
     "develop": {"agent_id": "<id>", "iteration": 1}
   }
   ```
   Если идентификатор не вернулся — запиши `null`.
2. Перед возвратом прочитай `agents.json` и продолжи агента через SendMessage с коротким
   re-brief:
   > Ты продолжаешь этап `<этап>` (итерация `<n>`). Перед правкой прочитай текущие
   > `<артефакт>` (путь), `TESTING.md`/`REVIEW.md` (путь) и лог (путь). Вердикт:
   > `<вердикт>`. Если в `DEVELOP.md` есть waiver-таблица — передай её ревьюеру вместе с
   > вердиктом. Твоя зона: `<зона>`. Не меняй `<ограничения>`. Верни краткий отчёт:
   > что прочитал, что изменил, какие проверки выполнил.
   > Если этап `tests` — после правки загрузи расширение (`1c-batch.py load-extension`)
   > и выполни красный смоук сам (`run-tests.py`, полный набор), обнови секцию
   > «Смоук» в `TESTS.md` и приложи пути логов.
3. После ответа проверь, что артефакт изменился и отчёт соответствует задаче. Если нет —
   fallback на нового агента.
4. Новый агент запускай, если: идентификатора нет; SendMessage недоступен; агент не
   резюмировался; две попытки подряд на одном дефекте не дали результата. После двух
   неудач продолжение прекращай — это защита от «защиты своего артефакта».
5. SendMessage — только для того же этапа и того же артефакта. Смену роли (`tests` →
   `develop`) он не выполняет. Статусы, артефакты, архивирование и вердикты остаются за
   оркестратором.
6. При переименовании артефакта (`TESTS.md` → `TESTS.<n>.md`) в re-brief передавай
   точные текущие пути.

## Статусы
`pending → running → done | failed`. Отключённый этап — `skipped`, его пропускаем.
`done` переводится только из `running`. Повторный запуск этапа без возврата на
доработку — команда `restart` (`task_status.py ... <этап> restart`): она
закрывает открытый прогон, увеличивает `iteration` и начинает новый. `pending`
используется только для возврата на доработку (и архивирует вердикты).
В циклическом workflow (правило `cyclic-review-workflow`) допустим обратный переход
`done → pending`: при возврате этапа на доработку оркестратор переводит его в
`pending` командой `task_status.py ... <этап> pending` и запускает заново.

## Циклический workflow develop ↔ testing/review (оркестратор ведёт его сам)
Если включены `testing` и/или `review`, задача идёт итерациями по правилу
`cyclic-review-workflow`. Оркестратор — единственный исполнитель этого цикла (внешнего
инструмента нет), поэтому обязан:
1. После `testing` прочитать вердикт из `TESTING.md`, после `review` — из `REVIEW.md`
   (ищи строку-ячейку `| Вердикт | … |` дословно).
2. При вердикте «✗ НЕ ПРОЙДЕНО» / «✗ НА ДОРАБОТКУ» — не продолжать к следующему
   этапу: вернуть нужный этап в `pending` командой `task_status.py ... <этап> pending`
   и запустить заново. Номер итерации этапа ведётся автоматически: `task_status.py`
   инкрементирует поле `iteration` соответствующего этапа в `task.json` при его
   повторном переходе в `running`. Архивируй `DEVELOP.md`/`TESTS.md` сам
   (`DEVELOP.md`→`DEVELOP.<n>.md`, где `<n>` — прежнее значение `iteration` этого
   этапа из `task.json`). **Вердикты `TESTING.md`/`REVIEW.md` архивирует
   `task_status.py` автоматически** при переводе `develop`/`tests` в `pending`
   (`TESTING.<n>.md`/`REVIEW.<n>.md`, `<n>` — `iteration` этапа `testing`/`review`) —
   вручную не дублируй. Если целевой файл уже существует, команда упадёт и статус
   не изменится — разбери файлы и повтори.
   Каждый прогон этапа пишется в историю `stage["runs"]` (`iteration`, `started_at`,
   `finished_at`) — это данные для метрик; поле `iteration` `runs[]` не меняет.
3. Лимит — 10 итераций: если `iteration` возвращаемого этапа в `task.json` ≥ 10,
   пометь этап `failed` и остановись.
4. При вердикте «✓ ПРОЙДЕНО» / «✓ ПРИНЯТО» — перейти к следующему включённому этапу.
5. Возврат `tests` из `review` завершается красным смоуком до `tests done`, даже если
   `testing` отключён (см. «Красный смоук после этапа `tests`»).

## Гейты (поля `gate` / `approved`)
Гейт — это обязательная пауза на подтверждение пользователя после этапа, у которого
`gate: true`. Единственный критерий — поле `gate`; никакие другие флаги на это не
влияют.

Порядок:
1. Заверши этап с `gate: true` (`... <этап> done`).
2. ОСТАНОВИСЬ и покажи пользователю результат/артефакт этапа, запроси подтверждение.
3. После подтверждения отметь гейт:
   `python .claude/tools/task_status.py tasks/task#<id> <этап> approve`.
4. Только теперь переходи к следующему этапу.

Это подкреплено кодом: `task_status.py` ОТКАЖЕТСЯ перевести следующий этап в
`running`, пока у предыдущего включённого этапа `gate: true` и `approved: false`
(вернёт ошибку «гейт не пройден»). Статус `approve` выставляет `approved: true`,
не меняя `status` этапа.
