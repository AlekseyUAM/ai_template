# Метаданные — `1c-md`

MCP-сервер не контейнерный: это **расширение 1С**, которое публикует
HTTP-сервис `mcp_APIBackend`. Клиент ходит в опубликованную базу по
`http://<хост>/<публикация>/hs/mcp/`. Расширение — из проекта
[vladimir-kharin/1c_mcp](https://github.com/vladimir-kharin/1c_mcp) (в поставке —
`deps/mcp_tools_cfe/MCP_Сервер.cfe`).

## Поля карточки

| Поле | Значение по умолчанию |
|---|---|
| Наименование | — (обязательно) |
| Имя в `.mcp.json` | `1c-md` |
| Назначение | «Вся информация об актуальных метаданных конфигурации» |
| URL | `localhost` — хост веб-публикации |
| Имя базы | `my_database` — имя публикации |
| Подключение | строится автоматически (см. ниже) |

```json
"1c-md": {
    "type": "http",
    "url": "http://localhost/my_database/hs/mcp"
}
```

Кнопка **«Скачать cfe»** отдаёт файл расширения — тот же, что
`deps/mcp_tools_cfe/MCP_Сервер.cfe`.

## Развёртывание

1. **Скачать расширение** — кнопкой «Скачать cfe» в карточке или взять
   `deps/mcp_tools_cfe/MCP_Сервер.cfe` из репозитория.
2. **Загрузить расширение в информационную базу**: Конфигуратор → «Расширения
   конфигурации» → «Добавить из файла» → выбрать `.cfe` → «Применить». Для
   серверной базы нужны права администратора. В расширении появляются
   инструменты чтения метаданных.
3. **Опубликовать базу на веб-сервере** (Apache/IIS) так, чтобы был доступен
   HTTP-сервис `mcp_APIBackend`. Адрес получается таким:
   `http://<хост>/<имя публикации>/hs/mcp/`.
   **Имя публикации в URL чувствительно к регистру** (например, `base`, а не
   `Base`): несовпадение приводит к редиректу, который превращает POST в GET.
4. **Настроить доступ.** Прямое подключение MCP-клиента к 1С требует
   публикации без аутентификации (в `default.vrd` «вшиваются» реквизиты
   доступа) — это допустимо только в доверенной сети. Рекомендуемый вариант —
   Python-прокси из `deps/1c_mcp/src/py_server`: он держит креды к 1С у себя и
   умеет OAuth2 для клиентов.
5. **Заполнить карточку**: `URL` — хост веб-сервера, `Имя базы` — имя
   публикации. Поле «Подключение» сгенерируется автоматически.

### Подключение через Python-прокси

Прокси избавляет от необходимости отключать аутентификацию 1С и умеет отдавать
MCP по HTTP (`/mcp/`) и SSE (`/sse`), а также по stdio.

```bash
cd deps/1c_mcp
python -m venv .venv && source .venv/bin/activate
pip install -r src/py_server/requirements.txt
cp src/py_server/env.example .env
# в .env: MCP_ONEC_URL=http://<хост-1С>/<публикация>,
#         MCP_ONEC_USERNAME=..., MCP_ONEC_PASSWORD=..., MCP_PORT=8000
python -m src.py_server http --port 8000
```

Вариант в Docker (если 1С на том же хосте — в `MCP_ONEC_URL` укажите
`host.docker.internal` или, на Linux, IP хоста):

```bash
cd deps/1c_mcp
cp .env.docker.example .env   # заполнить MCP_ONEC_URL/…_USERNAME/…_PASSWORD
docker compose up -d
```

В карточке тогда замените «Подключение» на адрес прокси:

```json
"1c-md": {
    "type": "http",
    "url": "http://<хост-прокси>:8000/mcp/"
}
```

## Развёртывание на отдельном сервере

Расширение и веб-публикация живут на сервере 1С (или на веб-сервере рядом с
ним). На машине агента ничего разворачивать не нужно — в карточке укажите
`URL` этого сервера и имя публикации. Если доступ идёт через прокси, прокси
разворачивается на сервере (или рядом) и в «Подключение» попадает его адрес.

## Проверка

```bash
# прямой HTTP-сервис: должен ответить на MCP-запрос, а не редирект/401
curl -i "http://<хост>/<публикация>/hs/mcp/"

# прокси
curl -s "http://<хост-прокси>:8000/health"
```

Из агента — вызов инструмента чтения метаданных (например, списка объектов
конфигурации); если ответ пустой, проверьте имя публикации и доступ к базе.
