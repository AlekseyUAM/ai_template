# Исследование: нужно ли переделывать `deps/mcp-bsl-lsp-bridge`

Задача из `tmp/NOTE1.md` (вид MCP «Статический анализ BSL»): нужен контейнер
**только с BSL LS**, который проверяет **присланный ему код** по настройкам из
`.bsl-language-server.json` и возвращает ошибки/предупреждения. **Доступа к
кодовой базе у него нет** — в отличие от `deps/mcp-bsl-lsp-bridge`.

## Что сейчас есть

### `deps/mcp-bsl-lsp-bridge` (Go-обвязка)
Тяжёлый сервер вокруг BSL LS, спроектированный вокруг **кодовой базы**:
- монтирует каталог проекта как volume (`/projects`), индексирует исходники;
- держит BSL LS «прогретым», file-watcher следит за изменениями;
- надстройка `call_graph` (полный граф вызовов), multiproject-режим;
- тянет дополнительный пакет `rlm-tools-bsl`, s6-overlay-супервизор.

Вывод: это ориентировано на навигацию/индексацию **существующей** кодовой базы,
а не на stateless-проверку присланного фрагмента. Для вида «Статический анализ
BSL» из NOTE1 — **избыточно и не соответствует требованию «без доступа к базе»**.

### `deps/bsl-language-server` (сам BSL LS)
Важно: у BSL LS **есть собственные режимы без всякой обвязки** (см.
`docs/en/features/McpMode.md` и корневой `CLAUDE.md`):
- `analyze` — пакетный анализ каталога исходников, отчёты SARIF/Generic/JSON (CI);
- `mcp` — **встроенный MCP-сервер** поверх того же движка диагностик:
  ```sh
  java -jar bsl-language-server.jar mcp --protocol streamable --server.port=8001
  ```
  транспорт `stdio` | `sse` | `streamable`, HTTP-эндпоинт `/mcp`. Настройки
  проверок берутся из глобального `-c/--configuration <path>` и/или
  `.bsl-language-server.json` в корне рабочей папки
  (`docs/en/features/ConfigurationFile.md`).

## Вывод

**Да, для вида «Статический анализ BSL» обвязку `mcp-bsl-lsp-bridge` переделывать
не нужно — от неё лучше отказаться.** Достаточно поднять **родной `mcp`-режим
самого BSL LS** в лёгком контейнере (JRE 21 + `bsl-language-server-*-exec.jar`),
прокинув порт и смонтировав только `.bsl-language-server.json` с настройками
проверок. Это:
- убирает индексацию/монтирование кодовой базы, file-watcher, call-graph,
  multiproject и зависимость `rlm-tools-bsl` — т.е. именно «только BSL LS»;
- даёт HTTP-эндпоинт `/mcp` на заданном порту — совпадает с шаблоном подключения
  вида из NOTE1 (`http://{url}:{port}/mcp`).

### Что уточнить при реализации контейнера (будущая работа Фазы 1/2)
1. **Тип транспорта в подключении.** NOTE1 задаёт `"type": "http"`; у BSL LS
   streamable-MCP клиентский тип в примере — `streamable-http` (эндпоинт `/mcp`).
   Свериться и привести к одному значению.
2. **Stateless-проверка присланного кода.** Инструмент `analyze_file` в `mcp`-режиме
   работает в пределах зарегистрированной workspace-папки (индексирует исходники).
   Для чистого «прислал фрагмент — получил диагностику без кодовой базы» ближе
   CLI-подкоманда `analyze` с временным srcDir; возможно, понадобится тонкая
   обёртка «код → временный каталог → `analyze`/`analyze_file` → диагностики».
   Это единственное место, где может потребоваться минимальная собственная логика
   вместо «голого» BSL LS.
3. **`.bsl-language-server.json`.** При разворачивании контейнера создавать/монтировать
   этот файл (в NOTE1 — «в корне проекта будет создан файл `.bsl-language-server.json`
   с настройками проверок»); формат — `docs/en/features/ConfigurationFile.md`.
4. **Образ.** Нужен образ `JRE21 + exec-jar` (без Go-бинарей bridge). Можно
   переиспользовать стадию загрузки jar из `mcp-bsl-lsp-bridge/Dockerfile`, но без
   финального слоя с `mcp-lsp-bridge`/`lsp-session-manager`/`rlm-tools-bsl`.
