# Проверка обработчиков событий 1С в code-analyze — дизайн

Дата: 2026-11-23
Статус: на согласовании

## Задача

Добавить в `template/.claude/skills/code-analyze` скрипт, который проверяет
объявления процедур-обработчиков стандартных событий 1С: не экспортные ли они,
правильные ли у них параметры, и относится ли событие к данному виду метаданных
и виду модуля.

Мотивация: LLM при генерации кода создаёт в модуле объекта документа
`Процедура ОбработкаПроведения(ОтменитьПроведение, Параметр, ВыполняетсяЛица) Экспорт` —
экспортную, с тремя параметрами вместо двух. Проверка должна ловить это до ревью.

## Что выяснено про источник данных

- В `shcntx_ru.hbk` платформы 8.3.27.2170 — **660 страниц описаний событий**,
  **140 типов-владельцев**. Для каждого события есть шаблон-заготовка `.st` с
  канонической подписью на русском и английском, например:
  `Процедура ОбработкаПроведения(Отказ, РежимПроведения)` /
  `Procedure Posting(Cancel, PostingMode)` — без `Экспорт`.
- Справка хранится как ZIP с HTML внутри контейнера `.hbk`; ZIP читается
  стандартной библиотекой Python. MCP `1c_platform` списки обработчиков событий
  не индексирует (только методы/свойства типов), поэтому источник — сама справка.
- Проверка количества параметров на реальной конфигурации
  (`D:\projects\test`, 2000+ модулей) даёт **4 настоящих несовпадения**:
  `ОбработкаПроведения(3)` в документе при документированных 2 (это ровно
  пример из задачи), `ПередЗаписью(3)` в справочнике при 1,
  `ПриКомпоновкеРезультата(4)` в двух отчётах при 3.
- В реальном коде встречаются и легальные «меньше параметров»: в модулях
  приложения `ПередНачаломРаботыСистемы()` без `Отказ`. Справка помечает такой
  параметр «Значение по умолчанию: Ложь», то есть он **необязателен**. Поэтому
  правило разрешает опускать только необязательные хвостовые параметры, но не
  обязательные: `ПередЗаписью(Отказ)` в документе — ошибка (пропущены
  обязательные `РежимЗаписи`/`РежимПроведения`), а `ПередНачаломРаботыСистемы()` —
  нет.
- BSL LS 1.30.0 уже содержит диагностику `EventHandlerInvalidSignature`
  (включена, severity Error), но она **не работает в текущем MCP-окружении**:
  MCP-обёртка `ai1c/mcp-bsl-ls` запускает stateless CLI на временном файле,
  в контейнере нет HBK (`bsl-context`) и нет метаданных workspace. По исходникам
  BSL LS контракт берётся из HBK, а owner-тип — из `documentContext.getMdObject()`
  (`ДокументОбъект.<Имя>`); без них контракт пуст. Диагностика сравнивает
  **только количество** параметров (по всем перегрузкам), имена и `Экспорт` не
  проверяет.
- События различаются по виду модуля: `ДокументОбъект` (10 событий),
  `СправочникОбъект` (8), `РегистрСведенийНаборЗаписей` (5),
  `КонстантаМенеджерЗначения` (4), менеджеры, команды, модули приложения/сеанса.
  У `ОбработкаЗаполнения` у объекта и набора записей — разные подписи.
- Путь в выгрузке однозначно даёт вид модуля:
  `Catalogs/X/Ext/ObjectModule.bsl`, `Documents/X/Ext/ManagerModule.bsl`,
  `.../Forms/Ф/Ext/Form/Module.bsl`, `src/cf/Ext/ManagedApplicationModule.bsl`,
  `.../Commands/К/Ext/CommandModule.bsl`.

## Цели

1. Отдельный скрипт `check_event_handlers.py`, работающий без платформы и MCP.
2. Снимок данных `event_handlers.json` — по образцу `system_enums.json`, чтобы
   рантайм не зависел от установленной платформы.
3. Генератор снимка `tools/update_event_handlers.py`, читающий `.hbk` напрямую.
4. Покрытие всех видов метаданных и видов модулей со стандартными событиями,
   где платформа вызывает обработчик **по имени**: объектные и менеджерские
   модули, наборы записей, менеджер значения константы, модули
   приложения/сеанса, команды, WebSocket-клиент, бот, объектные модули внешних
   обработок/отчётов, внешние источники данных.
5. Тесты pytest на инференс вида модуля, на каждую проверку и на целостность
   снимка.
6. Раздел в `SKILL.md` с командами и таблицей кодов.

## Не-цели

- Не проверяем обработчики HTTP-сервисов, Web-сервисов и сервисов интеграции:
  имена их методов задаются в метаданных и произвольны; параметры проверить
  нечем (кроме случая явного `--module-type` с известной подписью — не делаем).
- Не проверяем подписки на события (EventSubscriptions) и подключаемые
  обработчики вида `Подключаемые_*`.
- Не проверяем директивы компиляции (`&НаКлиенте`/`&НаСервере`) — для этого
  нужна отдельная таблица доступности по событиям, в справке её нет в
  машиночитаемом виде.
- Не разбираем `.hbk` в рантайме — только снимок.
- **Не проверяем модули управляемых и обычных форм в v1.** В форме обработчик
  привязывается через `Form.xml`, имя процедуры произвольно; проверка по имени
  даёт ложные срабатывания (в корпусе, например, есть служебная
  `Функция ОбработкаПроверкиЗаполненияНаСервере()`). Корректная проверка требует
  разбора `Form.xml`, owner-типа формы и набора перегрузок подписей — как это
  делает BSL LS через `FormTypesProvider`. Это возможное развитие.
- Не проверяем имена параметров и `Экспорт` через bsl_ls: bsl_ls этого не
  умеет (см. выше), это наша зона.

## Анти-цели

- Никаких ложных срабатываний на легальный код: `ПередЗаписью(Отказ)` в модуле
  объекта, произвольные процедуры, совпадающие по имени со случайным словом, не
  должны считаться ошибкой.
- Скрипт не должен требовать метаданные конфигурации, MCP или интернет.

## Ограничения

- Python 3.6+ stdlib (как `analyze_code.py` и `system_enums.json`).
- Формат вывода совместим с `analyze_code.py`:
  `severity | код | строка | сообщение`; при обходе каталога — блоки
  `# путь` + `--- 8< ---`.
- Код возврата 1 только при наличии `error`; флаг `-NoFail` отключает.
- В `SKILL.md` команды пишутся как `python "${CLAUDE_SKILL_DIR}/..."` —
  деплой заменяет `python` на интерпретатор `.venv`.

## Рассмотренные подходы

1. **Отдельный скрипт + JSON-снимок (выбран).** Совпадает с шаблоном
   `check_metadata_names.py`; `analyze_code.py` и `rules.py` не меняются;
   снимок обновляется отдельным генератором. Минус — ещё одна команда.
2. **Встроить в `analyze_code.py`/`rules.py`.** Один запуск, но правила
   перестают быть чисто текстовыми: появляется зависимость от пути и вида
   модуля, ломается тестируемость `ModuleContext(text)`.
3. **Разбирать `.hbk` при каждом запуске.** Всегда актуально, но требует
   установленной платформы, медленнее и нестабильно между машинами.

### Снимок `event_handlers.json`

```json
{
  "schema_version": 1,
  "platform": "8.3.27.2170",
  "generated_at": "2026-11-23",
  "source": "shcntx_ru.hbk (syntax assistant)",
  "modules": {
    "Document.ObjectModule": {
      "title_ru": "Модуль объекта документа",
      "title_en": "Document object module",
      "events": {
        "ОбработкаПроведения": {
          "name_en": "Posting",
          "kind": "procedure",
          "signatures": [
            {"params_ru": ["Отказ", "РежимПроведения"],
             "params_en": ["Cancel", "PostingMode"],
             "optional": [true, false],
             "required_count": 1}
          ]
        }
      }
    },
    "HTTPService.Module": {
      "title_ru": "Модуль HTTP-сервиса",
      "handler_name_arbitrary": true,
      "events": {}
    }
  }
}
```

- Несколько подписей у события бывают у перегрузок; скрипт принимает любое
  совпадение по количеству.
- `handler_name_arbitrary: true` — имена обработчиков задаются в метаданных;
  скрипт такие модули не проверяет.
- Имена событий при сопоставлении принимаются и русские, и английские,
  без учёта регистра (как и имена параметров).

### Ключи видов модулей

`<ВидМетаданных>.<ВидМодуля>`, например:
`Catalog.ObjectModule`, `Document.ManagerModule`,
`InformationRegister.RecordSetModule`, `Constant.ValueManagerModule`,
`Configuration.ManagedApplicationModule`, `Configuration.SessionModule`,
`CommonCommand.CommandModule`, `Command.CommandModule`,
`WebSocketClient.Module`, `Bot.Module`,
`ExternalDataProcessor.ObjectModule`, `ExternalReport.ObjectModule`,
`ExternalDataSourceTable.ObjectModule` и т.д.
`CommonModule.Module` присутствует как ключ, но событий не содержит.

### Проверки

Для каждой процедуры/функции модуля, имя которой совпадает с событием:

| Код | Severity | Условие |
|---|---|---|
| `event-handler-exported` | warning | у стандартного обработчика стоит `Экспорт` |
| `event-handler-params` | error | объявлено больше параметров, чем в контракте, или пропущен обязательный хвостовой параметр |
| `event-handler-param-name` | info | параметр на позиции назван не как в справке (ru/en, регистр не важен); не блокирует ревью |
| `event-handler-wrong-module` | warning | имя — стандартное событие другого вида модуля/метаданных |

Правила сопоставления параметров:

- объявление должно быть префиксом одной из документированных подписей; если в
  снимке несколько подписей — подходит любая;
- опускать можно только **необязательные хвостовые** параметры (в справке у них
  есть «Значение по умолчанию»); пропуск обязательного — error;
- лишний параметр сверх полной подписи — error;
- имена сравниваются позиционно, допустимы русское и английское канонические
  имена, регистр не важен; `Знач` перед именем не мешает (парсер его отбрасывает);
- несовпадения имён собираются в один Finding на процедуру (меньше шума);
- severity `info` у имён — потому что платформа и bsl_ls имена не проверяют;
  в корпусе легальные переименования встречаются (например,
  `КлючОтчета`/`КлючВарианта` в менеджере хранилища настроек);
- в каждом сообщении печатается правильная сигнатура целиком:
  `Процедура ОбработкаПроведения(Отказ, РежимПроведения)` (и английский
  вариант), чтобы обработчик можно было исправить без догадок;
- если событие документировано функцией, а объявлено процедурой (или наоборот),
  это не проверяем в v1 — таких случаев в корпусе нет.

Если вид модуля по пути определить не удалось: файл пропускается, в stderr
печатается одна строка-предупреждение; для каталога — итоговая сводка
«пропущено N файлов». `--module-type` допустим только с одним файлом или
stdin; с каталогом — ошибка аргументов.

`event-handler-wrong-module` не срабатывает:

- в общих модулях (там возможны подписки на события с произвольными именами);
- в модулях с `handler_name_arbitrary`;
- если имя не является событием ни одного вида модуля.

### CLI

```bash
# один файл с автоопределением
python .../check_event_handlers.py src/cf/Documents/Заказ/Ext/ObjectModule.bsl
# каталог
python .../check_event_handlers.py src/cf
# произвольный файл/stdin без пути
python .../check_event_handlers.py --module-type Document.ObjectModule \
    --object-name Заказ tmp/документ.txt
cat module.bsl | python .../check_event_handlers.py \
    --module-type Catalog.ObjectModule --object-name Товары -
# справочник ключей
python .../check_event_handlers.py --list-module-types
```

### Генератор

`tools/update_event_handlers.py --hbk <путь к shcntx_ru.hbk> --out event_handlers.json
[--platform 8.3.27.2170]`.

Шаги:

1. Прочитать контейнер `.hbk` (заголовок, TOC, `FileStorage`), получить ZIP.
2. Обойти `objects/**/events/*.html`, взять имя события и владельца из
   `V8SH_pagetitle`/`V8SH_title`; подпись — из парного `.st`
   (`Процедура <Имя>(<Параметры>)` / `Procedure ...`), при отсутствии — из
   секции `Синтаксис:`.
3. События приложения взять из категорий `События приложения`,
   `События обычного приложения`, `События внешнего соединения`,
   `События модуля сеанса`.
4. Смэпить владельцев на ключи модулей.
5. Записать JSON и напечатать сводку (модулей/событий).

Инструкция по обновлению — в `tools/README.md`.

## Тестирование

- `test_module_key_from_path` — все строки таблицы инференса, Windows/Unix
  разделители, `cfe`, `epf`.
- Позитивные: каноническое объявление документа; `ПередЗаписью(Отказ)` в
  справочнике; событие менеджера в менеджерском модуле; событие приложения в
  `ManagedApplicationModule.bsl`; произвольная процедура игнорируется.
- Негативные: экспорт; 3 параметра вместо 2 (пример пользователя);
  пропущен обязательный хвостовой параметр (error); переименованный параметр
  (info); `ОбработкаПроведения` в модуле объекта справочника. Позитивный:
  необязательный хвостовой параметр опущен (`ПередНачаломРаботыСистемы()`).
- Снимок: JSON парсится, все подписи непустые, у каждого ключа есть события,
  длина `optional` совпадает с числом параметров.
- CLI: `--module-type` на stdin; `--list-module-types`; автоопределение по пути.
- Калибровка на корпусе `D:\projects\test`: после разрешения БСП-перегрузки
  отчётов (`ПриКомпоновкеРезультата` с 4-м `АдресХранилища`) остаётся 1
  `event-handler-params` — реальный дефект `Справочник.ВопросыШаблонаАнкеты`
  (`РежимПроведения` в справочнике). Пример `ОбработкаПроведения(3)` из задачи
  покрыт тестом (файл `ПриходнаяНакладная` в текущей выгрузке отсутствует).
  Также 2-3 `event-handler-exported` (реальные экспортные БСП-обработчики),
  18 `event-handler-param-name` (info), ложных `event-handler-wrong-module`
  нет; 817 файлов форм пропущено осознанно.

## Что осталось на усмотрение исполнителя

- Точные формулировки сообщений и порядок вывода.
- Полный список ключей внешних источников данных (best-effort по путям
  `ExternalDataSources/...`).
- Формат `title_ru/title_en`.
- Нужен ли алиас `Document.ObjectModule` в коротком виде (`doc_object`).
- Формы как следующий этап: разбор `Form.xml`, owner-тип формы, перегрузки
  подписей (после v1).

## Риски

- Справка платформы меняется; снимок привязан к версии 8.3.27.2170, обновление —
  генератором.
- В конфигурации могут быть кастомные процедуры с именами стандартных событий;
  для модулей со стандартными событиями это будет warning — это и есть цель
  проверки.
- Внешние источники данных (`ExternalDataSources/...`) — best-effort: точная
  структура путей может отличаться от ожидаемой.
- Модули форм намеренно не проверяются в v1 — это осознанное ограничение, а не
  пропуск.
