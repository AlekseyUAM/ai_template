# Автоматический прогон benchmark-задач и анализ template — дизайн

Дата: 2026-11-14
Статус: утверждён к реализации

## Контекст

`benchmark/setup_benchmark.py` готовит проект (`BENCH_PROJECT_DIR` из
`benchmark/test.env`): окружение `.claude/`, базу 1С, выгрузки, задачи
`tasks/task##NNN` и базовый git-коммит. Дальше задачи выполняются агентом
Claude Code, но измерение качества template (время, итерации тестов и ревью,
качество кода) сейчас ручное.

Нужен самостоятельный инструмент, который после `setup_benchmark.py`:

1. выполняет задачи проекта последовательно в `claude-ds` с ограничением
   wall-clock на каждую;
2. собирает объективные метрики по ходу выполнения;
3. запускает отдельную сессию-аналитик, которая сравнивает результат с
   `benchmark/example.bsl` и предлагает улучшения template;
4. записывает отчёт в `<проект>/tmp/RESULT.md`.

## Цели

- Сократить время выполнения задач.
- Уменьшить число итераций написания и запуска тестов.
- Уменьшить число итераций код-ревью.
- Улучшить качество кода (сравнение итогового
  `src/cf/Documents/РасходнаяНакладная/Ext/ObjectModule.bsl` с
  `benchmark/example.bsl`).
- Улучшить качество окружения template.

## Ограничения

Из требований пользователя:

- template не затачивается под задачи #001/#002; рекомендации должны быть
  общими и пригодными для любых будущих задач;
- нельзя хардкодить фрагменты кода из `example.bsl` в template;
- нельзя увеличивать число символов в описаниях задач `benchmark/tasks`;
- допускаются предложения по расширению `ЮнитТесты`, новым инструментам,
  любым улучшениям template и изменениям описаний задач.

Дополнительные ограничения проекта:

- Python ≥ 3.10, только stdlib в раннере; новых зависимостей нет.
- Весь пользовательский текст (логи, ошибки, отчёт) — на русском.
- Коммиты — локально в `main`, без `push`.
- Задачи выполняются той же командой, что и в AgentMon:
  `claude -p "Выполни задачу tasks/<папка> по этапам из её task.json. Следуй навыку task-orchestration."`

## Принятые решения

| Вопрос | Решение |
|---|---|
| Кто делает качественный анализ | Отдельная сессия `claude-ds` в роли аналитика; скрипт лишь собирает данные и записывает её ответ в `tmp/RESULT.md` |
| Поведение при сбое/таймауте задачи | Остановить выполнение следующих задач; анализ по уже собранным данным всё равно выполнить |
| Лимиты времени | `max_minutes` из `task.json`, переопределение флагами `--limit <задача>=<N|Nм|Nч>` |
| Свежесть проекта | Отказ без `--force`: задачи должны быть `planned`, артефактов этапов нет, git-дерево чистое, HEAD — baseline-коммит setup'а |
| Набор задач по умолчанию | Все `tasks/task##*` в порядке имён; `--task` ограничивает набор |
| Размещение | Самостоятельный `benchmark/` (CLI + ядро + тесты), без зависимости от `agentmon` |

## Архитектура

```
benchmark/run_benchmark.py   # CLI: аргументы, логи, коды выхода
benchmark/bench_run.py       # ядро: preflight, запуск, метрики, дайджест, аналитик
benchmark/tests/conftest.py  # sys.path для импорта bench_run
benchmark/tests/test_bench_run.py
benchmark/README.md          # раздел «Прогон и анализ»
```

Ядро не импортирует `agentmon`; `BENCH_PROJECT_DIR` читается из
`benchmark/test.env` простым парсером `key=value` (комментарии и пустые строки
игнорируются). Значение флага `--project` приоритетнее env-файла.

## CLI

```bash
.venv/bin/python benchmark/run_benchmark.py \
  --limit task##001=30 --limit task##002=2ч
```

| Флаг | Назначение |
|---|---|
| `--project DIR` | каталог проекта; иначе `BENCH_PROJECT_DIR` из `--env` |
| `--env FILE` | env-файл, по умолчанию `benchmark/test.env` |
| `--task <селектор>` | ограничить набор; селектор — папка (`task##001`), идентификатор (`#001`) или номер (`001`); повторяемый |
| `--limit <селектор>=<значение>` | лимит задачи; `30`, `30м`, `30m`, `2ч`, `2h`; повторяемый; неизвестный селектор — ошибка |
| `--claude-cmd CMD` | команда агента, по умолчанию `claude-ds` (ищется в `PATH`) |
| `--analysis-timeout N` | лимит сессии-аналитика в минутах, по умолчанию 30 |
| `--skip-analysis` | только задачи и метрики; в `tmp/RESULT.md` — детерминированная сводка с пометкой |
| `--force` | разрешить прогон на непустом проекте; факт фиксируется в метриках и отчёте |

Ошибки аргументов и preflight — код `1`. Дубликат селектора в `--limit` —
ошибка (не «последний выиграл»).

## Preflight

До запуска проверяются:

1. Проект существует, `tasks/task##*` найдены, `task.json` читается.
2. У всех выбранных задач `status = planned`.
3. В каталогах задач нет артефактов выполнения: `ANALYZE.md`, `ARCHITECT.md`,
   `TESTS*.md`, `DEVELOP*.md`, `TESTING*.md`, `REVIEW*.md`, `DOCS*.md`,
   `task.diff`, `USER_FEEDBACK.md`.
4. `git status --porcelain` пуст.
5. `git log -1 --format=%s` начинается с `baseline before task` (baseline-коммит
   `setup_benchmark.py`).
6. `claude-cmd` существует и исполняем.

Нарушение пунктов 1–5 — понятная ошибка «пересоздайте проект через
`benchmark/setup_benchmark.py` или запустите с `--force`». `--force` снимает
проверки 2–5, но не 1 и не 6. В `run.json` пишется `contaminated: true`, в
промпте аналитика делается пометка о возможной загрязнённости.

## Цикл выполнения

Для каждой выбранной задачи в порядке имён:

1. Снять `HEAD` и `git status`, запомнить монотонное время старта.
2. Сформировать промпт оркестрации (как AgentMon).
3. Запустить `claude-cmd -p <промпт> --output-format stream-json --verbose`
   в каталоге проекта; stdout — `transcripts/<папка>.stream.jsonl`, stderr —
   `transcripts/<папка>.stderr.log`, новый process group.
4. Ждать завершения не дольше лимита задачи. По истечении: `SIGINT` группе,
   пауза до 10 с, затем `SIGTERM`, пауза 5 с, затем `SIGKILL`. Частичный вывод
   сохраняется, исход — `timeout`.
5. После завершения собрать:
   - код выхода, wall-clock;
   - `task.json` (общий статус, этапы, итерации, тайминги);
   - `HEAD` после, `git status`, дифф относительно `HEAD` до задачи (включая
     незакоммиченные и новые файлы);
   - `result`-событие stream-json (`duration_ms`, `num_turns`, `cost_usd`,
     usage, `session_id`, `is_error`);
   - транскрипт сессии и транскрипты сабагентов.
6. Определить исход:
   - `success` — код выхода 0 и все включённые этапы в `task.json` имеют
     статус `done`;
   - `timeout` — сработал лимит;
   - `failed` — ненулевой код выхода;
   - `incomplete` — код 0, но `task.json` не `done` (например, гейт
     `awaiting_user`).
7. При исходе, отличном от `success`, остановить цикл (следующие задачи не
   запускаются). Перейти к анализу.

Параллельного выполнения задач нет. Автоматического пересоздания проекта нет.

## Метрики

Источники и извлекаемые данные:

| Источник | Данные |
|---|---|
| Скрипт | wall-clock, код выхода, исход, HEAD до/после, пути |
| `task.json` | статус, этапы: `enabled/status/iteration/started_at/finished_at`, `changed_files`, тайминги `db_update` |
| `stream-json` | `session_id`, `duration_ms`, `num_turns`, `total_cost_usd`, токены, `is_error`, `permission_denials` |
| Транскрипт сессии и сабагентов | вызовы инструментов по именам, ошибки (`is_error`), правки по файлам, Bash-команды по классам, длительности операций, простои > 5 мин, вклад сабагентов |
| Артефакты задач | вердикты `TESTING.md`/`REVIEW.md`, архивы `*.n.md`, `result.json` тестов, маркеры `EXIT=`, `LOAD_EXIT=` |
| Git | диффы и статистика по задаче |
| Анализаторы | `code-analyze` и `query-analyze` по изменённым `.bsl` и по `benchmark/example.bsl`; `bsl_ls` — аналитик через MCP |

Классификация Bash-команд (по подстрокам, без привязки к задачам):
`test-run` (`run-tests.py`), `smoke`, `extension-load` (`load-extension`),
`config-load` (`load-config-optimized.py`, `1c-batch.py load`),
`static-check` (`analyze_code.py`, `analyze_query.py`, `bsl_ls`, `check`),
`mcp`, `git`, `other`.

Производные метрики по целям:

- **время**: wall-clock, длительности этапов, топ-5 долгих операций, простои;
- **тесты**: итерации этапов `tests`/`testing`, число `test-run` и `smoke`
  команд, правки тест-модуля до первого `tests done`, возвраты с виновником
  `тест`/`код`;
- **ревью**: итерации `review`, число архивов `REVIEW.<n>.md`, вердикты,
  возвраты;
- **качество**: находки анализаторов по итоговому модулю и эталону, дифф-статистика,
  число процедур/функций/запросов/комментариев;
- **окружение**: сбои MCP/хуков/платформы/загрузки, «команда не найдена»,
  таймауты, повторяющиеся сигнатуры ошибок.

## Транскрипты и дайджест

Сессия Claude хранится в `~/.claude/projects/<проект>/<session_id>.jsonl`;
сабагенты — в `<session_id>/subagents/*.jsonl`. Файлы находятся по
`session_id` из `system/init` stream-json (глобом по каталогам проектов).

`digest.md` — компактная выжимка для аналитика:

- сводная таблица задач;
- хронология этапов;
- топ ошибок и повторяющихся сбоев;
- топ долгих операций и простоев;
- активность по инструментам, правкам и сабагентам.

Сырые JSONL в контекст аналитика не передаются. Если транскрипт не найден,
дайджест строится только по `stream-json`, в отчёте — пометка.

## Каталог прогона

```
<проект>/tmp/benchmark/<YYYYMMDD-HHMMSS>/
  run.json                    # конфигурация, исходы, git-состояние
  metrics.json                # полные структурированные метрики
  digest.md                   # выжимка для аналитика
  run.log                     # лог работы раннера
  diffs/<папка>.diff          # дифф задачи (коммит + рабочее дерево + новые файлы)
  diffs/<папка>.stat.txt      # git diff --stat
  transcripts/<папка>.stream.jsonl
  transcripts/<папка>.stderr.log
  transcripts/analyst.stream.jsonl
  analysis-prompt.md          # точный промпт аналитика
  analyst-result.md           # сырой ответ аналитика
```

Итоговый отчёт — всегда `<проект>/tmp/RESULT.md` (атомарная запись
temp + `os.replace`).

## Статические проверки

Раннер детерминированно запускает:

- `analyze_code.py` (с `-NoFail`) по всем изменённым и новым `.bsl` задачам и
  по `benchmark/example.bsl` (если файл есть);
- `extract_queries.py` + `analyze_query.py` по тем же файлам (без `node`
  структурные проверки пропускаются — это фиксируется как «слой не отработал»);
- Python — `<проект>/.venv/bin/python`, если есть, иначе текущий интерпретатор.

Недоступность анализатора не считается «проверок нет»: в `metrics.json` и
отчёте она помечается как пропуск слоя контроля.

## Сессия-аналитик

Второй запуск `claude-cmd` в каталоге проекта:

```
claude-ds -p <analysis-prompt> --output-format stream-json --verbose \
  --add-dir <repo-root> \
  --disallowedTools Edit MultiEdit NotebookEdit Write
```

- Аналитик возвращает markdown текстом; скрипт берёт `result` из stream-json и
  пишет его в `tmp/RESULT.md`. Инструменты `Edit`/`MultiEdit`/`Write`/
  `NotebookEdit` ему запрещены; `Bash` остаётся для чтения логов и запуска
  анализаторов, поэтому целостность проекта дополнительно страхуется
  инструкцией промпта и сверкой `git` до/после.
- Промпт содержит абсолютные пути к `metrics.json`, `digest.md`, диффам,
  артефактам задач, `benchmark/example.bsl` и `template/`. Какое именно
  изменённое `.bsl`-файл сопоставлять с эталоном, аналитик определяет по диффу
  и артефактам задачи; раннер имя целевого модуля не хардкодит. Если эталонного
  файла нет, сравнение с эталоном помечается как недоступное.
- В промпте зафиксированы ограничения пользователя: общие рекомендации, без
  заточки под #001/#002, без хардкода `example.bsl` в template, описания задач
  не удлиняются (при предложении — длина «до/после»), не выдавать
  пропущенные проверки за пройденные, не выполнять задачи и не менять проект.
- До и после сессии сверяются `HEAD` и `git status`; изменения — предупреждение
  в отчёте и `metrics.json`.

### Структура `tmp/RESULT.md`

1. Сводка прогона: конфигурация, лимиты, исходы, wall-clock, стоимость/токены,
   таблица «задача → лимит → факт → исход → этапы → итерации → тесты → вердикт».
2. Время выполнения: где ушло время, долгие операции, простои.
3. Итерации написания и запуска тестов: циклы, причины возвратов, лишние прогоны.
4. Итерации код-ревью: раунды, находки, возвраты.
5. Качество кода: семантическое сравнение итогового модуля с
   `benchmark/example.bsl` (совпало/упущено/отличается), находки анализаторов
   по коду и эталону, дифф-статистика.
6. Окружение template: сбои MCP/хуков/платформы, повторяющиеся ошибки,
   отсутствующие инструменты, медленные места.
7. Рекомендации: P1 «быстрые победы» и P2 «крупные изменения»; каждая —
   проблема + доказательство (метрика/лог/файл:строка), изменение, ожидаемый
   эффект, риск/трудоёмкость. Отдельно — предложения по описаниям задач
   (длина «до/после»), расширению `ЮнитТесты`, инструментам.
8. Что уже работает хорошо.
9. Приложение: пути к метрикам, дайджесту, диффам, транскриптам.

Если аналитик не вернул текст или упал, `tmp/RESULT.md` перезаписывается
детерминированной сводкой с явной ошибкой; старый отчёт не остаётся
«действительным». `--skip-analysis` пишет такую же сводку с пометкой, что
качественный анализ пропущен.

## Обработка ошибок и коды выхода

| Ситуация | Поведение |
|---|---|
| Ошибка аргументов/preflight | сообщение, код `1`, задачи не запускаются |
| Таймаут задачи | процесс группы снят, исход `timeout`, цикл остановлен, анализ выполняется |
| Ненулевой код выхода агента | исход `failed`, цикл остановлен, анализ выполняется |
| Код 0, но `task.json` не `done` | исход `incomplete`, цикл остановлен, анализ выполняется |
| Нет транскрипта сессии | дайджест по stream-json, пометка |
| Анализатор недоступен | слой помечен пропущенным |
| Аналитик упал/нет текста | `tmp/RESULT.md` — детерминированная сводка с ошибкой, код `1` |
| Аналитик изменил проект | предупреждение в отчёте; изменения не откатываются автоматически |

Коды выхода: `0` — все задачи `success` и отчёт записан; `2` — были
`timeout`/`failed`/`incomplete`, но отчёт записан; `1` — preflight,
внутренняя ошибка или аналитик не дал отчёт.

## Тестирование

`benchmark/tests/test_bench_run.py`, без реальных вызовов `claude`, 1С и сети:

- разбор `--limit` (`30`, `30м`, `2ч`, мусор, дубликаты), селекторы задач;
- обнаружение и сортировка задач, `max_minutes` из `task.json`;
- проверка свежести: артефакты, грязное дерево, не-`planned`, baseline-коммит;
- построение промпта задачи и проверка триггера `tasks/task#`;
- парсинг stream-json (init/result, битые строки, таймаут без result);
- дайджест по синтетическим JSONL: инструменты, ошибки, правки, классы команд,
  пары `tool_use`→`tool_result`, сабагенты, простои;
- классификация исходов и сборка `metrics.json` из фикстур `task.json`/логов;
- таймаут-раннер на быстром `sleep`-процессе (убийство process group);
- статические анализаторы на фейковых скриптах (вызовы, пропуски, `node`);
- промпт аналитика: наличие ограничений и путей, запрет записи;
- извлечение markdown из `result`, fallback при сбое;
- end-to-end с фейковым `--claude-cmd`: задача симулирует `task.json`,
  аналитик возвращает stream-json с markdown; проверяются `RESULT.md`,
  `metrics.json`, коды выхода и остановка после первой ошибки.

Команда: `.venv/bin/python -m pytest benchmark/tests -q`.

## Критерии приёмки

1. После `setup_benchmark.py` одна команда выполняет все задачи проекта
   последовательно, соблюдает лимиты и останавливается после первого сбоя,
   но всё равно формирует отчёт.
2. `tmp/RESULT.md` создаётся и содержит разделы 1–9; рекомендации привязаны к
   доказательствам и не заточены под конкретные задачи.
3. `tmp/benchmark/<run-id>/` содержит `metrics.json`, `digest.md`, диффы,
   транскрипты и промпт аналитика.
4. Без `--force` проект с артефактами/грязным деревом/не-`planned` задачами
   отвергается.
5. В `bench_run.py` нет хардкода имён задач, модулей и папок: задачи
   обнаруживаются, лимиты берутся из `task.json`.
6. Тесты `benchmark/tests` проходят; `benchmark/README.md` описывает запуск.

## Безопасность

Раннер запускает `claude-ds`, который по контракту лаунчера работает с
`--dangerously-skip-permissions`. Это допустимо только для доверенного
benchmark-проекта: инструмент не создаёт дополнительной изоляции (контейнер,
пользователь ОС). Запускать его на недоверенном содержимом проекта нельзя.

## Вне области

- Изменение `setup_benchmark.py`, AgentMon-сервера и `template/` в рамках этой
