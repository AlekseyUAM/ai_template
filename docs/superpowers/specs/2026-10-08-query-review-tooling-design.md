# Инструментарий ревью запросов 1С — дизайн

Дата: 2026-10-08

## Задача

Дать ревьюеру инструментарий для проверки запросов 1С на соответствие
стандартам разработки оптимальных запросов (ИТС, std729 и др.). Источник
требований — 25 PDF в `tmp/docs/Ревью запросов/`.

Два навыка в `template/.claude/skills/`:

- **`query-analyze`** — автоматический анализ. Максимальный приоритет:
  Python-скрипты, которые находят проблемы/ошибки/потенциальные проблемы в
  тексте запроса.
- **`query-review`** — чеклист код-ревью. То, что скриптом проверить нельзя
  (нужны метаданные, индексы БД, семантика задачи), выписывается требованием.

## Контекст

- Существующие навыки: `SKILL.md` с frontmatter (`name`, `description`,
  `allowed-tools`) + `scripts/*.py`. Конвенция скриптов: argparse с
  PS-стилем флагов (`-Path`), `sys.stdout.reconfigure("utf-8")`.
- Навыки/правила регистрируются в `app/tests/env/test_content_files.py`
  (множества `SKILLS`, `RULES`). Новые навыки надо добавить в `SKILLS`.
- Извлечение текста запроса из `.bsl` уже реализовано в соседнем проекте
  `query_console_vscode` (`src/cli/extractQueries.ts`,
  `src/extension/queryAtCursor.ts`): скан строковых литералов с учётом
  экранирования `""`, продолжений `|`, пропуска комментариев `//` и дат
  `'…'`, фильтр по стартовому ключевому слову ВЫБРАТЬ/УНИЧТОЖИТЬ; для СКД —
  блоки `<query>…</query>` с декодированием XML-сущностей. Этот алгоритм
  портируется на Python дословно (≈130 строк), с зеркалированием тестов
  `test/unit/extractQueries.test.ts`.
- Полный SDBL-парсер в том же проекте (`sdblParser.ts`, 5108 строк) НЕ
  портируется — шаблон должен быть самодостаточным, без зависимости от
  соседнего репозитория и без тяжёлого порта. Анализ строится на
  эвристиках по тексту запроса.

## Архитектура

### Навык A: `query-analyze`

```
template/.claude/skills/query-analyze/
  SKILL.md
  scripts/
    extract_queries.py   # .bsl/каталог (+ опц. СКД-XML) → тексты запросов (файл:строка)
    analyze_query.py      # текст запроса (файл/stdin) → находки
    rules.py              # реестр проверок: одна функция = одна проверка, с std-кодом
    tests/
      test_extract.py     # зеркало extractQueries.test.ts
      test_rules.py       # по тесту на каждое правило
```

**`extract_queries.py`** — порт `extractQueryStrings` + `extractQueriesFromXml`.
Вход: путь к `.bsl`-файлу или каталогу (рекурсивный обход), флаг для СКД-XML.
Выход: для каждого найденного запроса — текст + `путь:строка` начала литерала.
По умолчанию печатает список запросов с разделителями; флаг для выгрузки
каждого запроса в отдельный файл.

**`analyze_query.py`** — движок анализа. Вход: текст запроса (позиционный файл
или stdin). Прогоняет все правила из `rules.py`, печатает находки в формате:
`severity | std-код | строка | сообщение`. Severity: `error` / `warning` /
`info`. Код возврата ≠ 0, если есть находки уровня error (настраивается
флагом). Флаг `-Detailed` — показывать и пройденные проверки.

**`rules.py`** — реестр. Каждая проверка:
```python
@rule(code="std729", severity="warning", title="...")
def check_select_star(ctx) -> list[Finding]: ...
```
`ctx` — нормализованный текст запроса + вспомогательные представления
(строки, регистронезависимый поиск ключевых слов, разбиение на пакеты по `;`).
Правила добавляются инкрементально по мере разбора PDF.

### Навык B: `query-review`

```
template/.claude/skills/query-review/
  SKILL.md   # чеклист требований, которые проверяются глазами
```

Каждый пункт: std-код, формулировка требования, что именно смотреть
(поля/индексы/метаданные/контекст задачи), почему не автоматизируется.

### Поток работы ревьюера

`.bsl` → `extract_queries.py` → `analyze_query.py` (автопроверки) → сверка по
чеклисту `query-review`.

## Разбор PDF и отчёты

Инкрементально, по одному PDF (не спеша, малыми частями). Для каждого:

1. `pdftotext -enc UTF-8` → извлечь требования стандарта.
2. Классифицировать каждое требование:
   - **автоматизируемо** → правило в `rules.py` (+ тест в `test_rules.py`);
   - **не автоматизируемо** → пункт в `query-review/SKILL.md`.
3. Отчёт `tmp/docs/Ревью запросов/Done/{Имя файла}.md`:
   - выводы из стандарта;
   - добавленные автопроверки (правило + std-код);
   - добавленные пункты чеклиста;
   - что осознанно НЕ автоматизировано и почему.

Порядок: от базовых к частным (Общие требования → Оформление текстов →
ВЫБРАТЬ * → ПОДОБНО → ОБЪЕДИНИТЬ → ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ → …).

## Тестирование

- pytest на извлечение (кейсы из `extractQueries.test.ts`: экранирование,
  `|`-продолжения, комментарии, даты, фильтр ключевого слова, СКД-XML).
- pytest на каждое правило: позитивный и негативный кейс.
- Регистрация навыков в `app/tests/env/test_content_files.py` → `SKILLS`.

## Границы (YAGNI)

- Не делаем интеграцию с метаданными/индексами БД в автоскриптах — это зона
  чеклиста `query-review`.

## ПЕРЕСМОТР (2026-10-08): AST вместо регэкспов

После разбора первых 7 стандартов стало ясно: регэксп-эвристики по сырому тексту
дают ложные срабатывания почти в каждом структурном правиле (псевдонимы полей vs
источников, `+` в несвязанном условии, `[` под СПЕЦСИМВОЛ и т.п.). Разворот:

- **Боевой SDBL-парсер.** В `query_console_vscode` (`src/core/query/sdblParser.ts`)
  есть `parseBatch(text)` → структурная модель (таблицы с псевдонимами, соединения
  с видом inner/left/full, условия с оператором ПОДОБНО, union с флагом `distinct`,
  тип запроса, порядок, итоги). Протестирован на большом корпусе. Метаданные не
  нужны (resolver опционален).
- **Вендоринг.** Парсер собирается esbuild в один автономный JS
  `query-analyze/scripts/vendor/sdbl_parse.js` (≈420 КБ, без `npm install`),
  коммитится в шаблон. `scripts/vendor/build-parser.sh` пересобирает его из
  `query_console_vscode`. Рантайм-зависимость — только `node` (уже нужен навыку
  `web-test`; кросс-платформенно).
- **Гибрид.** `QueryContext` получает ленивое `.model` (разбор через `node`,
  кеш). **Структурные** правила (std729 select*/many-joins, std758 псевдонимы,
  std434 объединить, std726 подобно, std412 автоупорядочивание, и дальнейшие про
  соединения/ВТ/виртуальные таблицы) — по модели. **Форматные** (std437 регистр
  ключевых слов, запрос в одну строку) остаются текстовыми — AST нормализует
  оформление.
- **Graceful fallback.** Если `node`/бандла нет или разбор упал — анализатор не
  падает: гонит текстовые правила, а AST-правила помечает как пропущенные (не
  молча).
- Извлечение (`extract_queries.py`) остаётся Python-портом — оно и было
  «прекрасно реализовано» в исходнике; переделывать не нужно.
