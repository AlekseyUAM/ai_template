# Дизайн: красный смоук и продолжение агентов по результатам task##002

**Дата:** 2026-11-13
**Статус:** на ревью
**Источник:** прогон `test2/tasks/task##002` (13:47–14:53), артефакты `TESTING.1–6.md`,
`REVIEW.1.md`, `task.json`.

## 1. Контекст

Прогон task##002 дал 7 итераций `testing`: 6 красных и одна зелёная, затем ревью
вернуло задачу на доработку. Лимит 60 минут был превышен. Красные итерации:

- TESTING.1 — ошибка компиляции тест-модуля (`ДобавитьКДате`);
- TESTING.2–4 — дефекты кода (`Новый()`, `ДополнительныеСвойства`, соединение
  с объектом в запросе к ТЧ);
- TESTING.5 — смешанный дефект: чтение сальдо оборотов в тесте и очистка движений
  через `Прочитать()`/`Записать()` в коде;
- TESTING.6 — тест читал `СтоимостьРасход` и получал 0.

При этом `ARCHITECT.md` уже содержал предупреждения Р2 и Р4, которые разработчик
проигнорировал, а тест 4 был построен только на сравнении оборотов — на пустом коде
он, вероятно, был бы зелёным.

Отдельная находка: `РегистрНакопления.Товары` — регистр **остатков**
(`RegisterType = Balance`). Код `РасходнаяНакладная` пишет расход отрицательными
ресурсами без `ВидДвижения`, поэтому `Товары.Обороты.СтоимостьРасход` остаётся
пустым. Тест, который это проверял, был переписан на чтение записей с
`Количество < 0` — то есть подстроен под дефект. Ревью этого не поймало.

## 2. Цель и критерии успеха

**Цель:** сократить число тестовых циклов до `develop`, не отдавая субагентам
тяжёлые операции с тестовой базой, переиспользовать контекст агента при возвратах
на тот же этап и закрыть правило о виде регистра/знаке движений.

**Критерии успеха (на следующем реальном прогоне, без benchmark):**

- ошибки компиляции/setup в тест-модуле и зелёные тесты до реализации не доходят
  до этапа `testing`;
- автор тестов получает дефект смоука через SendMessage и чинит только тест-модуль;
- разработчик и автор тестов продолжаются через SendMessage при возврате на тот же
  этап, с fallback на нового агента;
- ревью возвращает этап(ы) по принадлежности находки, а не всегда `testing`;
- `pytest app/tests` проходит.

Смоук добавляет к задаче не более ~2 минут.

## 4. Решение 1. Правило движений в регистре остатков

Файл: `template/.claude/skills/bsl-coding-standards/reference/accumulation-registers.md`.

В разделе «Заполнение движений» заменить неявные пункты на явное правило:

- **[критичная] Регистр «Остатки»:** `ВидДвижения` заполняется (`Приход`/`Расход`),
  ресурсы пишутся **положительными**. Отрицательный ресурс в регистре остатков —
  ошибка модели: `Обороты.<Ресурс>Расход` останется пустым, баланс сойдётся
  арифметически, но разрезы «Приход/Расход» и отчёты по ним будут неверными.
- **Регистр «Обороты»:** `ВидДвижения` нет, расход пишется минусом.
- Пример для регистра остатков:

  ```bsl
  Движение.ВидДвижения = ВидДвиженияНакопления.Расход;
  Движение.Количество = КоличествоВПартии;
  Движение.Стоимость = СтоимостьПартии;
  ```

В «Типичные ошибки (сигналы для ревью)» добавить:
`[критичная] Отрицательные ресурсы в регистре вида «Остатки» вместо
ВидДвижения = Расход`.

В «Чек-лист проведения» заменить пункт про `AllowedSign` на составной:
`[ ] Для регистра «Остатки» заполнен ВидДвижения и ресурсы неотрицательны;
для «Обороты» — знак ресурса соответствует направлению; AllowedSign соответствует
знаку движений.`

Промпты архитектора и ревьюера уже ссылаются на этот файл — отдельных правок
в них не требуется. `movements-deletion.md` не трогаем.

## 5. Решение 2. Красный смоук после этапа `tests`

Смоук — часть завершения этапа `tests`, до `develop`. Новой стадии нет.

### 5.1. Порядок

1. Автор тестов записал `TESTS.md` и `configs/task#<id>/test.json`; этап `tests`
   остаётся `running`.
2. Оркестратор в фоне загружает расширение и запускает набор:

   ```bash
   python .claude/skills/1c-batch/scripts/1c-batch.py load-extension \
       src/cfe/ЮнитТесты --name ЮнитТесты \
       > logs/task#<id>/load-extension-tests.log 2>&1

   python .claude/tools/run-tests.py configs/task#<id>/test.json --timeout 120 \
       > logs/task#<id>/run-tests-smoke.log 2>&1
   ```

   Полный набор, а не один сценарий: прогон занимает ~55 секунд, а `--test`
   оставляем для отладки.
3. Оркестратор просыпается по завершении процесса, читает лог и `result.json`
   (`ИмяФайлаЛог` из конфига).
4. Критерии прохождения:

   | Проверка | Требование |
   | --- | --- |
   | Код возврата | `0`; `1`/`3` — ошибка среды, цикл не гоняем; `124` — зависание теста |
   | `result.json` | `Выполнено = true`, `ОписаниеОшибки = null` |
   | Зелёные тесты | Ни одного `Результат = true` до реализации |
   | Красные тесты | Падение по утверждению (expected/actual) или по ожидаемому отсутствию ещё не написанной функциональности |
   | Setup/компиляция | Нет ошибок компиляции тест-модуля и setup-исключений, не относящихся к проверяемой функциональности |

   Если причина красного неочевидна, оркестратор не угадывает: он отправляет лог
   автору тестов и просит подтвердить причину.
5. При дефекте теста — SendMessage автору (см. решение 3). Автор чинит тест-модуль,
   не ослабляя проверку, и сообщает о готовности. Оркестратор повторяет смоук.
   Максимум 2–3 цикла «смоук → правка → смоук».
6. Смоук прошёл → `task_status.py ... tests done --files <изменённые>`, дальше
   `develop`.
7. Смоук не прошёл после лимита → `tests` помечается `failed`, задача
   останавливается; лог сохраняется.

### 5.2. Особые случаи

- **Ошибка компиляции в `ЮнитТесты`** — дефект теста, SendMessage автору.
- **Ошибка компиляции в `src/cf`** — дефект baseline; тест-модуль не виноват.
  Зафиксировать лог, закрыть `tests` и передать лог разработчику на `develop`;
  после `develop` смоук повторится в рамках `testing`.
- **Ошибка среды (`1`/`3`)** — не вина теста; зафиксировать и остановиться,
  не гонять цикл.
- **Зелёный тест до реализации** — дефект теста: он проверяет не новое поведение.
  Это, в частности, случай теста 4 из task##002, который сравнивал только
  неизменность оборотов.

### 5.3. Роль автора тестов

В `developer-tests.md`:

- сохранить запрет «сам прогон не запускай» — смоук запускает оркестратор;
- добавить: лог смоука приходит через SendMessage; при дефекте теста автор правит
  тест-модуль и сообщает о готовности к повторному смоуку;
- добавить критерии смоука из 5.1, чтобы автор понимал, что именно проверит
  оркестратор;
- сохранить правило «не ослабляй проверки и не подстраивай ожидания под
  фактическую реализацию».

## 6. Решение 3. SendMessage для возвратов на тот же этап

Файл: `template/.claude/skills/task-orchestration/SKILL.md`, новый раздел
«Продолжение субагента (SendMessage)».

### 6.1. Механизм

- После запуска субагента оркестратор сохраняет идентификатор в
  `logs/task#<id>/agents.json`:

  ```json
  {
    "tests": {"agent_id": "<id>", "iteration": 1},
    "develop": {"agent_id": "<id>", "iteration": 1}
  }
  ```

  Если инструмент не вернул идентификатор — пишется `null`.
- При возврате на тот же этап (`tests` из смоука/`testing`, `develop` из
  `testing`/`review`) оркестратор читает файл и продолжает агента через
  SendMessage с коротким re-brief:

  > Ты продолжаешь этап `<этап>` (итерация `<n>`). Перед правкой прочитай текущие
  > `<артефакт>` (путь), `TESTING.md`/`REVIEW.md` (путь) и лог (путь). Вердикт:
  > `<вердикт>`. Твоя зона: `<зона>`. Не меняй `<ограничения>`. Верни краткий
  > отчёт: что прочитал, что изменил, какие проверки выполнил.

- После возврата агента оркестратор проверяет, что артефакт изменился и отчёт
  соответствует задаче; иначе — fallback.
- SendMessage применяется только к тому же этапу и тому же артефакту. Смену роли
  (tests → develop) он не выполняет.
- Статусы этапов, артефакты, архивирование и вердикты остаются за оркестратором;
  меняется только способ делегирования.

### 6.2. Fallback и ограничения

- Новый агент запускается, если: идентификатора нет; SendMessage недоступен;
  агент не резюмировался; две попытки подряд на одном дефекте не дали результата.
- После двух неудач продолжение прекращается — защита от «защиты своего
  артефакта».
- При переименовании артефактов (`TESTS.md` → `TESTS.<n>.md`) в re-brief
  передаются точные текущие пути.

### 6.3. Промпты агентов

- `developer-tests.md`: при возврате агент может быть продолжен; перед правкой
  перечитать `TESTS.md`, лог смоука и `TESTING.md`.
- `developer.md` (раздел «Разбор возврата на доработку»): при возврате агент может
  быть продолжен; перед правкой перечитать `DEVELOP.md`, `TESTING.md`/`REVIEW.md`
  и лог; вердикт оркестратора авторитетен.

### 6.4. Влияние на отлаженную оркестрацию

Контракт этапов не меняется: `task.json`, порядок этапов, артефакты, вердикты,
архивирование — те же. Меняется только lifecycle субагента. Риски:

| Риск | Митигация |
| --- | --- |
| Устаревший контекст агента | re-brief + обязательное перечитывание текущих файлов и лога |
| Защита своего артефакта | вердикт оркестратора авторитетен; после 2 неудач — новый агент |
| Потеря идентификатора после компакции | `logs/task#<id>/agents.json` |
| Переименование артефактов | точные текущие пути в re-brief |
| Нет SendMessage в рантайме | fallback на нового агента, оркестрация не блокируется |

Откат — удалить раздел 6 из `task-orchestration.md` и вернуться к новому агенту
на каждый возврат.

## 7. Решение 4. Возврат из review по принадлежности находки

Файл: `template/.claude/rules/cyclic-review-workflow.md`, раздел 2.

Сейчас при вердикте «✗ НА ДОРАБОТКУ» правило возвращает `testing`, если он включён.
Это не соответствует практике: в task##002 оркестратор фактически вернул
`develop` и `tests`. Заменить на:

- находки по коду (`src/cf`, `src/cfe` кроме тест-модуля) → `develop`;
- находки по тестам (`src/cfe/ЮнитТесты`, `TESTS.md`) → `tests`;
- находки и по коду, и по тестам → вернуть оба этапа;
- принадлежность неоднозначна → вернуть `develop` и `tests`, чтобы не потерять
  тестовую правку.

Порядок выполнения возвращённых этапов: `tests → develop → testing → review`.
Для каждого возвращённого этапа архивировать его артефакт
(`REVIEW.md` → `REVIEW.<n>.md`, `DEVELOP.md` → `DEVELOP.<n>.md` и т.д.) и перевести
в `pending`; `iteration` инкрементируется автоматически. Если `iteration` любого
возвращаемого этапа ≥ 10 — пометить его `failed` и остановиться.

Это единственная правка протокола; смешанный виновник в `TESTING.md` и логика
определения виновника не меняются.

## 9. Поток выполнения

1. `tests`: автор пишет тесты и конфиг; оркестратор сохраняет `agent_id`.
2. Оркестратор запускает смоук. Дефект теста → SendMessage автору → правка →
   повторный смоук (до 2–3 раз). Успех → `tests done`.
3. `develop`: разработчик пишет код; оркестратор сохраняет `agent_id`.
4. `testing`: полный прогон. Виновник код → архив `DEVELOP.md`, возврат `develop`,
   SendMessage разработчику. Виновник тест → архив `TESTS.md`, возврат `tests`,
   SendMessage автору, затем смоук и повторный `testing`.
5. `review`: находки → `develop`/`tests`/оба по принадлежности; архив артефактов;
   SendMessage соответствующему агенту (`tests`/`develop`); после исправлений
   `testing → review`.

## 10. Обработка ошибок

- Смоук: коды `0/1/2/3/124` различаются до чтения `result.json`; ошибка среды не
  превращается в дефект теста.
- SendMessage: любая ошибка/недоступность → новый агент; оркестрация не падает.
- Review: неоднозначная принадлежность → возврат `develop` + `tests`.
- Автор тестов не отвечает/не резюмируется → новый агент с логом смоука.

## 11. Проверка

- `pytest app/tests` — весь набор, включая `app/tests/env`.
- Ручная проверка изменённых промптов на противоречия с существующими правилами
  (`task-orchestration`, `cyclic-review-workflow`, `run-unit-tests`).
- Проверить в рантайме, что Agent/SendMessage доступны и возвращают идентификатор;
  если нет — зафиксировать деградацию до нового агента.
- На следующем реальном прогоне зафиксировать: результат смоука, использование
  SendMessage/fallback, число итераций `testing`, этап(ы) возврата из review.
  Benchmark-прогон в рамках этой работы не запускается.

## 12. Риски и откат

| Риск | Влияние | Митигация/откат |
| --- | --- | --- |
| SendMessage даёт устаревший контекст | агент правит не то | re-brief + перечитывание; после 2 неудач — новый агент |
| SendMessage защищает свой артефакт | дефект не исправляется | вердикт авторитетен; новый агент после 2 неудач |
| Смоук не поднимает тестовую базу | этап блокируется | ошибка среды фиксируется, цикл не гоняется; эскалация |
| Смоук добавляет время | +1–2 минуты | полный набор ~55 с; оправдано снятым циклом |
| Правило меняет модель движений в будущих задачах | тесты, читающие записи, должны ждать положительные ресурсы и `ВидДвижения` | это целевое исправление; ожидания в новых тестах — по правилу |
| Правка review-возврата меняет привычный цикл | оркестратор может вернуть два этапа | порядок `tests → develop → testing → review`; лимит итераций |

## 13. Открытые вопросы

- Доступны ли в развёрнутом рантайме Agent/SendMessage и идентификатор агента.
  Если нет — механизм деградирует до текущего поведения без блокировки.
- Полный набор или один сценарий на смоуке: по умолчанию полный; `--test`
  остаётся для отладки.
- Если принадлежность находки ревью неочевидна, возврат `develop` + `tests` может
  добавить лишнюю работу; альтернатива — возврат только `develop` и передача
  тестовой части разработчику. Выбран безопасный вариант.
- Чисто дизайнерские находки (без правки кода/тестов) этап не возвращают: они
  фиксируются в `REVIEW.md` как вопрос. Если потребуется правка `ARCHITECT.md`,
  это отдельное решение за рамками данной работы.
