## 1. Контекст и корневые причины

1. **Логи прогона тестов.** `run-tests.py` не печатает результаты и даже при
   упавших тестах возвращает `0`; в конце пишет «Результаты смотри там, куда их
   пишет обработчик тестов». Старый `result.json` перед прогоном не удаляется,
   поэтому при ошибке компиляции (`EXIT=2`) выводится результат **прошлого**
   прогона (наблюдалось 14:52:09 UTC). Дополнительно `task-orchestration`
   и `developer.md` упоминают несуществующее поле `ЗаписиЖР`, которого в
   `result.json` нет (это оговорено в `developer-tests.md`).
2. **Пре-флайт перед загрузкой в ИБ.** `task-orchestration` требует от
   оркестратора «убедись, что `DEVELOP.md` на месте, метаданные валидны,
   статический анализ чист». Это заставляет его повторять работу разработчика и
   ревьюера и читать модули (в транскрипте — «Проверяю состояние перед загрузкой
   в ИБ: границы изменений, DEVELOP.md, статанализ»).
3. **Программная сборка запроса.** Разработчик собрал текст запроса с заглушкой
   `!НАПРАВЛЕНИЕСОРТИРОВКИ!` и подставил направление через `СтрЗаменить`.
   Исходный литерал не проходит `validate_query`; ревьюер проверил вариант
   **после** подстановки и признал пункт `query-review` выполненным. Правило
   допускало такое прочтение: «осевой текст» не был определён однозначно.
   `developer.md` пересказывал правило, но не обязывал вызвать `query-analyze`
   и проверить литерал как записан.
4. **Устаревший `read_file` из code_index.** Штатное обновление индекса —
   debounce 1.5 с + batch 2 с. Но в `daemon.toml`, который генерирует
   `_daemon_toml()`, нет секции `[[cache_targets]]`, поэтому `serve` не получает
   `/mark-dirty` и `/invalidate`; встроенный кэш результатов (TTL 3600 с) может
   отдавать старое содержимое до часа. Наблюдалось: `stat_file` показывает
   267 строк / 16 109 байт, а `read_file` — 3 байта (пустой модуль с BOM).

## 2. Цель и критерии успеха

- `developer-tests` сам доводит тест-модуль до корректного красного смоука;
  оркестратор не тратит итерации на setup-дефекты тестов.
- Оркестратор перед загрузкой в ИБ не повторяет статанализ и валидацию
  метаданных — только проверяет артефакт и состав изменённых файлов.
- Любой литерал запроса, не проходящий `validate_query` в том виде, как он
  записан в исходнике, — блокирующая находка (`warning`/`важная`), независимо от
  того, проходит ли вариант после подстановки.
- `read_file` из code_index после правки отдаёт свежее содержимое в пределах
  нескольких секунд; агенты знают признак протухания и умеют обойти.
- `pytest app/tests` проходит.

## 4. Решение A. Смоук и отладочные прогоны — у `developer-tests`

### A.1. `template/.claude/agents/developer-tests.md`

Добавить раздел «Запуск тестов (Red) — выполняешь сам» и убрать действующий
запрет «сам прогон не запускай».

1. После записи `TESTS.md` и `configs/task#<id>/test.json` загрузи расширение и
   прогони **полный** набор:

   ```bash
   python .claude/skills/1c-batch/scripts/1c-batch.py load-extension \
       src/cfe/ЮнитТесты --name ЮнитТесты \
       > logs/task#<id>/load-extension-tests.log 2>&1
   python .claude/tools/run-tests.py configs/task#<id>/test.json --timeout 120 \
       > logs/task#<id>/run-tests-smoke.log 2>&1
   rc=$?; echo "EXIT=$rc" >> logs/task#<id>/run-tests-smoke.log
   tail -80 logs/task#<id>/run-tests-smoke.log
   ```

   У вызова Bash задавай таймаут не меньше 300 000 мс. Команды выполняются
   последовательно в одном проекте; параллельно с этапом `testing` (полный
   прогон оркестратора) тесты не запускаются.

2. Для локализации дефекта — `--test <ИмяСценария>` (один или несколько через
   запятую, короткий `--timeout 60–120`), с логом в отдельный файл
   `logs/task#<id>/run-tests-debug.log`. Итоговое доказательство смоука — только
   **последний полный** прогон в `run-tests-smoke.log`, не `--test`: отладочный
   прогон перезаписывает `result.json` подмножеством, поэтому после отладки
   полный набор запускается заново последним.

3. Критерии смоука (те же, что были у оркестратора):
   - компиляция расширения без ошибок, setup-исключений нет;
   - ни один тест не зелёный до реализации;
   - красные падают по утверждению (expected/actual) или ожидаемому отсутствию
     функциональности;
   - проверяемый вызов не обёрнут в `Попытка` (кроме сценария ожидаемого отказа);
   - тест, сравнивающий состояние до/после («не изменилось»), до реализации
     зелёный быть не может — усилить.

4. Если смоук нашёл собственный дефект теста — чини тест-модуль и повторяй сам;
   оркестратору не нужно слать лог. Лимиты итераций — прежние (2–3 цикла).

5. В `TESTS.md` добавь секцию «Смоук»: дата/время, пути
   `load-extension-tests.log` и `run-tests-smoke.log`, `EXIT`, итог
   (`Выполнено`, `ОписаниеОшибки`, все `Результат=false`), **общее число
   сценариев полного набора**, подтверждение, что красные падают по утверждению.

6. При возврате на `tests` из `testing`/`review`: сначала `--test` по упавшим
   сценариям, после правки — полный набор и обновление секции «Смоук». Сам прогон
   `testing` по-прежнему не твой — его делает оркестратор.

## 5. Решение B. `run-tests.py`: очевидные логи и коды результата

Файл: `template/.claude/tools/run-tests.py`.

1. **До прогона.** Прочитать `ИмяФайлаЛог` из эффективного конфига (в т.ч. при
   `--test`). Если файл существует — удалить его. Напечатать:
   `📄 Результат будет записан в: <абсолютный путь>`.
2. **После прогона.** Если предприятие завершилось с `rc != 0` — вернуть этот
   код как раньше, сводку не печатать. Если `rc == 0` — прочитать `result.json`
   (`utf-8-sig`) и напечатать сводку:
   - `Выполнено`, `ОписаниеОшибки`;
   - по каждому тесту `✓/✗ <Имя>` и `ОписаниеОшибки` для упавших;
   - `ИТОГ: N/M пройдено`.
3. **Коды возврата** (новые константы):
   - `0` — результат свежий и валиден, `Выполнено=true`, `ОписаниеОшибки=null`,
     список тестов непустой, все тесты `Результат=true`;
   - `4` — результат свежий, но есть проваленные тесты/`Выполнено=false`/
     `ОписаниеОшибки≠null`. На смоуке это **ожидаемый** код (все красные);
   - `5` — после успешного завершения предприятия файла результата нет, он
     невалиден или список тестов пуст;
   - `1/2/3/124` — без изменений.
4. Строку «Результаты смотри там, куда их пишет обработчик» удалить.
5. Обновить docstring с кодами и примером.

## 6. Решение C. Валидация запросов

### C.1. Общее правило (дословно для обоих скиллов)

> `validate_query` применяется к тексту запроса **ровно в том виде, как он записан
> в исходнике**: литерал целиком, каждая часть конкатенации. Подстановка
> допускается только в места, где исходный текст остаётся валидным запросом:
> параметры вида `&ОсобыйПараметр` и нейтральные подстроки `1 = 1`, `2 = 2` и
> т.п.; в коде — `СтрЗаменить(ТекстЗапроса, "&ОсобыйПараметр", "<фрагмент>")`.
> Произвольные заглушки (`!НАПРАВЛЕНИЕСОРТИРОВКИ!`, `%1`, `{0}`) запрещены:
> текст с ними не проходит `validate_query` и не открывается конструктором.
> Проверка варианта после подстановки не заменяет проверку исходного литерала.
> Если направление/режим нельзя выразить параметром — использовать два
> статических текста.

## 7. Решение D. code_index: инвалидация кэша и признаки протухания

### D.1. Генератор `daemon.toml`

Файлы: `app/src/agentmon/env/mcp_docker_recipes.py`,
`app/src/agentmon/env/code_index_local.py`.

- `_daemon_toml(alias, path, cache_target_url=None)`: при заданном URL добавлять
  секцию

  ```toml
  [[cache_targets]]
  url = "http://127.0.0.1:<port>"
  ```

- `launch_params()` (docker) передаёт `http://127.0.0.1:{port}` (serve слушает
  `0.0.0.0:<port>` в том же контейнере).
- `deploy_local()` передаёт `http://127.0.0.1:{port}` (host/127.0.0.1).
- Без URL секция не генерируется (для тестовых вызовов и обратной совместимости).

### D.2. Тесты

- `test_mcp_docker_recipes.py`: `launch_params(... port=8004 ...)` →
  в `daemon.toml` есть `[[cache_targets]]` и `url = "http://127.0.0.1:8004"`;
  `_daemon_toml` без URL секции не содержит.
- `test_code_index_local.py`: после `deploy_local(port=8005)` в `daemon.toml`
  есть `url = "http://127.0.0.1:8005"`.

### D.3. `template/.claude/skills/mcp-usage/SKILL.md`

В раздел `code_index` добавить:

- штатное обновление индекса после сохранения файла — ~2–5 с (debounce 1.5 с +
  batch 2 с); во время переиндексации инструмент может вернуть
  `{"status":"indexing"}` — повторить через пару секунд;
- признак протухшего `read_file`: содержимое не сходится по `file_size`/
  `lines_total` со `stat_file`, либо выглядит как прошлая версия. Тогда
  использовать `get_file_summary`/`get_function` (структурированные данные
  индекса) и не делать вывод «модуль пуст»; если расхождение держится больше
  минуты — сообщить об ошибке окружения (кэш `serve` не инвалидируется);
- после правки деплоя `[[cache_targets]]` `read_file` должен обновляться в
  пределах секунд.

## 12. Уточнение после финального ревью (2026-11-14)

Финальное ревью нашло дыру в смоуке: если `load-extension` падал, его код
возврата терялся, и `run-tests.py` мог прогнать **старое** расширение, выдав
правдоподобный `EXIT=4`. Итоговые правила (они же в реализации):

- смоук-команда фиксирует `LOAD_EXIT` и запускает прогон только при `LOAD_EXIT=0`;
  иначе в `run-tests-smoke.log` пишется `EXIT=load-failed`;
- оркестратор проверяет, что `load-extension-tests.log` заканчивается
  `LOAD_EXIT=0` и его mtime не старше тест-модуля;
- `--test` помечается в выводе `run-tests.py` как отладочный прогон, а не
  доказательство смоука;
- таймаут смоука — `300` c.

```bash
python .claude/skills/1c-batch/scripts/1c-batch.py load-extension \
    src/cfe/ЮнитТесты --name ЮнитТесты \
    > logs/task#<id>/load-extension-tests.log 2>&1
load_rc=$?; echo "LOAD_EXIT=$load_rc" >> logs/task#<id>/load-extension-tests.log
if [ "$load_rc" -eq 0 ]; then
    python .claude/tools/run-tests.py configs/task#<id>/test.json --timeout 300 \
        > logs/task#<id>/run-tests-smoke.log 2>&1
    rc=$?; echo "EXIT=$rc" >> logs/task#<id>/run-tests-smoke.log
else
    echo "EXIT=load-failed" >> logs/task#<id>/run-tests-smoke.log
fi
tail -80 logs/task#<id>/load-extension-tests.log logs/task#<id>/run-tests-smoke.log
```
