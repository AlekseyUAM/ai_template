# Telegram-интеграция AgentMon — дизайн

Дата: 2026-10-17

## Цель

Дать управление и наблюдение за агентскими сессиями из Telegram:

1. **Уведомления о статусах задач** — старт/финиш задачи, выход на гейт
   «ожидает пользователя», события стека.
2. **Управление стеком** — запуск, продолжение, остановка.
3. **Просмотр отчётов и внесение замечаний** — чтение артефактов этапов
   (аналитика, план, тесты, реализация, ревью) и текстовые замечания,
   которые агент учтёт на следующей итерации.

## Решённые вопросы (вводные)

- «Внесение изменений» = **текстовые замечания** к этапу, не перезапись
  файлов артефактов. Агент учитывает их на следующей итерации (цикл
  develop→review). Файлы артефактов бот сам не редактирует.
- Авторизация = **allowlist `chat_id`** в конфиге. Чужие чаты игнорируются.
- Доставка апдейтов = **long-polling** в том же процессе FastAPI (работает
  из-за NAT, без публичного HTTPS).
- Уведомления = **старт/финиш задачи + гейт «ожидает пользователя» +
  события стека**. Переходы между этапами НЕ уведомляются (чтобы не шуметь).
- Кнопка «Замечание» на гейте = **зафиксировать замечание + одобрить гейт**
  (MVP). Агент идёт дальше и учитывает замечание на ближайшем этапе.

## Контекст существующей архитектуры

- FastAPI-приложение с фоновым `dispatch_loop()` в lifespan: тикает
  `Dispatcher.tick()` и `StackDispatcher.tick()` каждые `DISPATCH_INTERVAL`
  (3 с). Естественная точка, где статусы меняются.
- Статусы задачи: `planned`, `queued`, `running`, `stopped`,
  `awaiting_user` (ожидает пользователя), `done`, `failed`. Статус
  `awaiting_user` вычисляет `overall_status()`: гейтированный `enabled`-этап
  `done` и не `approved`, и после него есть `enabled`-этап в `pending`.
  `approve` ставит `approved=True` на этапе и снимает гейт.
- Стеки: `StackRepo` со статусами `idle`/`running`; эндпоинты
  `POST /api/env/stacks/{id}/start` (`set_status(running)`) и `/stop`
  (`stop_stack`, срубает текущий прогон).
- Задача: 7 этапов (`analyze/plan/tests/develop/testing/review/docs`) с
  артефактами (`ANALYZE.md`, `ARCHITECT.md`, `TESTS.md`, `DEVELOP.md`,
  `TESTING.md`, `REVIEW.md`, `DOCS.md`). Гейты: `approved`-флаг этапа,
  эндпоинт `POST /api/env/tasks/{id}/approve`.
- Каталог задачи: `<project.path>/tasks/task#<identifier|id>/`; имя через
  `task_folder_name(id, identifier)`. Артефакты уже читаются в `open-report`.
- Цикл review ведёт оркестратор по вердиктам в артефактах
  (`REVIEW.md` → «✓ ПРИНЯТО»/«✗ НА ДОРАБОТКУ»). Пользовательских замечаний
  в текущей схеме нет — их нужно добавить.
- Конфиг — через переменные окружения (`config.py`), секреты в `.ai1c.env`.
- Зависимости приложения: `fastapi`, `uvicorn[standard]`, `paramiko`,
  `psycopg[binary]`. `httpx` сейчас только в dev.

## Выбранные подходы

- **Библиотека бота:** тонкий клиент на `httpx` поверх Bot API (без
  фреймворка). Нужны лишь `getUpdates`, `sendMessage`,
  `answerCallbackQuery`, inline-клавиатуры. `httpx` переносится в runtime-
  зависимости. Причина: минимум зависимостей, полный контроль, тестируемость
  фейковым транспортом — в духе самодостаточности проекта.
- **Ловля смены статусов:** отдельный поллер-диффер `TelegramNotifier.tick()`,
  сравнивающий текущие статусы с «уже уведомлёнными» (таблица
  `tg_notify_state`). Не трогает точки мутации, переживает рестарт без
  повторного спама — по аналогии с reconcile/diff приложения.

## Структура модуля

Новый пакет `app/src/agentmon/telegram/`, полностью опциональный: если
`AGENTMON_TG_TOKEN` не задан — фича выключена, нулевое влияние на остальное.

- `client.py` — тонкий async-клиент Bot API на `httpx`: `get_updates(offset,
  timeout)`, `send_message(chat_id, text, reply_markup=None)`,
  `answer_callback(callback_id, text=None)`; хелперы сборки inline-клавиатур.
  HTTP-транспорт инъектируемый → тесты без сети.
- `bot.py` — `TelegramBot`: long-poll цикл (тянет апдейты по `offset`),
  проверка `chat_id` по allowlist, роутинг команд и callback-кнопок в
  хендлеры. Устойчивость к ошибкам по образцу `dispatch_loop` (catch-all,
  дедуп повторяющихся ошибок, бэкофф на сетевых сбоях).
- `handlers.py` — обработчики команд/коллбэков; вызывают существующие
  репозитории (`StackRepo`, `TaskRepo`, `ProjectRepo`), без дублирования
  логики.
- `reports.py` — чтение артефактов этапов (через `task_folder_name` и модель
  этапов `DEFAULT_STAGES`), нарезка текста под лимит Telegram (4096 символов),
  экранирование.
- `notifier.py` — `TelegramNotifier.tick()`: дифф статусов задач/стеков и
  отправка уведомлений.
- `feedback.py` — приём замечаний: запись в БД + зеркало в
  `tasks/task#<id>/USER_FEEDBACK.md`.
- `config.py` (расширение `agentmon/config.py`): `AGENTMON_TG_TOKEN`,
  `AGENTMON_TG_CHAT_IDS` (список `chat_id` через запятую), читаются из
  env/`.ai1c.env`.

## Интеграция в рантайм

В `__main__.py` (lifespan): если токен задан — поднимаем рядом с
`dispatch_loop`:
- (а) long-poll цикл бота отдельной asyncio-задачей;
- (б) `notifier.tick()` встраиваем в `dispatch_loop` (тот же период
  `DISPATCH_INTERVAL`), под общим обработчиком ошибок.

Нет токена → ни одна из задач не стартует.

## Схема БД (2 новые таблицы)

```sql
CREATE TABLE IF NOT EXISTS tg_notify_state (
    id <pk>,
    scope TEXT NOT NULL,          -- 'task' | 'stack'
    ref_id INTEGER NOT NULL,      -- task_id или stack_id
    last_status TEXT,             -- последнее уведомлённое состояние
    UNIQUE(scope, ref_id)
);

CREATE TABLE IF NOT EXISTS task_feedback (
    id <pk>,
    task_id INTEGER NOT NULL,
    chat_id TEXT NOT NULL,
    text TEXT NOT NULL,
    created_at DOUBLE PRECISION,
    consumed INTEGER NOT NULL DEFAULT 0
);
```

Миграция добавляется в `store/schema.py` (идемпотентно, как остальные
таблицы) и в путь миграций существующих БД.

## Уведомления (data flow)

`notifier.tick()`:
1. Читает статусы задач (`TaskRepo`) и стеков (`StackRepo`).
2. Сравнивает с `tg_notify_state`.
3. На интересующих переходах шлёт форматированное сообщение всем `chat_id`
   из allowlist:
   - **Задача**: →`running` (старт), →`done`, →`failed`, →`awaiting_user`
     (гейт «ожидает пользователя»).
   - **Стек**: →`running`, →`idle`/`stopped`, →completed (все элементы done).
4. **Первый тик после включения**: текущее состояние заносится в
   `tg_notify_state` *молча* (без сообщений по уже существующим статусам) —
   baseline.
5. `last_status` продвигается **только после успешной отправки** (чтобы не
   терять уведомление), с ограничением числа попыток, чтобы устойчивый сбой
   не спамил логи.
6. Сообщение о гейте несёт inline-кнопки **[✅ Одобрить] [✍️ Замечание]** с
   `callback_data`, включающей `task_id` и имя этапа.

## Команды и UX бота

- `/start` — приветствие, статус авторизации текущего чата.
- `/projects` — список проектов.
- `/tasks` — задачи со статусом и текущим этапом; у каждой кнопка → меню
  отчётов.
- `/stacks` — стеки со статусом и кнопками **▶️ Запустить / ▶️ Продолжить /
  ⏹ Остановить**:
  - *Запустить* и *Продолжить* → `StackRepo.set_status(running)` (тот же путь,
    что REST `start`). Выполненные элементы остаются `done`, диспетчер
    подхватывает следующий `pending` — это и есть «продолжение».
  - *Остановить* → логика `stop_stack` (срубает текущий прогон running-задачи
    стека).
- **Отчёты**: задача → меню этапов (кнопки по включённым этапам) → тап по
  этапу → присылаем содержимое артефакта (нарезка по 4096 символов) +
  кнопка «Сводка» (overall-статус).

## Замечания → агент (единственная правка со стороны `template/`)

1. Замечание из чата: запись в `task_feedback` + дозапись в
   `tasks/task#<id>/USER_FEEDBACK.md` (секция с отметкой времени и текстом).
2. Новое правило `template/.claude/rules/user-feedback.md`: субагенты и
   оркестратор перед каждым этапом читают `USER_FEEDBACK.md` (если есть) и
   отрабатывают открытые пользовательские замечания. Упоминание добавляется в
   навык `task-orchestration`.
3. Бот остаётся развязанным: он пишет замечание и отпускает гейт
   (`approve`-логика). Учитывает замечание агент через правило.
4. Кнопка «✍️ Замечание»: бот просит прислать текст ответом, затем сохраняет
   его (БД + файл) и **одобряет гейт** (MVP «зафиксировать + одобрить»). Задача
   идёт дальше, замечание учитывается на ближайшем этапе.

## Авторизация и обработка ошибок

- `chat_id` каждого апдейта сверяется с allowlist; чужой — игнорируется.
  Мутации (старт/стоп стека, approve, замечание) — только авторизованным
  чатам.
- Длинные сообщения режутся на части ≤4096 символов; Markdown экранируется.
- Сбой отправки в Telegram логируется, не фатален; нотификатор не продвигает
  `last_status` до успешной отправки (с лимитом попыток).
- `getUpdates` подтверждает обработанные апдейты через `offset`; на сетевых
  сбоях — бэкофф и повтор.

## Тестирование

Без реальной сети, фейковый транспорт/клиент, захватывающий отправленные
сообщения; in-memory store существующих фикстур:

- **Нотификатор**: сид состояния → смена статусов → ожидаемые сообщения;
  «молчим на baseline» на первом тике; продвижение `last_status` только после
  успешной отправки.
- **Хендлеры команд**: команда/коллбэк → ожидаемые вызовы репозиториев и
  ответы (`/stacks` start/continue/stop, `/tasks`, меню отчётов).
- **Авторизация**: апдейт из неразрешённого чата игнорируется; мутации
  запрещены.
- **Отчёты**: чтение артефакта, нарезка длинного текста, отсутствующий
  артефакт.
- **Замечания**: сохранение в `task_feedback` + дозапись в `USER_FEEDBACK.md`
  + одобрение гейта.
- **Клиент**: сборка запросов `getUpdates`/`sendMessage`/
  `answerCallbackQuery` и inline-клавиатур на фейковом транспорте.

## Вне scope (YAGNI)

- Перезапись файлов артефактов из Telegram.
- Webhook-доставка и публичный HTTPS/туннель.
- Многопользовательские роли/права сверх allowlist.
- Уведомления о переходах между этапами.
- Вариант «вернуть этап в pending» по замечанию (возможное расширение после
  MVP).
