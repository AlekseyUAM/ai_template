# Автономный раннер списка задач — дизайн (подсистема №4)

Дата: 2026-10-01
Статус: утверждён к реализации (автономный режим)

## Контекст

№4 даёт выбрать список задач проекта и выполнить их автономно агентами. Строится
поверх уже существующего в agentmon механизма: очередь (`queue.enqueue/list`) +
диспетчер, который сам по очереди запускает claude-сессию на каждую задачу очереди
(auto-advance). Система задач №3 уже даёт структуру `tasks/task#<id>/task.json` с
постадийными статусами и промпт оркестрации. Поэтому №4 не пишет собственный
движок прогона, а: отбирает задачи → ставит по промпту оркестрации на каждую в
очередь agentmon → показывает агрегированный статус. Рамочные решения проекта
действуют (своя реализация, кросс-платформа, без новых зависимостей, русский).

## Компоненты

### `task_run.py`

- Константы `OVERALL_PENDING/RUNNING/DONE/FAILED`.
- `task_overall_status(spec) -> str` — сводный статус задачи из её включённых этапов:
  есть `failed` → `failed`; все `done` → `done`; есть `running` → `running`; иначе
  `pending`. Нет включённых этапов → `done`.
- `select_tasks(project_dir, task_ids=None, only_runnable=True) -> list[TaskSpec]` —
  список задач проекта; при `task_ids` — только указанные; при `only_runnable` —
  исключая уже `done`.

### `task_schema.orchestration_prompt(task_id) -> str`

Единый текст промпта оркестрации (переиспользуется мастером создания №3 и раннером
№4; DRY — убирает дублирование строки из `task_api` №3).

### `task_api.py` (дополнения)

- `POST /api/tasks/run` — тело `{project_id, task_ids?: [...], only_runnable?: bool}`.
  Отбирает задачи через `select_tasks`, ставит на каждую `orchestration_prompt` в
  очередь agentmon. Возвращает `{enqueued: [ids], count}`.
- `GET /api/tasks/status?project_id=` — по каждой задаче `{id, title, overall, done,
  total}` (done/total — по включённым этапам). Для прогресса в UI.
- Рефактор `POST /api/tasks/create`: enqueue использует `orchestration_prompt`.

### Web-страница «Выполнить задачи»

Поле `project_id` → «Загрузить» (GET `/api/tasks/status`) рисует список задач с
чекбоксами и сводным статусом/прогрессом. Кнопки «Запустить выбранные» (POST run с
`task_ids`) и «Запустить все невыполненные» (POST run без `task_ids`,
`only_runnable=true`). «Обновить» перечитывает статус. Ссылка со страницы index.

## Как идёт прогон

`POST /api/tasks/run` только ставит задачи в очередь agentmon. Дальше существующий
диспетчер agentmon сам поднимает claude-сессию на каждую задачу очереди по очереди;
оркестратор (контент №3) ведёт этапы и обновляет `task.json`. Агрегированный статус
`GET /api/tasks/status` читается из `task.json` (источник истины прогресса), а не из
очереди (та отражает жизненный цикл сессии).

## Границы (не входит в №4)

- Движок прогона — существующий диспетчер agentmon (не переписываем).
- Бенчмарки (разворачивание тестовой базы, таймауты, оценка) — №5.
- Богатый дашборд/история прогонов — позже (здесь список + сводный статус).

## Тестирование

- `task_run`: `task_overall_status` для комбинаций (все done→done; есть failed→failed;
  есть running→running; смешанный pending→pending; нет включённых→done).
  `select_tasks`: по `task_ids`; `only_runnable` исключает done; без фильтров — все.
- `orchestration_prompt`: содержит `tasks/task#<id>` и ссылку на навык.
- `task_api`: `POST /api/tasks/run` ставит в очередь по задаче на выбранную (проверка
  через `queue.list`); исключает done при `only_runnable`; `GET /api/tasks/status`
  возвращает overall и done/total; неизвестный project → 404.
- Web-страница «Выполнить задачи» отдаётся (содержит заголовок).
- Полный набор тестов зелёный.
