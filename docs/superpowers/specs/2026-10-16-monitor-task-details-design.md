# Монитор: детальная карточка задачи (свёртка/разворот)

Дата: 2026-10-16

## Проблема

В окне «Монитор» (стартовая страница, стеки выполнения — `app/web/start.js`,
`renderStacks`) задача в стеке рисуется одной строкой: имя + статус. По задаче не
хватает данных о ходе выполнения:

- текущий этап;
- время начала и окончания;
- лимит длительности;
- время запуска/окончания обновления БД (если применимо);
- кнопка «открыть отчёт» по завершённому этапу (артефакт вида `ANALYZE.md`);
- номер итерации этапа.

Задачу нужно показывать **свёрнуто одной строкой**, а по кнопке разворачивать всю
информацию.

## Текущее состояние (факты из кода)

- **Оркестратор не имеет прямого канала к БД `agentmon`.** `template/.claude/tools/task_status.py`
  импортирует только `argparse/json/time/pathlib` — ни HTTP, ни sqlite. Хуки
  (`route_to_orchestrator.py`, `bsl_nudge.py`) и `SKILL.md` тоже без сети/БД.
  Оркестратор пишет прогресс **только в файл** `tasks/task#<id>/task.json`.
- **Мост «файл → БД» существует и работает по pull со стороны бэкенда:**
  `POST /api/env/projects/{pid}/refresh` (`app/src/agentmon/env/project_api.py:380`)
  читает `task.json` каждой задачи и переносит в БД `status / stage / started_at /
  finished_at`. Сейчас триггерится **вручную** (кнопка `refreshProject`, `start.js:37`),
  перерисовывает дерево; `stages_json` не переносит.
- **Монитор читает БД:** `GET /api/env/stacks` → `_enrich_items`
  (`app/src/agentmon/env/stack_api.py`) отдаёт только `item_id, task_id, task_name,
  project_id, task_status`.
- **Что пишется в `task.json` сейчас:** статусы этапов, `stage` (текущий),
  task-уровневые `started_at`/`finished_at`, артефакты этапов как файлы в каталоге
  задачи. Счётчик итераций — в **отдельном файле** `.iteration_count` (один на задачу),
  которым вручную управляет оркестратор (`SKILL.md`).
- **Чего нет нигде:** тайминги каждого этапа, тайминги обновления БД, итерация в
  `task.json`, API чтения артефакта.
- **Прецедент запуска VS Code:** `POST /api/env/projects/{pid}/open-vscode`
  (`project_api.py:428`) выполняет `popen(["code", path])`.
- **Автообновление Монитора:** `setInterval` каждые `REFRESH_INTERVAL_MS = 5000` мс
  перерисовывает дерево и стеки из БД (`start.js:442`).

## Принятые решения

1. **Слой-потребитель — расширяем существующий мост `refresh`** (не вводим второе
   параллельное чтение файлов). `refresh_project` дополнительно переносит в БД
   `stages_json` (с таймингами и итерациями этапов) и `db_update`. Монитор остаётся
   DB-only. Чистый эффект: Монитор отражает содержимое live `task.json`.
2. **Периодичность синка — 5 минут.** Отдельный таймер в `start.js` раз в 5 мин
   триггерит `refresh` для проектов, у которых есть задачи в running-стеках, затем
   `renderStacks`. Существующий 5-секундный ре-рендер из БД не трогаем (он дёшев).
3. **Итерацию переносим в `task.json`** вместо отдельного файла `.iteration_count`.
   Храним **по этапу** — `stage["iteration"]`.
4. **Кнопка «Отчёт» — для последнего завершённого этапа** (последний в порядке этапов
   со статусом `done`), в развёрнутой панели. Открывает артефакт в VS Code.

## Архитектура

Три слоя: запись (producer, в шаблоне проекта) → синхронизация/API (бэкенд Монитора)
→ фронтенд.

### Слой 1. Запись в `task.json` (producer)

Правим файлы шаблона (деплоятся в проекты):
`template/.claude/tools/task_status.py` и
`template/.claude/skills/task-orchestration/SKILL.md`.

`task_status.py` работает с `task.json` как с сырым словарём — добавление полей
безопасно.

1. **Тайминги этапа.** В `update()`:
   - при переходе этапа в `running`: `stage["started_at"] = now`;
   - при `done`/`failed`: `stage["finished_at"] = now`.
2. **Итерация этапа.** `stage["iteration"]` = `1` при первом запуске. Если этап
   уходит в `running`, а у него уже проставлен `finished_at` (повторный прогон в
   цикле develop↔testing/review): инкремент `iteration` и сброс `finished_at`.
   Делается автоматически в `task_status.py` — оркестратору больше не нужно вручную
   вести счётчик-файл.
3. **Тайминги обновления БД.** Новые подкоманды:
   - `task_status.py <dir> db-update start` → `data["db_update"] = {"started_at": now,
     "finished_at": null}`;
   - `task_status.py <dir> db-update done` → проставляет `finished_at`.
4. **`SKILL.md`:**
   - секция «Загрузка в базу после этапа develop (флаг update_db)»: обрамить загрузку
     в ИБ вызовами `db-update start` / `db-update done`;
   - секция «Циклический workflow»: читать лимит итераций (10) из `iteration`
     соответствующего этапа в `task.json`; архивирование артефактов
     (`DEVELOP.md`→`DEVELOP.<n>.md`) опирать на `iteration`; убрать упоминания файла
     `.iteration_count`.
5. **dataclass `Stage`** (`app/src/agentmon/env/task_schema.py`): добавить поля
   `started_at`, `finished_at` (дефолт `None`) и `iteration` (дефолт `1`), чтобы
   round-trip `from_dict`/`asdict` не падал на новых ключах.

Все отметки времени — epoch-секунды (как уже принято: `queue.py`, task-уровневые
`started_at`).

### Слой 2. Синхронизация и API (бэкенд Монитора)

1. **Расширить `refresh_project`** (`project_api.py:380`): помимо `status/stage/
   started_at/finished_at` переносить в БД `stages_json` (сериализованные этапы с
   новыми полями) и `db_update`. Защищённые статусы стека (`queued`/`stopped`) по
   `status` по-прежнему не перезаписываем.
   - Требуется колонка БД под `db_update` (или хранить его внутри `stages_json`/
     отдельного JSON-поля — уточняется на этапе плана по схеме `tasks`).
2. **Обогатить `_enrich_items`** (`stack_api.py`): в каждый элемент добавить:
   - `stage`, `started_at`, `finished_at`, `max_minutes`;
   - `db_update: {started_at, finished_at}` — только если у задачи включён `update_db`;
   - `stages: [{name, status, enabled, gate, approved, started_at, finished_at,
     iteration, artifact, artifact_exists}]`, где `artifact_exists` — проверка файла
     на диске;
   - `last_done_stage` — имя последнего по порядку этапа со статусом `done` (для
     кнопки «Отчёт»), либо вычисляется на фронте.
   - Деградация: нет данных этапов → поля `null`/пустой список (нормально для
     `planned`).
3. **Новый эндпоинт `POST /api/env/tasks/{tid}/open-report`** (тело `{stage}`), по
   образцу `open_vscode`:
   - резолвит каталог задачи (путь проекта + `task_schema.task_dir(identifier)`) и имя
     артефакта **из определения этого этапа** (защита от path-traversal: имя берём из
     `stages`, а не из тела запроса);
   - `popen(["code", artifact_path])`;
   - `404` если файла нет; `500 "команда 'code' не найдена в PATH"` как в прецеденте.

### Слой 3. Фронтенд (`app/web/start.js` + стили)

1. **Свёрнутая строка:** шеврон ▸, имя задачи, бейдж статуса, текущий этап, прошедшее
   время vs лимит (`now − started_at` / `max_minutes`).
2. **Разворот по кнопке ▾** — панель деталей:
   - Задача: начало, окончание, лимит; блок «Обновление БД: запуск / окончание»
     (показываем только если `db_update` присутствует);
   - Таблица этапов: этап · статус · итерация · начало · окончание;
   - Кнопка **«Отчёт»** у строки последнего завершённого этапа (`last_done_stage`,
     при `artifact_exists`) → `POST open-report` → открытие в VS Code.
3. **Синхронизация 5 мин:** отдельный `setInterval(..., 5*60*1000)` вызывает `refresh`
   для проектов с задачами в running-стеках, затем `renderStacks`.
4. **Сохранение состояния разворота** между ре-рендерами: множество развёрнутых
   `task_id`, повторно применяется после `renderStacks`.
5. **DnD не ломаем:** шеврон и кнопки — `event.stopPropagation()`; строка остаётся
   `draggable`.

## Краевые случаи

- `planned`-задача ещё не запускалась → этапы `pending`, таймингов нет → «—».
- Повторный прогон этапа → `iteration > 1`, `started_at` текущего прогона, `finished_at`
  сброшен до завершения.
- `update_db` выключен → блок обновления БД скрыт.
- Нет завершённых этапов → кнопка «Отчёт» не показывается.
- `code` не в PATH → понятная ошибка в `alert` (как в `openVsCode`).
- Нет `task.json` / битый JSON → `refresh` пропускает задачу (как сейчас), поля `null`.

## Границы (YAGNI)

- Не рендерим Markdown в браузере и не делаем модалку/вкладку — отчёт открывается в
  VS Code.
- Не вводим WebSocket/push от оркестратора — синк остаётся pull по таймеру.
- Не трогаем 5-секундный ре-рендер из БД.
- Не добавляем историю таймингов по итерациям сверх текущего прогона этапа.

## Тестирование

- `task_status.py`: unit-тесты на простановку `started_at`/`finished_at`/`iteration`
  (первый прогон и повторный), на подкоманды `db-update start|done`.
- `refresh_project`: тест, что `stages_json` и `db_update` переносятся в БД; что
  `queued`/`stopped` по `status` не перезаписываются.
- `_enrich_items`: тест формы обогащённого элемента (этапы, тайминги, `artifact_exists`,
  `last_done_stage`).
- `open-report`: тест запуска `code <artifact>` (мок `popen`, как в
  `test_project_actions.py`), 404 на отсутствующий файл, 500 на отсутствие `code`.
- Фронтенд (env-тесты, как `test_start_page.py`): свёрнутая строка, разворот,
  сохранение состояния, наличие кнопки «Отчёт» у последнего завершённого этапа.
