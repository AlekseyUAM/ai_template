# Фазы развития проекта

Проект (окружение ИИ-разработки на 1С) развивается фазами. Ниже — границы каждой.

## Фаза 0 — Прототип (ЗАВЕРШЕНА)

Базовый сквозной прототип на SQLite + файлах, на базе вендоренного `agentmon` (`app/`):

- **Ядро + установщик** (№1): структура окружения на диске, мастер «Создать проект»
  (одностраничный), генерация `.mcp.json`/`docker-compose.mcp.yml`, выгрузка cf/cfe,
  регистрация проекта. Источник истины — `ai1c.config.json`.
- **Содержимое окружения** (№2): субагенты (analyst/architect/developer/tester/
  reviewer/orchestrator), скилы-руководства, правила, Python-хуки, инструменты;
  вендоринг cc-1c-skills (без дублей) + `1c-batch`; деплой через `content.py`.
- **Система задач** (№3): `tasks/task#<id>/` (`task.json` + `TASK.md` + артефакты
  этапов), статус-CLI, API и мастер «Создать задачу», контент оркестрации.
- **Автономный раннер** (№4): отбор задач, сводный статус, постановка в очередь,
  страница «Выполнить задачи».
- **Доработки**: деградируемый Вход субагентов, хук-роутер к оркестратору, ветка git
  на старте задачи; шаблон окружения в корневом `template/`; тёмная тема GitHub;
  удаление чата (две страницы: Проекты, Агенты).
- **Detached-мониторинг**: агенты — отдельные процессы (`claude -p`), слежение по
  PID + код выхода + JSONL + `task.json`; устойчивость к перезапуску монитора.

Состояние: всё на `master`, локально; полный набор тестов зелёный. Это прототип:
хранение — SQLite + файлы, UI — две простые страницы.

## Фаза 1 — Продуктовый UI и модель данных (ЗАВЕРШЕНА*)

Превращение прототипа в удобный продукт.

\* Реализованы все буллеты ниже (PostgreSQL-адаптер, стартовая страница и панели,
справочник Проекты с одностраничным мастером и валидациями, справочник MCP под
8 видов, задачи с полем тестов и гейтами, тестовые заглушки, возможности MCP/скилов
в `template/agents`).

Кнопка «Развернуть в Docker локально» работает: `mcp_docker_recipes` задаёт рецепт
на каждый docker-вид (образ, маппинг порта host→внутренний, env, тома), endpoint
`POST /api/mcp/{id}/launch/stream` собирает образ при отсутствии и запускает
контейнер, **стримя лог сборки и запуска построчно** (FastAPI `StreamingResponse`;
UI читает поток и дописывает в панель лога в реальном времени). Блокирующий
`POST /api/mcp/{id}/launch` сохранён (лог целиком).

Проверено вживую: `code-index` (поднят на реальном каталоге, MCP отвечает на `/mcp`)
и `bsl-ls` (образ собран из `app/docker/mcp/bsl-ls.Dockerfile`: BSL LS 1.1.0-rc.6
плюс FastMCP-обёртка с единственным инструментом `check`, эндпоинт `/mcp`).
Сборка образов идёт с `--network=host` (в sandbox DNS
сборочного namespace недоступен). Поля-предпосылки: `1c-platform` — обязательный
«Путь к платформе» (`ONEC_PLATFORM_PATH` + ro-монтирование); `1c-naparnic` — токен
code.1c.ai + интернет, запуск из готового образа (Dockerfile только в апстриме), на
Linux поднимается в сети хоста (`--network=host`) для внешнего DNS (bridge в sandbox
не резолвит `code.1c.ai`).

- **Хранилище → PostgreSQL**: проекты, задачи, MCP-серверы — во внутренней БД.
- **Стартовая страница** «Agent Monitor v.{версия}»: верхнее меню — справочники
  (Проекты, Задачи, MCP); две панели — «Проекты и задачи» и «Выполнение». Ничего
  лишнего.
- **Панель «Проекты и задачи»**: дерево проект → задачи (удаление, название, путь,
  время выполнения, статус, этап). Статусы задачи: запланирована, в очереди,
  выполняется, остановлена, ожидает пользователя.
- **Панель «Выполнение»**: стеки выполнения — перетаскивание запланированных задач,
  запуск/стоп/удаление стека (удаление срубает процесс), последовательное выполнение
  внутри стека, параллельные стеки, переупорядочивание в незапущенном стеке.
- **Справочник Проекты**: карточка (имя/каталог неизменяемы, кнопка «обновить версию
  окружения» → мастер с предзаполненными полями, хранится версия окружения).
  Мастер создания — **одностраничный** (разделы Проект, Разработчик, Платформа, База,
  MCP, Модели агентов, Действия на одной странице, без шагов Далее/Назад — решение
  зафиксировано, отменяет прежний «многостраничный» вариант),
  валидация имени (python-идентификатор), пустой каталог, проверка доступа к базе,
  проверка требований (python и т.п.), лог разворачивания.
- **Справочник MCP**: карточка с видами MCP, полями и значениями по умолчанию —
  см. подраздел «Справочник MCP» ниже.
- **Задачи**: владелец (ссылка на проект), поле «тесты» (обязательно при галке tests;
  testing недоступен без tests), кнопки «все/снять галочки», **гейты** (остановка и
  ожидание OK пользователя после выбранных этапов).
- **Тестовые задачи**: заглушки (sleep ~1 мин → успех) для проверки стеков/монитора.
- **Субагенты `template/.claude/agents`**: прописать возможности стандартных MCP
  (считаем все поднятыми) и возможности скилов `template/.claude/skills`.

### Справочник MCP

Инструкции по развёртыванию каждого вида (кнопкой, вручную и на отдельном
сервере) — в `docs/mcp/`.

**Поведение карточки (общее для всех видов):**

- Поля карточки растянуты на всю ширину — как в карточках задач и проектов.
- Поле «Назначение» — многострочное, как поле «План» в создании задачи.
- Поле «Наименование» — обязательное.
- Поле «Подключение» формируется автоматически при изменении полей «Имя в .mcp.json»,
  «URL» и «Порт» (состав зависит от вида).
- **Исправлено:** первое нажатие «Добавить» на странице MCP сразу открывает форму
  создания (надёжный тоггл по инлайн-стилю формы).

**Виды MCP и поля карточки:**

- **Произвольный** — поля: Наименование, Назначение, Подключение. Подключение по
  умолчанию:
  ```json
  "name": { "type": "http", "url": "http://localhost:8000/mcp" }
  ```
- **Метаданные (http-сервис в 1С)** — поля: Наименование, Имя в .mcp.json, Назначение,
  URL, Подключение. Имя в .mcp.json по умолчанию `1c-md`; URL по умолчанию `localhost`;
  Назначение по умолчанию «Вся информация об актуальных метаданных конфигурации».
  Подключение:
  ```json
  "1c-md": { "type": "http", "url": "http://localhost/my_database/hs/mcp" }
  ```
  Кнопка «Скачать cfe» → `deps/mcp_tools_cfe/MCP_Сервер.cfe`.
- **Метаданные + произвольные запросы (http-сервис в 1С)** — поля: Наименование, Имя
  в .mcp.json, Назначение, URL, Подключение. Имя в .mcp.json по умолчанию `1c-md`; URL по
  умолчанию `localhost`; Назначение по умолчанию «Произвольные запросы к данным, вся
  информация об актуальных метаданных конфигурации». Подключение — как у
  «Метаданные». Кнопка «Скачать cfe» →
  `deps/mcp_tools_cfe/1c-mcp-tools-1.0.6.cfe`.
- **Статический анализ BSL** — поля: Наименование, Имя в .mcp.json, Назначение, URL,
  Порт, Подключение. Имя в .mcp.json по умолчанию `bsl_ls`; URL по умолчанию `localhost`;
  Назначение по умолчанию «Статический анализ кода на соответствие стандартам 1С».
  Подключение:
  ```json
  "bsl_ls": { "type": "http", "url": "http://localhost:8001/mcp" }
  ```
  Кнопка «Развернуть в Docker локально» поднимает контейнер **только с BSL LS**
  (без кодовой базы, в отличие от `deps/mcp-bsl-lsp-bridge`). В образе —
  FastMCP-обёртка с единственным инструментом `check(code, config, filename)`:
  проверка stateless, код пишется во временный каталог, а настройки передаются
  содержимым `.bsl-language-server.json` в самом вызове (файл копируется в проект
  из шаблона окружения). Доступа к кодовой базе у сервера нет.
- **Справка по платформе** — поля: Наименование, Имя в .mcp.json, Назначение, URL, Порт,
  Подключение. Имя в .mcp.json по умолчанию `1c_platform`; URL по умолчанию `localhost`;
  Назначение по умолчанию
  «Справочная информация по встроенным функциям, типам данных, методам и свойствам
  платформы». Подключение:
  ```json
  "1c_platform": { "type": "sse", "url": "http://localhost:8002/sse", "transport": "sse" }
  ```
  Кнопка «Развернуть в Docker локально» (см. `deps/docker_1c_sandbox/mcp-bsl-context`).
- **1С:Напарник** — поля: Наименование, Имя в .mcp.json, Назначение, URL, Порт, Токен,
  Подключение. Имя в .mcp.json по умолчанию `1c_naparnic`; URL по умолчанию `localhost`;
  Назначение по умолчанию
  «Объяснение логики кода, любые вопросы по информационно-технологическому
  сопровождению 1С». Подключение:
  ```json
  "1c_naparnic": { "type": "http", "url": "http://localhost:8003/mcp" }
  ```
  Кнопка «Развернуть в Docker локально» (см. `deps/docker_1c_sandbox/mcp-bsl-context`).
- **Индексированная кодовая база (в Docker локально)** — поля: Наименование,
  Имя в .mcp.json, Назначение, URL, Порт, Каталог кодовой базы (обязательный),
  Имя проекта — alias репозитория (обязательное), Подключение. Имя в .mcp.json по
  умолчанию `code_index`; URL по умолчанию `localhost`; Назначение по умолчанию
  «Полнотекстовый поиск по функциям и классам,
  граф вызовов, паспорт объекта, смысловой поиск процедур по именам, синонимам и
  комментариям». Подключение:
  ```json
  "code_index": { "type": "http", "url": "http://localhost:8004/mcp" }
  ```
  Кнопка «Развернуть в Docker локально» (см. `deps/code-index-mcp`). Каталог
  кодовой базы монтируется в контейнер как `/repos/src`, alias репозитория в
  `daemon.toml` равен имени проекта.
- **Индексированная кодовая база (локально)** — поля: Наименование, Имя в
  .mcp.json, Назначение, URL, Порт, Каталог кодовой базы (обязательный),
  Имя проекта — alias репозитория (обязательное), Каталог code_index
  (обязательный), Подключение. Имя в .mcp.json по умолчанию `code_index`; URL по
  умолчанию `localhost`; порт по умолчанию `8005`; Назначение — как у docker-вида.
  Кнопка «Развернуть локально»: скачивает бинарь `bsl-indexer` с GitHub Releases
  под хост (Windows x64 / Linux x64 / macOS arm64), пишет `daemon.toml` с реальным
  путём каталога кодовой базы, ставит **user-level автозапуск** двух процессов
  (индексатор `daemon run` и MCP-сервер `serve`; systemd --user / LaunchAgent /
  Планировщик Windows) и сразу их стартует. Соединение —
  `http://localhost:8005/mcp`.

**Отдельные задачи (ВЫПОЛНЕНО):**

- **cfe как часть проекта**: `deps/mcp_tools_cfe/MCP_Сервер.cfe` и
  `deps/mcp_tools_cfe/1c-mcp-tools-1.0.6.cfe` входят в поставку; кнопки
  «Скачать cfe» в карточках «Метаданные» и «Метаданные + произвольные запросы»

- **Исследование BSL-моста**: обвязку `deps/mcp-bsl-lsp-bridge` решили не
  переделывать — она ориентирована на индексацию кодовой базы. Вместо неё вид
  «Статический анализ BSL» получил тонкую FastMCP-обёртку (`check`) над
  CLI-режимом `analyze` BSL LS: stateless-проверка присланного кода, без индекса
  и доступа к ФС проекта. Реализация — `app/docker/mcp/bsl_check_server.py`,
  план — `docs/plans/bsl-check-mcp.md`.
- **Автоклонирование исходников deps**: репозитории `deps/` не входят в состав
  шаблона (`.gitignore`), поэтому перед сборкой образа отсутствующий исходник
  клонируется с GitHub (`mcp_sources`, `repo_url` в `BuildSpec` рецепта).
  Скачивание видно в логе — и в блокирующем, и в стриминговом развёртывании.

### Windows — требуемые доработки (docker-развёртывание MCP)

Приложение таргетит и Windows (`bootstrap.py`/`run.py`). Непосредственно docker-часть
справочника MCP проверена на Linux; для Windows (Docker Desktop, WSL2-бэкенд, Linux-
контейнеры) нужны доработки — реализованное и остающееся:

- **`--network=host` при сборке** (СДЕЛАНО): `mcp_docker.build_cmd` добавляет
  `--network=host` только на Linux (`sys.platform`). На Docker Desktop host-сеть не
  поддерживается так же и не нужна (DNS в сборке работает) — флаг не добавляется.
- **Пути bind-монтирования томов** (ОСТАЁТСЯ): `launch_params` строит тома как
  `"<host>:<container>"`. На Windows хостовые пути (`C:\…`, обратные слэши, двоеточие
  диска) конфликтуют с разделителем `host:container` и форматом Docker Desktop.
  Нужна нормализация пути (слэши/драйв-леттер → `C:/…`) для `catalog_dir`
  (code-index), каталога состояния `.ai1c/mcp-state` с `daemon.toml` и пути платформы;
  плюс требование «расшарить» диск в Docker Desktop (File Sharing).
- **`1c-platform` — монтирование пути платформы** (ОСТАЁТСЯ): рецепт монтирует путь
  платформы «тем же путём» (`<path>:<path>:ro`) — это Linux-допущение. На Windows путь
  платформы (`C:\Program Files\1cv8\…`) нельзя использовать как внутренний путь
  Linux-контейнера: нужен фиксированный внутренний путь (например `/opt/1cv8`) и
  `ONEC_PLATFORM_PATH`, указывающий на него, при монтировании Windows-пути снаружи.
  Отдельно проверить, что серверу `mcp-bsl-context` достаточно файлов справки из
  каталога платформы (а не запуска самой платформы 1С).
- **Предпосылки среды** (ОСТАЁТСЯ, документация): Docker Desktop с включёнными Linux-
  контейнерами/WSL2; образы `bsl-ls`/`code-index`/`mcp-bsl-context` — Linux.

Остальные части Фазы 1 кроссплатформенны: бэкенд на Python/FastAPI (SQLite/Postgres
через `psycopg[binary]` — есть колёса под Windows), статический web, генерация
`.mcp.json`/конфигов, скачивание cfe. Отдельной Windows-доработки они не требуют.

## Фаза 2 — Бенчмарки (ЗАВЕРШЕНА)

Эталонный набор задач для оценки качества окружения собран в `benchmark/` и
прогнан через AgentMon на реальной конфигурации 1С.

### Реализовано

- **`benchmark/cf`** — XML-выгрузка конфигурации 1С (БСП, редакция 3.1) —
  исходное состояние, на котором выполняются задачи. Объектов, создаваемых
  задачами, в ней нет.
- **`benchmark/tasks/task##001…004`** — четыре задачи в состоянии сразу после
  заведения в AgentMon: только `TASK.md` и `task.json`, без артефактов
  выполнения:
  - `#001 Учетная политика`;
  - `#002 Оперативный учет`;
  - `#003 Отчет Продажи`;
  - `#004 Отчет Остатки товаров`.

  Задачи выполняются последовательно на одной конфигурации: каждая следующая
  может опираться на объекты, созданные предыдущими.
- **Референсный прогон** (7 и 9 ноября 2026) — все четыре задачи доведены до
  статуса `done`:

  | Задача | Этапы | Итерации | Длительность |
  |--------|-------|----------|--------------|
  | #001 | develop | 1 | 8 мин |
  | #002 | analyze → plan → tests → develop → testing → review → docs | develop/testing — 8, review — 4 | 6 ч 43 мин |
  | #003 | plan, develop | 1 | 32 мин |
  | #004 | develop | 1 | 8 мин |

  У `#002` финальный прогон тестов — 5 из 5 успешно; артефакты итераций
  (`DEVELOP.1.md`, `TESTING.1.md` и т.п.) в набор не входят — в `benchmark/`
  задачи лежат в исходном состоянии.
- **Использование**: конфигурация загружается из `benchmark/cf` в `src/cf`
  проекта, задачи копируются в `tasks/` и выполняются через AgentMon.
  Состав набора — в `benchmark/README.md`.

Отдельный каркас автоматического сбора метрик и цикл улучшения окружения не
строились: прогон идёт штатным AgentMon, а этапы, итерации, длительность и
результаты тестов видны в `task.json`, артефактах задачи и журналах прогона.

## Фаза 3 — Удалённый доступ (ЗАВЕРШЕНА)

### Реализовано

**Provisioner — абстракция целевой машины (слой `env/`).**
Рядом с двумя имеющимися протоколами (`AgentRunner`, `SessionFiles`) добавлен третий —
`Provisioner`: операции над файловой системой целевой машины и запуск команд на ней.
Реализации:

- `LocalProvisioner` — локальная ФС, тот же хост что и монитор;
- `SshProvisioner` — удалённый хост: SFTP для файловых операций, exec-канал для
  команд поверх существующего SSH-соединения (`_Connection`).

Весь слой разворачивания окружения (`scaffold`, `content`, `venv`, `devbase`,
`nethasp`, `project_checks`) теперь работает через `Provisioner`, поэтому один и тот
же код создаёт проект как локально, так и на удалённом хосте.

**Создание проекта по SSH.**
Мастер создания проекта получил раздел **«Размещение»**: бэкенд «Локально» или
«Удалённо (SSH)» + поля хост/порт/пользователь/путь к ключу. В разделе «Платформа»
добавлено поле **«Сервер лицензий»** (адрес NETHASP-сервера, необязательное).

При выборе SSH-бэкенда всё разворачивание происходит **на удалённом хосте**:

- scaffold каталогов и шаблона окружения (`template/`);
- генерация `.mcp.json` и конфигов;
- изолированный `.venv` проекта (Python на удалённой машине);
- `.1c-devbase.json`;
- `git init` + первый коммит;
- `conf/nethasp.ini` — если задан «Сервер лицензий».

Проверки при создании (пустой каталог, доступность базы 1С, наличие Python) также
выполняются на удалённом хосте через `Provisioner.run`.

Модель ресурсов: тестовая БД — клиент-серверная (сервер 1С), лицензии — по сети
(NETHASP), платформа 1С на Linux — всё доступно по TCP; USB-ключи, файловые базы
через SSHFS и тому подобное не предусмотрено.

**Docker-бэкенд (проект 1С в контейнере).**
Третий backend рядом с `local`/`ssh`: `DockerBackend` с `DockerProvisioner`/
`DockerRunner`/`DockerFiles` (модуль `backends/docker.py`) и `_DockerContainer`
(жизненный цикл контейнера). Мастер получил третий вариант размещения —
«В Docker-контейнере» (`value="docker"`). Модель: **чистый контейнер** на выбранном
Docker-демоне (локальном или удалённом); файлы проекта живут в контейнере, все
операции — через `docker exec`/`docker cp`, симметрично SSH-бэкенду. Создание
проекта (scaffold, шаблон, `.mcp.json`, `.venv`, `.1c-devbase.json`, `git`,
`nethasp.ini`, проверки) идёт через
`DockerProvisioner` внутри контейнера; агент `claude` запускается `docker exec -it`,
журналы сессий читаются `docker exec`.

- Образ агента — **свой** `app/docker/agent-image/Dockerfile`, без зависимости от
  `deps/docker_1c_sandbox`: Ubuntu 22.04 + Node.js 20 + Claude Code + Xvfb +
  платформа 1С, устанавливаемая из дистрибутива build-контекста
  (`*.run --mode unattended`); симлинк `/opt/1cv8/current`.
- Тег образа — `ai1c-agent:<версия платформы>`; образ переиспользуется между
  проектами с той же версией. Если образа нет, мастер требует **«Путь к
  дистрибутиву платформы (.zip)»** (проверка — `POST
  /api/env/projects/check-image`) и собирает образ первым шагом создания, стримя
  лог сборки в UI (`--progress=plain`). Транзиентные сетевые ошибки сборки
  повторяются (до 6 попыток; buildkit продолжает с кеша слоёв). Сборка идёт на
  выбранном docker-демоне — локальном или удалённом.
- Сеть: bridge + `--add-host=host.docker.internal:host-gateway`.
- Том `/workspace` — корень проекта 1С внутри контейнера.
- Платформа 1С: `/opt/1cv8/current`.
- При выборе бэкенда «docker» мастер предзаполняет поля **Путь** (`/workspace`) и
  **Путь к платформе** (`/opt/1cv8/current`), если они ещё не заполнены.
- Поле **Образ контейнера** в мастере — наследие прежней модели: при создании
  проекта `conn["image"]` перекрывается вычисленным тегом.

**Удалённые операции окружения (cf/cfe, tools-install, update-env).**
Выгрузка `cf`/`cfe` (`platform_dump.dump`), установка инструментов
(`tools_install.install_tools`) и обновление окружения (`update-env`) теперь идут
через `Provisioner` на **целевой** машине — работают и для ssh, и для docker, не
только локально. Гейт `is_local` снят; DESIGNER/`pip` исполняются через
`prov.run`/`prov.venv_python` на цели. `update-env` стал backend-aware: берёт
`backend`/`conn` проекта из `ProjectRegistry` и резолвит нужный provisioner.
`Provisioner.run` получил опциональный `timeout` (при истечении — единообразный
`RunResult(124)`, без разнобоя исключений бэкендов).

**docker-гигиена.** `DockerFiles.list_files`/`read_from` теперь отличают упавший
контейнер/демон (коды docker `125/126/127` или маркеры в stderr → `mark_broken`,
монитор видит недоступность) от «сессий ещё нет» (`find` rc=1 → просто `[]`). `~/.claude`
контейнера проекта (журналы сессий + авторизация claude) вынесен в именованный том
`{имя}-claude` → переживает пересоздание контейнера. (ssh `list_files` уже различал
через SFTP — его не трогали.)

**Docker-поверх-SSH (docker-over-ssh).**
Docker-бэкенд умеет целиться в **удалённый** Docker-демон через
`docker -H ssh://user@host` — все команды (`docker exec`, `docker cp`,
`docker run`, чтение JSONL-журналов, PTY-агент) уходят на удалённый демон;
локальный Docker не задействован. Параметры задаются в `conn` проекта
полями `host`/`user`/`port` (или явным полем `docker_host`); мастер
создания проекта предоставляет поля **Docker-хост**, **Пользователь** и
**SSH-порт** — пустые значения означают локальный режим (без изменений).
Образ `ai1c-agent:<версия>` собирается и проверяется на **удалённом** демоне —
том же, где запускается контейнер проекта; аутентификация SSH работает через
`ssh-agent` или `~/.ssh/config`.

**Состояние фазы.** Фаза завершена: работают бэкенды `local`, `ssh`, `docker` и
`docker-over-ssh`; все операции окружения (создание проекта, cf/cfe,
tools-install, update-env) идут через `Provisioner` на целевой машине. Монитор
(control plane) запускается **только на хосте**: режим монитора в Docker был
реализован и затем удалён как неоправданно усложнявший сопровождение. Проекты в
контейнерах при этом поддерживаются docker-бэкендом.
